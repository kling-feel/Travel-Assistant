# P3.1e4 完整旅程验收记录与本机操作指南

> 2026-10-21｜功能分支验收记录。结论：对话、交易边界、重启恢复通过；航班时长数据存在系统性不合理，暂不进入主线发布。

## 1. 环境边界

本轮在独立的 `travel_p31e4` PostgreSQL 项目中验收，数据库宿主端口为 `5434`，页面和 API 为 `http://127.0.0.1:8002/app`。正式演示库仍由默认 Compose 项目管理，使用数据库端口 `5433`，常规页面地址为 `http://127.0.0.1:8000/app`。两套数据库不共用卷；不要把隔离库里的测试订单当作正式演示订单。

开工时正式库只读基线为：`as_of=2026-10-20`，机票订单 2、酒店订单 2、租车订单 0、待确认动作 6。收尾只读复核完全相同。隔离库按 2026-10-21 重新导入；导入前备份、失败回放后备份和干净重放前备份均位于被 Git 忽略的 `data/generated/`。没有重置正式库或删除任何数据库卷。

### 发布阻断项：航班时长

浏览器中的 `SIM-3831` 从上海虹桥机场 2026-10-26 01:18（当地）起飞，却在伦敦盖特威克机场 2026-10-25 19:28（当地）到达。换成统一时区后，实际飞行时间约 2.17 小时，显然不足以完成该航段。这不是单纯的跨时区显示错误。隔离库只读地理审计发现：10,594 条距离至少 5,000 公里的计划航班中，10,049 条飞行时间不足 5 小时；约占这组的 94.9%。因此落地酒店的入住日期虽然严格来自数据库，却可能沿用错误的航班到达日。当前不能把这一版视作可可信展示的完整旅行规划。

原始源数据保留，修复另按 [P3.1e5 计划](操作计划/P3.1e5-航班时长与到达日质量修复.md)评审；在修复和重新验收前，G-16 主线合并及 GitHub 同步暂缓。

## 3. Windows 本机复现步骤

以下命令在项目目录的 PowerShell 执行。先启动 Docker Desktop；已有隔离卷时**只启动**，不要重复运行迁移或导入，也不要运行带 `--reset-demo` 的命令。端口 `8002` 若被占用，先停止之前的隔离 API 进程。

```powershell
$env:POSTGRES_PORT = '5434'
docker compose -p travel_p31e4 up -d --wait db
$env:PORT = '8002'
.\.venv\Scripts\python.exe main.py
```

在浏览器打开 `http://127.0.0.1:8002/app`，用 `demo1` 登录；密码从本机 `.env` 的 `DEMO_TRAVELER_1_PASSWORD` 读取，勿复制到聊天或仓库。可先问“从上海到伦敦最早什么时候有航班”，再说“就预订最早那班，顺便找落地附近酒店”。核对机票卡对象、起飞时间与金额；订单只有在点击卡片、核对详情并再次确认后才会增加。当前航班时长缺陷会影响落地日期，遇到跨洲航段时请把结果视作待修复的测试数据，不按其安排真实行程。地点、天气查询可检验阿里云搜索的只读来源。

结束时在运行 API 的 PowerShell 按 `Ctrl+C`，另开 PowerShell 在项目目录执行：

```powershell
$env:POSTGRES_PORT = '5434'
docker compose -p travel_p31e4 stop db
```

隔离卷保留，下一次可直接启动。不要用 `down -v` 删除卷。默认项目的 `8000` 页面和 `5433` 数据库不受这两条隔离服务命令影响。
