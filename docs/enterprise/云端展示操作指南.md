## 2. 当前云端程序的结构

云端单独使用 `compose.cloud.yaml`，与本机 `compose.container.yaml` 和正式演示库隔离。数据库和应用均无宿主机公开端口；Caddy 只发布 80／443。普通 `up` 不运行数据库初始化。首次初始化需先对空库作备份，迁移和虚构数据导入成功后记录批次清单；以后重启只核对清单，绝不自动平移时间或覆盖订单。

若购买 2 GiB 规格，每次云端 Compose 操作都叠加 `-f compose.cloud.2g.yaml`。该文件只给应用 768 MiB、数据库 640 MiB、代理 128 MiB 及一次性任务设置资源上限，不改正式 80／443、域名证书或私有数据卷。备份、初始化、账号管理及恢复分时执行，必要时先停应用与代理；不得把本机 8021／8022 和内部证书的试验覆盖文件带上云。正式主机仍须检查整机内存、OOM、磁盘和真实请求。

公开页面只允许已有授权账号登录；不开放注册。初始 `demo1`／`demo2` 必须停用，先创建一个单独授权账号，再启动应用。管理命令只在容器内执行，随机密码写入服务器上 Git 忽略的私有文件，不打印到终端。给面试官使用独立账号；展示后停用或轮换其密码。

云端配置使用香港主机 Git 忽略的 `data/generated/cloud.env`，绝不复制本机整份 `.env` 或 `data/generated/p33b-next.env`。P3.4c2d 已在服务器用生成器创建独立数据库／JWT／种子账号随机值，并只转移旅客授权的两项本机服务密钥；私有目录 `0700`、文件 `0600`，字段级预检通过。模板里的服务密钥默认为空，已有文件会拒绝覆盖；基础镜像使用固定摘要。域名、密钥或镜像摘要不符时应用拒绝启动。`requirements.lock` 固定 Python 依赖，香港主机应用镜像的 `pip check` 已通过；P3.4c2f 的实际服务连通、授权登录与重启检查也已通过。

执行云端操作前，先运行 `python3 scripts/preflight_cloud_env.py`。它检查文件位置与权限、域名、日期、独立密码、服务商参数、测试模式和固定镜像摘要；只报告字段名，不显示密钥。若使用别的文件名，传 `--env-file data/generated/<文件名>.env`。P3.4c2e 的预检已通过，但这只表示配置结构就绪，不能代替 DNS、密钥实际连通和公网验收。旅客目前授权云端暂用本机既有的两项服务密钥。

购买 2 GiB 套餐时统一用 `python3 scripts/cloud_compose.py <动作>` 管理云端 Compose。入口固定组合 `compose.cloud.yaml` 和 `compose.cloud.2g.yaml`，默认读取 Git 忽略的 `data/generated/cloud.env`，默认项目名 `travel-cloud`；可在动作前显式指定 `--env-file` 和 `--project`。它只允许下述动作，没有删容器／删卷入口。`--dry-run` 只展示无密钥的命令结构；私有配置必须先存在，且不会打印其内容。

```text
python3 scripts/cloud_compose.py services       # 只核对服务清单
python3 scripts/cloud_compose.py build          # 构建镜像；2 GiB 主机需观察整机内存
python3 scripts/cloud_compose.py db-up          # 启动新空数据库
python3 scripts/cloud_compose.py empty-backup   # 首次空库备份，拒绝覆盖
python3 scripts/cloud_compose.py init           # 只在空库与已验证备份上初始化一次
python3 scripts/cloud_compose.py admin create interviewer "面试展示" --output /run/travel-credentials/interviewer.json
python3 scripts/cloud_compose.py admin disable-seeds
python3 scripts/cloud_compose.py app-up          # 启动应用和公网代理
python3 scripts/cloud_compose.py status          # 核对容器状态
python3 scripts/cloud_compose.py stop            # 停止服务，保留卷
```

上面是**顺序示意**，不是现在可直接运行的购买或部署指令。执行前须核对目标项目为空、主机内存与端口，备份格式有效，授权账号密码文件只留私有目录，DNS 已指向实际服务器。`init` 成功后不得再次执行；`empty-backup` 仅用于首次空库。`stop` 不删除数据库、证书或备份卷。异地加密备份和新卷恢复另按本计划的验收步骤完成，不能仅靠 `empty-backup`。

## 3. P3.4c 购买和上线的顺序

以下保留 P3.4c 首次部署时制定的完整执行顺序：第 1～5 步及第 6 步的少量业务／真实服务抽样已完成；第 7 步的手动服务器外加密恢复和第 6 步的隔离九类交易已由 P3.4c3a／b 完成。修复版已完成 P3.4c3c1b 短时基础入口复验并补齐云防火墙规则核对；正式云端登录／交易对话及展示日流程仍待单独核对，OSS 自动留存另属 P3.4c3c2。**不能把下面的首次初始化示意命令重新用于现有数据库。**

1. 已购买并核对香港 Ubuntu 24.04 服务器和 `adzyforever.com`；根域与 `www` 均已指向该实例。正式部署将以根域为主地址，`www` 跳转到根域；在开启公网前再次核对外部 DNS。实际购买与域名管理仍由旅客负责。
2. P3.4c2c 已完成专用密钥登录、非 root 管理账号、关闭远程 root／密码认证、Ubuntu 24.04 补丁和 Docker Engine／Compose 安装。P3.4c3c1b 已核对云防火墙：入站开放 HTTP 80、HTTPS 443、SSH 22 与 ICMP，没有 8000／5432 或其他开放规则；SSH 22 当前对所有 IPv4 来源开放，后续按旅客出口地址规划限制。上线时仍要检查 Docker 实际发布端口，因为容器端口配置与云防火墙规则是两道独立边界。
3. 用已经发布、通过审计的仓库版本部署。创建新云端忽略配置，核对域名 DNS、证书邮箱、独立数据库和 JWT 随机值、新的模型／搜索密钥，以及 Python、PostgreSQL、Caddy 三种基础镜像的版本与摘要。环境文件和账号文件只让管理员读取。禁止把这些内容放进 Git、镜像构建上下文、截图或聊天。
4. 在**新 Compose 项目、新卷**中构建镜像、启动空 PostgreSQL；验证项目标签、卷和空库。作迁移前 `pg_dump -Fc` 备份并检查目录后，显式运行一次 `backup` 与 `init`。初始化失败后先查明情况，不在非空库重新运行，不使用 `down -v`。
5. 用 `account-admin` 预置单独授权账号，将一次性密码文件私下交给对应使用者，并停用 `demo1`／`demo2`；随后启动应用和代理。核对应用只监听容器网络、数据库无公开端口、HTTP 自动跳转 HTTPS、域名证书有效、`/docs`／`/health` 等内部入口在公网不可访问。
6. 分别用未登录、错误账号、授权账号做访问验收；用两个独立账号验证本人数据隔离。执行虚构航班、酒店、租车查询和九类待确认动作的抽样旅程；未点击确认前订单不能变。只在密钥授权且有必要时做少量真实模型与联网搜索连通测试，随后对照服务商账单。
7. 制作正式备份：`pg_dump -Fc`，验证备份目录，使用独立备份密钥加密并上传到服务器外的私有存储；保留至少 7 份每日备份。演示结束和每次升级前额外备份。解密私钥与备份分开保管，在全新空卷实际恢复，核对批次日、迁移、订单、会话、动作和审计摘要。单机服务器快照仅作辅助。异地存储选型、加密工具、自动任务和实测恢复命令要在 P3.4c 确定并验证，未完成前不把云端标为可恢复。
8. 展示结束后先确认备份和费用，再停止代理、应用及数据库容器，保留数据卷与证书卷；平时关闭公网。下次展示前先启动并确认 DNS、证书、数据库就绪、授权登录和一轮真实旅程。包月套餐仍按购买周期收费。

## 4. 运行期能看到什么

旅客页面会说明所有供给与订单均为虚构演示，交易确认卡只改变模拟数据。云端按账号限制短时登录失败、对话频率和同时处理轮数；这些是防滥用措施，不按费用自动停机。模型及联网搜索调用记录只含账号、服务类别、结果类别、可获得的 token 数和时间，不记录提示词、响应正文或密钥。旅客可查看自己的调用量；管理员可运行 `scripts/usage_report.py` 查全站次数。实际金额由服务商账单确定。

模型／搜索服务返回余额不足、限流或鉴权失败时，页面应明确提示，绝不能声称已完成实时联网核验。联网地点推荐仍须经过来源校验，未核实则回退已审查目录。异常暴增时管理员查看次数与服务商账单，并停用异常账号或轮换密钥。
