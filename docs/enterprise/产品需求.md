# 产品需求：旅行助手作品项目

> 版本：v0.16｜日期：2026-10-21｜状态：用户已确认的目标范围；已实现进度见《当前进度》

## 1. 定位与边界

这是面向旅客的求职作品，按可落地项目标准建设。平台、航班报价、酒店/租车产品、订单和交易均为**模拟内容**；页面和 API 要清楚标记，不暗示与携程、真实航司或供应商合作。保留 FastAPI、LangGraph 主助手与业务专门助手、Python 分层及简洁易读的代码风格，可为正确性重构。交付 API 和简单操作页面，先在本机完整演示，再提供云服务器部署路径。

DeepSeek 是主要演示模型，GPT 和本地兼容模型是可选接入。模型密钥只在本机忽略的环境配置中提供。项目不接真实支付、出票、供应商库存或退款。

## 2. 已确认的能力

| 能力 | 旅客可见结果 | 写入边界 |
| --- | --- | --- |
| 基本对话 | 多轮问答、问候、澄清日期/地点/偏好、旅行话题交流；一般离题问题可简要回应 | 对话文本不能宣称未执行的交易成功 |
| 行程和政策查询 | 查看本人航班、酒店、租车订单；查询带规则 ID、版本和适用条件的虚构平台政策 | 只读无需确认；无依据时说明无法确定 |
| 航班 | 按日期、起终点等搜索；新预订、改签、取消模拟订单 | 每笔新增/改签/取消独立展示并确认 |
| 酒店 | 搜索并预订、取消；保留现有改期能力 | 每笔预订/改期/取消独立展示并确认 |
| 租车 | 搜索并预订、改期、取消模拟租车订单 | 每笔预订/改期/取消独立展示并确认 |
| 旅行推荐 | 仅推荐现有模拟航班可达城市的经典地点；结合已确认行程、酒店位置/日期和偏好，在对话中介绍理由，后台保留可核查来源与检索／审查时间 | 推荐只读，不建游览产品、场次或订单；不可达城市说明演示覆盖边界并建议可达替代城市 |

示范场景：“把明天下午的航班改签，并订一晚附近酒店。”助手应先查本人行程、政策与候选产品，澄清必要条件，分别生成航班改签与酒店预订确认卡。旅客可以分别确认或拒绝；每步执行结果和最新订单必须与数据库一致。其他端到端场景覆盖航班新预订/取消、酒店取消、租车预订/改期/取消及有来源的经典地点推荐。旅客要求预订景点时，助手说明本演示不支持游览预订，并提供有来源依据的地点建议；对话正文可只作介绍，不强制展示链接。

**P3.1e1 已确认的混合任务规则**：旅客说“预订前面说的机票，顺便找落地酒店”时，已明确且仍有效的机票可先生成一张待确认卡；酒店作为独立只读查询继续推进，缺入住／退房日期时只追问酒店部分。酒店产品和日期明确并再次提出预订后，才另建酒店卡。旧话题候选、冲突日期或已变化的报价不能自动作为本轮交易依据。

**P3.1e2a 最早班次与确认卡规则**：旅客要求“最早能出发”时，继承当前航班任务中明确的起终点及日期下界，或以当前时刻为下界；在演示基准日次日至第 30 日的可订窗口中，跨同城全部机场组合按实际起飞时刻全局比较直达班次，再显示当地日期、时间与模拟报价。未找到班次要说明搜索范围；同一最早时刻有多班则请旅客选择。明确要求“预订最早那班”且唯一时，仅生成待确认卡，订单仍须本人逐笔确认。对话中以新请求键重复提出完全相同的写操作，若本人同会话已有参数、目标、快照、金额、规则及产品版本均一致且未过期的卡，应沿用原卡；不同账号／会话或已过期、拒绝、版本变化的卡不得沿用。独立交易 API 仍允许并发提案，以检验确认时的冲突防护。

**P3.1e2b 住宿、价格和租车时刻规则**：“明天和后天都住”表示连续两晚，退房在大后天；明确的晚数决定退房日，若同一轮同时给出冲突的退房日期，先请旅客澄清。酒店最高／最低价按同地点、同入住区间的全部有效房型总价比较，租车先按同地点、同日期区间全部有效车辆的每日价比较；并列最高／最低时要求选定具体产品，不从仅展示的前三项推断全局排名。租车任务保留旅客明确说出的取还日期及当地钟点；仅有日期或“两天”时可提供 48 小时用车建议，但不得猜测具体还车时刻或生成订单卡。时刻完整后由产品机场时区规范化，按照实际经过时间向上计费，并在卡片显示当地时间、偏移、日数及总额。所有提案仍须旅客逐笔确认。

**P3.1e3a 地点与行程规则**：旅客明确说“我在某城市”时，只把该城市作为本会话的自述所在地，不宣称设备定位。查到可售航班后，目的地与实际到达机场／当地到达日由数据库候选确定；“我附近”在所在地与航班目的地都可能时先追问，不能继承其他业务的旧城市。落地酒店以旅客选定航班或本人唯一未来已确认航班为依据，展示机场及可核实的当地到达日；到达日入住只是建议，旅客确认入住日和住宿晚数后才查询房型。酒店有坐标时可给机场至虚构酒店的近似直线距离，不能冒充道路距离；经典地点只提供所在城市的有来源建议，没有坐标时不声称离旅客很近。“最近／接下来有什么行程”先列进行中或未来的已确认订单，已取消订单只作历史说明。地点补全及查询不会自行确认任何订单。

**P3.1e3b 答复组织规则**：有核实依据的只读查询可由模型选择候选列表版式和服务端预设的下一步提示，让答复更易读；航班、订单、日期、金额、政策和地点事实保留服务端证据文本。无证据或模型失联时使用确定性答复。模型不得把待确认卡说成已执行订单；卡片状态、确认步骤和查询并行结果由服务端组织。

**P3.1e3c 地点展示规则**：可达城市的地点推荐优先显示经过审查的中文名称，并附原名帮助旅客核对；结构化引用保留稳定地点 ID、原名、原来源和审查日期。旅客随后提及中文地点名或原名时，应回到同一个已核查地点和城市；同名跨城市要澄清。推荐主题由审查表决定，豫园按历史古典园林的文化主题说明，不能机械标成自然景观。名称来源只证明称呼与所指地点，不证明实时票价、营业时间或距离。

## 3. 模拟交易规则和确认协议

- 所有增加、修改、删除业务记录的操作都由智能体发起**提案**，由旅客查看具体结构化内容并逐笔确认；服务端在确认时执行确定性事务。取消是订单状态变更，不物理删除历史。
- 确认卡显示对象、变更前后、日期与当地时区、模拟金额/费用、规则来源、有效期和动作 ID。一次确认只执行一笔变更；拒绝、过期、失败、版本冲突或模型失联均不得写入。
- 机票改签只补新旧票价差额或退回差额，无额外改签费；取消费为原票价 30%，模拟应退 70%。租车在取车前可免费取消，取车后不允许取消。酒店取消仅能在产品机场当地入住日期前确认，手续费为 0、模拟应退原订单总额；入住日起不可取消。同日入住的预订和改期仍可进行，但须提示不可再取消。取消条件不从模型文字推断。
- 确认时复核登录身份、会话/订单归属、动作状态与有效期、价格、产品可用性、规则版本及订单版本；重复确认不得重复写入。模拟补退只作核算，不发生真实支付。
- 虚构平台政策是本系统模拟交易的唯一规则依据。原 FAQ 须去除真实航司品牌及与本规则冲突的表述；用户询问真实航司政策时，仅可提供有来源的外部信息，不能把它当作本平台的交易规则。
- 旧图的租车改期已按上述交易边界重建。旧图游览写工具只是修改共享推荐记录，不符合最终确认的产品范围；新图不接入这些工具，也不提供游览预订、修改或取消入口。
- 租车改期只调整本人已确认订单的取车、还车时间，车辆产品不变；必须在原取车时刻前确认，新时间仍须有效且可用。按新旧总价补差或模拟退差，不收额外改期费。

## 4. 数据范围与时间

原虚构 SQLite 只读。已盘点约 33,121 条航班、115 个机场和 **618 条不同起终点航线**，其中所有 618 条航线都有预定状态航班；源库另有历史/取消/延误记录。目标是提取全部航线和必要的非个人航班、机场字段，形成可交付且可重建的演示数据，不把两份约 114 MB 的原库作为启动依赖。旅客 ID、票号等原始订单标识不得直接外泄。

每次初始化/重置按统一时间差整体平移相关航班时间，保留时间间隔、状态先后和时区语义，使未来约 30 天有可预订班次；查询超出范围或无对应班次时如实说明。若迁移后的既有演示订单不再对应“明天下午”场景，重新设定匿名化种子订单，不能虚构航班。全部路线可查，用户未指定具体航班时按条件展示最多 3 个候选；明确要求最便宜时可按模拟报价排序，但仍须确认后下单。

航班候选报价、各可达城市的酒店与租车产品由可复现规则生成，明确标为模拟值，提供足够的价格、位置、时间与可用性变化供演示，不假扮真实供应商。经典地点推荐只覆盖当前模拟航班可达城市，不生成虚构游览产品或场次；可达城市集合由正式航班数据计算。推荐中的酒店“附近”用有坐标且来源可信的数据计算近似直线距离，明确不等于道路距离或通行时间；缺少坐标时不声称距离。

## 5. 旅行推荐与防幻觉要求

推荐真实地点时，取得可追溯来源、链接和检索／审查时间；优先景点/城市官方资料，再结合旅客行程组织建议。对话正文允许只介绍地点与依据，不强制直接给旅客链接；API 内部仍须保留来源以便核查。联网阶段使用阿里云 CleverSee 国际版 `GlobalBasic`；P2.7c 真实来源质量未通过验收，需先建立可信地点基线再考虑启用。无密钥、超时、额度耗尽或资料不足时说明证据不足，不编造地点细节、开放时间、票价、交通耗时或实时状态。搜索结果属于不可信外部内容，不能改变系统规则或触发写工具。对不可达城市，说明演示推荐范围，并从当前可达城市给出替代建议；不凭模型记忆补充无来源的景点事实。

**2026-10-20 联调方向调整**：用户要求联网搜索在真实助手体验中默认开启。P3.1c 将有密钥时的代码缺省行为改为开启；本机 `.env` 可显式设置 `ALIYUN_IQS_ENABLED=false` 暂停检索。实时搜索仍只补充人工核查地点目录的候选／新鲜度判断，不把未经核实的搜索结果直接写入旅客事实或订单。具体联调结果见《当前进度》，主线发布仍需 G-16 单独确认。

**P3.1d 对话与天气补充**：中文城市和机场别名、今天至大后天及明确日期应在服务端规范化；连续补充条件须保留已明确的起终点或入住城市，新话题应切换任务。航班查询覆盖同城多个机场，空结果应说明日期、航线或供给边界；已取消订单不得回答成待出发行程。“我在上海，想去其他国家”中的上海是出发地。旅客询问未来七天内中国可达城市的天气时，可用已配置的阿里云 `GlobalBasic` 搜索公开城市和日期，但只在重新读取的国家气象中心页面能核对城市、目标日和发布时间时给出预报；结构化引用保留来源，无法核实时明确说明。联网天气不代表机酒库存或交易规则来自互联网。

订单、班次、价格、可用性只能来自数据库与确定性服务；模型只负责理解、澄清、选择工具与组织回答。政策回答给出具体规则 ID/版本；旅行事实有可核查来源。对“有航班但无房”“过期报价”“不存在的班次”“跨账号订单”“模型声称已预订却无确认”等情况必须拒绝编造或误操作。

## 6. 页面、质量和验收

页面包括演示账号登录、对话、本人航班/酒店/租车行程与订单、对应候选产品、逐笔确认卡、操作结果与历史。经典地点推荐在对话中展示，来源在 API 中可核查；页面可只给地点介绍，不设游览产品浏览页。明确区分“建议”“待确认”“已执行”“失败”和模拟数据。API 有相同的结构化契约。

**旅客展示约定（P3.1a）**：页面以中文城市、机场、房型和车辆类型为主，航班号、机场代码及订单／产品／规则 ID 在次级详情中保留，便于逐笔核对。查询表单可按中文地点选择，服务端交易继续使用原始代码。示例报价按人民币样式展示（如 `¥4,258`），不改变存储数值、报价算法或交易规则，不代表真实市场报价或外币换算。登录页、工作台和确认前清楚说明作品体验环境、示例数据以及不会产生真实预订、付款或退款；避免在每条内容中重复堆砌“演示／模拟”，但 API 的模拟声明和规则依据仍需保留。

验收至少证明：两个账号隔离；所有航班/酒店/租车写操作在确认前订单不变；拒绝、重复确认、过期和并发不重复写入；会话与图状态跨服务重启恢复；完整演示对话可完成改签加酒店两张独立卡，以及新增航班、租车改期、虚构政策问答和有来源的可达城市推荐；不可达城市、无来源、网络搜索失败和模型错误不产生幻觉性事实或写入。测试既包含固定模型输出的确定性场景，也包含配置好密钥后的少量 DeepSeek 实测。记录任务完成、错误、延迟及模型/检索调用成本基线，不预先承诺生产 SLA。

## 7. 分阶段交付与未决细节

已完成阶段的实际情况见《当前进度》。租车改期已进入本机主线，原游览交易路线已撤销。后续按独立事前计划推进：先接入受控多轮对话、虚构政策查询和现有九类航班/酒店/租车交易提案，再用有效 DeepSeek 密钥做真实联调；随后实现有来源的可达城市推荐，最后完成页面、评估和部署说明。每一步须先出详细计划、经用户确认再实施，结果同步《当前进度》。

尚待实施时确定而不阻碍当前方向的细节：虚构平台名称和页面风格、推荐检索 API 的后续替换选择、云服务器供应商/预算、本地模型的实际工具调用能力。新的有效 DeepSeek 密钥只在真实联调前由用户配置到 Git 忽略的本机环境文件，不在聊天中发送。任何新增交易规则须先写入版本化政策，再纳入交易计算与测试。
