# 产品需求：旅行助手作品项目

> 版本：v0.2｜日期：2026-10-17｜状态：需求基线，P0 实施中

## 1. 项目定位

这是面向旅客的求职作品，使用**虚构旅行平台、虚构旅客和模拟交易数据**。目标是做出能在本机完整演示、以后可部署到云服务器的旅行助手；以企业项目的方式处理身份隔离、交易确认、持久化、测试和可观测性。页面及文档须清楚标注“模拟数据／演示交易”，不得暗示与携程、航空公司或酒店有真实合作。

项目保留原有的 FastAPI 接口、LangGraph 主助手与业务专门助手、工具调用和 Python 分层习惯。允许为正确性重构，但代码应简洁、清楚，不为了展示技术而引入额外服务。

### 已确认的用户决策

- 目标是求职作品，按可落地的企业项目标准设计；第一阶段只面向旅客。
- 需要 API 和简单操作页面；优先本机运行，保留云服务器部署路径。
- 智能体执行查询，并提出增加、修改、取消业务记录的动作；**每一笔写操作都须先向当前旅客展示内容并获得确认**。
- 没有可用的真实业务数据库或供应商接口；数据量小可以接受。可使用 DeepSeek、GPT 模型 API，并希望试接本地模型。
- 可以较大幅度重构，但保持原旅行助手的框架和易读的代码风格。

## 2. 第一阶段范围

| 优先级 | 能力 | 旅客看到的结果 |
| --- | --- | --- |
| P1 | 我的行程和规则查询 | 登录后查看自己的航班、酒店订单；查询航班退改规则，答复标明所用的模拟规则来源 |
| P1 | 航班改签与取消 | 助手搜索可选航班，提出改签或取消方案；确认后改变旅客自己的模拟机票订单 |
| P1 | 酒店查询与预订管理 | 助手搜索酒店，提出预订、改期或取消方案；确认后改变旅客自己的模拟酒店订单 |

贯穿场景：旅客说“把明天下午的航班改签，并订一晚附近酒店”。助手先查当前行程、规则、可选航班与酒店；缺少日期、目的地或酒店偏好时询问；依次生成**航班改签**和**酒店预订**两张独立确认卡。旅客逐项确认，页面显示每一步执行结果、最新订单和审计记录。前一步失败时不得宣称后一步已经成功。

### 第一阶段不包含

- 真实出票、支付、库存锁定、真实退款或真实供应商交易。
- 租车、景点交易的新功能开发；现有专门助手结构保留，后续按同一交易接口接入。
- 企业多租户、客服工作台、完整后台管理、移动 App。
- 对真实携程或航司政策的承诺。规则文档全部为演示政策，版本和生效范围清晰可见。

## 3. 关键用户流程与验收

| 编号 | 需求 | 验收方式 |
| --- | --- | --- |
| F-01 | 旅客登录及会话 | 至少两个演示账号；登录后只能读取自己的行程、会话和待确认动作；越权请求返回拒绝 |
| F-02 | 行程查询 | 助手能列出当前旅客的航班和酒店订单；订单状态、日期、地点来自数据库，不靠模型编造 |
| F-03 | 规则问答 | 回答退改问题时给出模拟规则名称或段落；缺少依据时明确表示不能确定 |
| F-04 | 航班搜索与改签 | 按出发地、目的地、日期查询候选航班；方案展示旧／新航班、时间和模拟费用；确认后订单变更 |
| F-05 | 航班取消 | 方案展示机票、取消结果和模拟规则；确认后将订单标为已取消，历史记录保留 |
| F-06 | 酒店搜索和预订 | 方案展示酒店、入住／离店日期、房型或可用产品、模拟价格；确认后创建旅客酒店订单 |
| F-07 | 酒店改期与取消 | 修改旅客自己的酒店订单；取消改变订单状态，不直接删除历史订单 |
| F-08 | 逐笔写入确认 | 每笔增加、修改、取消均显示操作对象、变更前后内容、影响及有效期；拒绝、超时、取消均不写入 |
| F-09 | 执行结果 | 旅客能看到成功、失败或待确认状态；重复点击确认不会重复创建／重复修改订单 |
| F-10 | 会话恢复 | 页面刷新和服务重启后，旅客仍能看到自己的会话与未过期待确认动作 |
| F-11 | 模型切换 | 配置选择 DeepSeek、GPT 或符合接口契约的本地模型；不支持可靠工具调用的模型显示能力不足，不进入写操作流程 |

### 确认规则

1. 只读查询无需确认。模型只能**提出**写操作，不能绕过确认直接调用数据库写入。
2. 一个确认动作只对应一个订单变更；多笔动作必须逐笔确认。确认卡展示系统生成的结构化参数，不能仅显示模型的自然语言描述。
3. 确认时重新核对登录身份、订单归属、动作有效期、目标资源及订单版本；执行成功后动作一次性失效。
4. 用户拒绝或修改要求时，旧动作失效，助手重新提出方案。取消属于业务状态变更；数据库物理删除不向智能体开放。
5. 若模拟价格、规则或可用性发生变化，应生成新方案重新确认。任何费用都标明为模拟值。

## 4. 演示数据与页面

用户确认原有 SQLite 是虚构数据。第一阶段**从现有大库按关联关系精选并匿名化**航班、机票与酒店，附带一份可随项目交付的小型样本；不足的旅客订单状态和演示规则再补齐。规模以覆盖场景为准，**无需追求大量记录**。最低包含：两个互不重叠的旅客、各自的行程；同一目的地的多条候选航班；可预订、不可预订和已取消的订单；数家不同位置和价格的酒店；至少两条带版本的模拟退改规则。导入时把日期相对演示当天平移，保证“明天”等场景可用。允许一键重置演示环境；两份 114 MB 左右的原 SQLite 保持只读，不作为新环境启动的必需文件。

简单操作页面包含登录、对话、我的行程／订单、待确认卡和操作历史。页面要明显区分“助手建议”“等待确认”“已执行”“执行失败”；可选展示当前模型名称和一次演示的步骤轨迹。

## 5. 质量与交付验收

- **安全**：跨账号读取和写入在自动化测试中全部被拒绝；无确认写入为零；密钥不进入源码、日志和演示数据。
- **正确性**：航班改签、取消及酒店预订、改期、取消五类写流程均有成功、拒绝、重复确认和过期场景测试；可核对数据库最终状态。
- **可靠性**：待确认动作在服务重启后可恢复；失败可重试且不重复写入；模型超时不会改变订单。
- **可演示**：按 README 在本机启动 API、页面和数据库；可重置数据并连续完成固定演示脚本。云服务器部署作为下一阶段的可执行说明和验证目标。
- **可观察**：每笔确认与写入有动作 ID、旅客 ID、前后状态、结果和时间；日志不记录令牌、密钥或完整敏感信息。
- **可维护**：依赖可复现、数据迁移可执行、核心业务自动化测试通过，接口和主要架构决策有文档。

首版不承诺生产 SLA 或真实高并发数值。待模型、服务器和演示脚本固定后记录端到端耗时、错误率和模型成本基线，再确定量化门槛。

## 6. 推荐实施阶段

1. **基础可运行**：整理依赖和配置、移除源码凭证、建立小型演示数据与本机启动方式。
2. **业务与身份**：统一旅客与订单模型，完成服务端身份绑定、订单归属检查和规则数据。
3. **智能体闭环**：保留主助手／专门助手，加入结构化待确认动作、逐笔审批、幂等写入、持久化会话。
4. **页面与交付**：完成简单页面、关键场景测试、日志／审计、演示脚本和云端部署说明。

个人项目建议以 4～6 周为**规划参考**，不是承诺截止日期；每阶段以验收结果推进。任何实现工作都遵循《当前进度》中的开工确认流程。

## 7. 待验证假设

- 平台使用新的虚构名称和标识；具体名称可在制作页面前确定。
- 第一阶段只提供预置演示账号，不开放公众自行注册；旅客可查看自己的资料。
- 演示数据以用户确认的虚构 SQLite 为来源，但交付的小型样本将旅客 ID 和机票号匿名化；若将来引入真实数据，须另行核验来源和处理方式。
- 本地模型通过兼容接口接入；是否能参与工具调用由实测决定，不能仅因接口可连通就标为可用。
