# P3.1e5：航班时长与到达日质量修复操作计划

> 2026-10-21｜事前计划，等待用户确认；承接 P3.1e4 的发布阻断项。本计划本身不授权重置正式演示库、合并本机 `main` 或推送 GitHub。

## 1. 为什么需要这一步

P3.1e4 在真实页面确认机票时发现上海至伦敦航班的统一时区飞行时间仅约 2.17 小时，且当地到达日早于当地出发日。对隔离库 15,383 条带坐标的计划航班核查后，距离至少 5,000 公里的 10,594 条中有 10,049 条时长不足 5 小时。酒店“落地当天入住”依赖到达日，因此仅修复文字呈现不能解决行程错误。原航线和时间数据是虚构样本，不应把它包装成真实航司时刻表。

## 2. 拟定规则及用户需要判断的取舍

建议保留机场、航线、起飞时间、航班号和模拟报价，重新计算**计划到达时间**，并把时长规则清楚标为虚构排程。先从机场坐标计算大圆距离，以保守的地面准备时间、巡航速度和可解释的上下限产生确定性时长；跨洲距离不能得出几小时内到达的结果。同一来源、同一演示日期重复导入应产生一致的到达时间。新规则只用于展示和交易演示，不声称真实飞行时长、转机安排或运营可靠性。按目的地机场时区换算当地到达日，再由该日推导落地酒店建议。

两种处理已存在订单的方案需要在执行前确定：

1. **建议方案：隔离库验证后，经用户另行确认再备份并显式重建正式演示库。**旧演示订单、会话和待确认卡作为备份保留；正式库重新生成两名示例旅客的基础订单。优点是数据完全一致，代价是本机现有测试会话和动作卡会被清空。
2. 保留正式库原有订单，仅对新导入航班更新到达时间。这样需要迁移旧订单快照、已发卡片和会话内落地上下文，容易出现新旧到达日并存；不建议作为作品演示基线。

本阶段先做隔离库和代码验证，不会自动执行正式库重建。需要正式库更新时，另列备份位置、受影响记录和具体命令供用户判断。

## 3. 实施顺序

1. 重读《产品需求》《软件架构》《当前进度》及本计划，核对分支、未提交文件、默认库与隔离库状态。只读抽样检查源 SQLite、导入后 UTC 时间、机场时区和距离，确认问题来自源排程，避免将时区换算问题掩盖为时长问题。
2. 在独立纯函数中实现确定性虚构飞行时长，明确距离缺失、极短航段、跨洲航段、夏令时切换和到达时间不得早于起飞的处理。给出易读的规则说明及版本号；不要由模型或实时搜索决定航班时刻。
3. 使完整航线导入在转换阶段校正计划到达时间，必要时同步校正实际到达时间的一致性；原始样本文件保持不变。报价、可售日期窗、航班 ID 和出发时间保持稳定。先在全新隔离库备份并导入，核对航线、报价和长期航段时长分布。
4. 对跨洲、短途、日期跨越、夏令时和重复导入加有区分力的测试。重放 P3.1e4 上海至伦敦订票加落地酒店路径，逐项核对到达当地日期、酒店入住建议、两晚总价和确认卡；三类交易确认、重启恢复、权限和过期规则不得退化。
5. 运行全套自动化、Python 编译、页面脚本语法、依赖及差异检查；在窄屏和桌面页面分别核对跨洲航班与落地酒店。若真实 DeepSeek 的对话规则未变，优先使用固定模型回放；只有模型对新日期产生歧义时才做少量付费联调并逐次记录。
6. 将新旧数据差异、风险、备份和通过／失败结果写入《当前进度》及独立验收记录。先在功能分支提交。只有发布阻断项和桌面页面验收都通过，才重新制定 G-16 主线合并与 GitHub 同步计划，并单独征得用户确认。

## 4. 停止条件

若新时长规则导致出发时间或航班 ID 变化、订单/卡片指向错误航班、报价不一致、正式库发生未授权写入，立即停止并保留隔离备份。若大圆距离无法合理表示某条路线，需明确排除或另订规则，不能默默产出不可信到达日。
