# P3.1e2b：住宿夜数、价格选择与租车时刻操作计划

> 编写日期：2026-10-21｜状态：用户已确认并在功能分支实施。承接已验收的 P3.1e2a，处理缺陷 D08～D10；不包含正式库重置、主线合并或 GitHub 推送。结果见《当前进度》。

## 1. 本步目标与当前依据

旅客原话中，“明天和后天都要住”“最贵的酒店，住两晚”没有变成正确的退房日和订单卡；“贵的那个车，两天，明天和后天都要用”重新返回酒店列表。目标是在同一会话内理解这三类连续补充，并在信息充分时给出**目标、日期、时间、金额都可核对的待确认卡**，仍须旅客逐笔确认后才改订单。

开工前已重读《产品需求》《软件架构》《当前进度》和 P3.1e 缺陷路线。当前 `find_hotels`、`find_rentals` 先按单价升序取前三项；候选选择只支持“最便宜”，不支持“最贵”；酒店 `check_out` 可从已展示的旧候选继承；租车交易要求带时区的 `pickup_at`／`dropoff_at`，对话只有日期任务上下文。现有服务已按实际 UTC 使用时长向上取整计算租车计费日数，并在确认时重算。本步沿用这些确定性规则，不增加新产品数据、支付或供应商接口。

## 2. 建议的旅客语义，供确认

| 旅客表达 | 建议执行规则 | 需要澄清的情况 |
| --- | --- | --- |
| “10 月 22 日入住，住两晚” | 10 月 24 日退房，入住 22、23 日两晚；展示每晚单价、夜数和总额 | 没有入住日期时先问入住日；“住两晚”覆盖旧的一晚退房日 |
| “明天和后天都要住” | 把明天和后天理解为两晚住宿，退房在大后天；不把后天当作退房日 | 若旅客同时明确了矛盾的退房日期，指出冲突并请其选择 |
| “最贵／最便宜的酒店” | 在**明确城市或机场、完整入住区间**内，对全部有效房型按该次住宿总额排序；同夜数下等价于每晚单价排序。只展示少量候选，但选择依据是全量有效结果 | 并列最高／最低价时列出并列房型，请旅客选定；城市或日期不明时只追问缺项 |
| “最贵／最便宜的车” | 在**明确取车城市或机场、取还日期**内先比较全部有效产品的每日价并说明这是每日价排名；具体取还时刻确定后按当前计费规则重算总额和可用性 | 最高／最低日价并列时请选车辆；未给时刻时可展示车辆但不能生成预订卡 |
| “明天用大后天还” | 保存取车、还车当地日期，定向追问两端当地时刻；不自行假设 00:00、酒店退房时刻或机场落地时刻 | 明确时刻若跨时区夏令时缺失或重复，按现有时区校验要求修正或补 UTC 偏移 |
| “两天租车，明天 10 点取” | 建议“两天”指连续 48 小时，推算大后天当地约 10 点还；回答中明确拟采用的还车时刻，并在建卡前让旅客明确同意该时刻 | 只说“两天、明天和后天都用”但无取车钟点时，问取车和还车当地时刻；不能擅自建卡 |

两晚和两天分别按住宿夜数与租车实际计费时长处理，避免混同。租车现行规则为实际 UTC 时长除以 24 小时向上取整；跨夏令时的当地“同一钟点”可能不是 48 小时，因此卡片必须显示当地时间、UTC 偏移、计费日数和总额。若最后一项推算时间的交互过于繁琐，实施时可以仅提出建议并要求旅客补齐还车时间；不得用模型猜测的钟点写卡。

## 3. 分层实施步骤

### A. 开工与可复现基线

1. 用户确认后重读三份核心文档及本计划，核对 `feature/p31-traveler-ui`、提交、工作区、当前服务和正式库状态。正式演示订单只做只读核查，不重置数据。
2. 在隔离数据库构造同城至少四个有效房型／车辆、价格并列、产品日期范围不同、住宿一晚与两晚、租车跨当地日和跨夏令时样本。用用户原话回放，记录现有选错产品、旧退房日延续、租车只问日期等失败结果；只保存脱敏结构化结果。

### B. 住宿夜数与确认卡

1. 在服务端解析“住 N 晚”“明天和后天都住”等明确表达，限定合理夜数范围；把入住日加夜数得到退房日。用户本轮明确夜数优先于同任务旧退房日，冲突的本轮日期不能静默覆盖。
2. 更新酒店任务上下文和只读查询：继承已明确城市／入住日，重新查询新日期范围、重算可用房型；答复显示入住、退房、夜数、每晚价和总额。新日期与旧候选不一致时清除旧候选。
3. 酒店预订／改期仍通过受控 `prepare_actions`、重新报价、`create_proposal` 和确认 API；不允许模型提供未经旅客表达支撑的退房日期。卡片明确夜数和总金额，同日入住不可取消的原规则继续提示。

### C. 全量有效产品的价格选择

1. 为酒店和租车的查询服务增加服务端降序排序或等价的全量最高／最低选择，先按地点与完整日期过滤，再排序，最后限制展示数量；保留旧升序与距离查询 API 兼容性。设置稳定次序只用于展示，并列第一不得静默选 ID。
2. 对话识别“最贵／贵的那个／最便宜／便宜的那个”，只从当前业务类型、地点和日期的查询结果选择；必要时扩展只读 API 的 `sort` 枚举并同步页面排序说明。其他任务的候选、前三项中的局部最贵、旧报价及模型填入的产品 ID 都不能决定全局排名。
3. 生成卡前再次核对产品价格、可售日期、旅客身份和会话范围。价格或条件变化时重新查询并告知，不沿用旧排序或旧卡。

### D. 租车时刻与两天语义

1. 在租车任务上下文保留取还车当地日期、用户明确给出的钟点及地点。缺钟点时只问缺的那一端；新租车话题不得继承酒店日期或地点。
2. 对“明天 10 点取、大后天 10 点还”等明确表达形成候选时间，按产品所属机场的 IANA 时区转换为规范化时间；跨夏令时缺失／重复的时刻走现有服务校验，重复时刻要求偏移。不能用服务器时区或模型猜测时区。
3. “租两天”可提供 48 小时后的建议还车时刻，但未获旅客明确接受前不形成提案；一旦接受，按实际时长和现有向上取整规则展示计费日数、每日价与总额。租车改期保留原车辆、原取车前截止及补退差价规则。

## 4. 验收与停止条件

1. 连续对话回放原场景：上海酒店查询 → “明天和后天都住” → “订最贵的，住两晚”；上海租车查询 → “贵的那个车，两天，明天和后天都用” → 补齐当地时刻 → 待确认卡。每张卡的产品、日期、时间和金额应与隔离库一致，未确认前订单数不变。
2. 检验第四个及更后面的产品可能最贵、并列最贵／最便宜、旧候选与新日期冲突、跨城市或业务切换、价格变动、无货、超出演示日期窗、两账号与两会话隔离、重复请求键与有效卡复用。
3. 对租车覆盖“只给日期”“两天但无钟点”“先说钟点后说日期”“当地时间不存在／重复”“跨夏令时实际时长”“取车已过”“退车早于取车”，核对报价与确认时重算一致。任何自动补全未经旅客确认的时刻、错产品卡或未确认订单写入，立即停止。
4. 运行全套自动化测试、编译、依赖检查、文档链接和 Git 差异检查。隔离库用少量真实 DeepSeek 回放关键多轮样本，建议本步最多 **20 次模型调用**；记录可得 token 用量，账单以提供方为准。阿里云检索与本步酒店／租车库存无关，不调用。
