# P3.1g1：国家目的地与跨任务订票操作计划

> 制定日期：2026-10-22｜状态：用户已确认并执行 P3.1g1；结果详见《当前进度》。本文件只覆盖第一小步，不授权 P3.1g2～g4、正式数据库写入、主线合并或 GitHub 推送。

## 1. 本步解决什么

修复“我在伦敦 → 去中国 → 订最早机票”无法前进及重复索要出发地。航班必须是当前演示库真实可售的虚构班次；缺目的地城市时先让旅客选，不把国家名当城市、不给无根据的航班，也不因旅客说“订”就确认订单。保留现有单城最早班次、同城多机场、报价复核、逐笔待确认卡和旧候选失效规则。

## 2. 开工核对与隔离

1. 重读《产品需求》《软件架构》《当前进度》、总计划、本计划及公开发布规则；确认功能分支和工作区状态、当前代码哈希，检查 Git 忽略目录和密钥文件不会进入提交。
2. 只读核对 8000 服务：若可达，记录页面静态资源版本、进程标识和启动时刻；若不可达，仅记事实。现有接口未暴露可信提交哈希，不能仅凭页面外观断言 8000 曾运行哪个提交。绝不停止或重启用户调试进程。
3. 使用隔离内存数据库构造可售和无售两种线路；如需实库和真实页面，再另启独立 PostgreSQL 项目及 API 端口，不沿用正式 5433／8000。先记录账号、订单、动作和审计计数；不使用真实模型或联网搜索，本步付费调用预算为 0。

## 3. 实施顺序

1. 以用户原话建立逐轮失败回归：“我在伦敦”“我打算去中国，给我订最近的机票”“我现在在哪里”“从伦敦到中国，给我订最早的机票”“选第一个城市”。记录每轮的所在地来源、出发地、国家目标、日期下界、订票意图、可售城市、候选、卡片及订单。
2. 在航班任务状态中明确区分 `arrival_city` 与 `arrival_country`。只从用户当轮文字或本会话带来源的自述城市补出发地；旅客改口或选新国家时清除冲突的目的地、日期和候选。新会话不继承当前位置。“最早／尽快／最近能出发”按时间下界寻找可售班次；“明天”按出发机场当地日历计算，不能沿用中国时区导致跨日错误。模型可辅助识别表达，服务端负责国家、城市、机场与路线的确定性校验。
3. 从当前出发城市的全部机场出发，在可订 30 天窗口内筛选有效报价、可售、未起飞的直达航班，再按受控机场地理资料筛到目标国家。同一目的地城市合并机场组合，按 UTC 起飞时刻确定各城最早班次，最多显示 5 座城市的中文名称、当地出发时间和参考报价；说明搜索范围及仅含模拟直达航班。若无结果，明确没有查到，而不借其他城市的推荐目录补答案。大量记录按有界查询处理，不截前几条冒充全局最早。
4. 城市选择可用中文城市名或当前列表序号，必须绑定本人同会话、本任务和列表有效期。选定城市后服务端重新查询该路线，核对旅客原先的日期下界与“预订最早”意图；只有唯一最早班次才可生成一张待确认卡。并列最早时请旅客选具体班次；列表过期、改价、路线改口时要求重查。确认前订单不变。
5. 澄清文案具体说明“已记下你自述在伦敦；中国包含多个城市，请先选择当前有可售直达航班的目的地”，避免重复说“还缺出发地、目的地”。目的地或出发地确实不可核实时指出具体缺项。一般只读国家推荐仍保持原边界，不被误分流成订票交易。

## 4. 验收矩阵

| 场景 | 必须满足 |
| --- | --- |
| 同会话伦敦→中国，要求最早并预订 | 不再要求重复提供伦敦；列实际可售的中国城市及各自最早班次；选城市后在唯一最早条件下出正确待确认卡 |
| 仅说“去中国”但没有可信出发地 | 只追问出发城市，不猜旅客当前位置 |
| 伦敦出发窗口内无中国直达可售班次 | 说明当前窗口及直达覆盖限制，不编造城市、班次或卡片 |
| 多机场、多城市、同刻并列、当地“明天”及上限 | 按出发机场当地日历确定日期、按绝对起飞时刻全局排序；同城合并；并列不自动选班；结果上限不得改变最早结论 |
| 更改所在地、目的地国家、日期或跨会话 | 清除不再适用的任务条件和候选；旧候选不能生成新卡 |
| 报价变化、过期、跨账号及重复请求 | 重新核实或拒绝；无越权；相同有效目标复用卡，确认前无订单增量 |

固定模型逐轮回放和新增针对性回归全部通过后，运行完整现有测试、Python 编译、依赖及差异检查。核对每一张新卡的目标航班、当地时间、金额、规则和对应审计。任何错城市、错班次、未经确认写单或跨账号信息泄露均停止实施并保留脱敏证据。
