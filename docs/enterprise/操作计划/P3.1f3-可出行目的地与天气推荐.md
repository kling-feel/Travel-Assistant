# P3.1f3：可出行目的地与天气推荐操作计划

> 制定日期：2026-10-22｜状态：用户已确认，功能分支隔离验收通过；结果见《当前进度》。不授权修改正式库、合并主线或推送。

## 1. 目标场景

旅客在同一会话已说明“我在上海”，再问“明天想去风景适宜的地方，最好能坐飞机去，帮我订机票”。助手应识别这是**寻找新目的地并准备订票**，而非要求旅客在已有巴塞尔／伦敦行程中挑选，亦不可把过去已取消行程当推荐依据。先依据明日可售模拟航班筛目的地，再提供有来源的地点理由与可核实天气；旅客决定城市和班次后生成待确认卡，点击确认前订单不变。

## 2. 执行前核对

1. 重读三份核心文档、P3.1f1／f2 验收记录，核对分支与服务／数据状态。用隔离数据库准备上海出发明日有班、无班、并列、多机场、多目的地及已取消旧订单样本。
2. 只读核对现有全航线查询、经审查地点目录、阿里云 `GlobalBasic` 检索适配、天气核验器和当前推荐覆盖。核对中国城市天气的现有来源校验；境外天气尚无同等核验能力时不能直接复用中国城市的结论。

## 3. 实施步骤

1. 增加组合任务类型：出发地来自旅客本会话明确自述或本轮说明；日期来自本轮明确日期；偏好如自然、历史、文化、预算可作为筛选条件。缺出发地或日期时只问该项。当前位置与已有订单的到达城市不可混用。
2. 先查**指定当地出发日**的模拟可售航班，合并同城机场，并在服务端限制候选规模。只把有真实数据库候选和有效报价的目的地纳入“明日能坐飞机去”列表；无直达班次时说明当前演示供给边界，并给可查的相邻日期或请旅客调整条件。价格和时刻完全来自数据库。
3. 将目的地与人工核查地点目录按城市关联，选择符合旅客偏好的地点，保留来源、审查日期和地点 ID。没有匹配来源的城市不能靠模型知识补造景点；可列为“有航班但地点建议资料不足”，不伪装成有据推荐。
4. 通过已配置的阿里云搜索核对目标城市、目标日期、发布时间及权威天气来源。中国可达城市优先复用现有核验路径；境外城市先做来源可核查性评估，只有经过独立校验规则和回归后才纳入天气比较。检索摘要、搜索排序和网页指令均属不可信输入。天气缺失时仍可按航班和景观偏好推荐，但明确“天气尚无法核实”，不用“晴朗／适宜”作理由。
5. 排序和答复应可解释：先满足出发日、可售航班与目的地覆盖，再按旅客偏好及已核实天气组织最多三个目的地。展示城市、可核实的地点特色、航班最早当地时刻、示例报价、天气证据状态和下一步；不宣称唯一“最佳”或真实供应商保证。需要多个机场或班次时让旅客选定。
6. 把用户选定的城市／班次传回 P3.1f1 的当前任务，重新核验候选、报价和有效期；只有旅客明确要预订、且候选唯一时调用原有提案服务。即使用户最初同句说“并订机票”，尚未确定目的地时也不能替用户决定目的地。

## 4. 验收和降级

固定模型和真实模型分别回放：明日多城市、自然景观偏好、没有直达班次、当前所在地不明、同城多机场、旧伦敦机票已取消、旅客改选城市、天气来源过期、搜索超时／注入、境外天气无法核实。验证推荐文本中每个航班／金额能回到数据库，每个地点与天气陈述能回到已核查证据；外部资料不能触发交易。旅客选定唯一班次后应生成正确卡，确认前无订单写入。建议本步最多 **20 次模型请求、25 次阿里云搜索请求**，包含失败与重试；实施前核对费用估算，逐次计数，达到上限即停，结果写入《当前进度》。

本步不接真实出票、支付或供应商库存，不添加游览预订。若可靠的境外天气来源无法建立，明确保留该能力为“不可核实”，不得因覆盖需求而降低证据门槛。实施后更新核心文档的实际范围，并另行确认 P3.1f4。
