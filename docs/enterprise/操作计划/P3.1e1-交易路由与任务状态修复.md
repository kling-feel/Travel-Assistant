# P3.1e1：交易路由与任务状态修复操作计划

> 编写日期：2026-10-21｜状态：用户已确认执行，实施结果见《当前进度》。用户已确认“机票条件齐备先给待确认卡，酒店查询独立推进”的产品行为。本计划不包含主线合并、GitHub 推送或演示库重置。

## 1. 目标与本步边界

先解决 [P3.1e 缺陷清单](P3.1e-真实对话缺陷清单与修复路线.md) 的 D01～D05、D15、D03 的任务切换和 D07 的基本混合任务：明确预订不再降级为只读查询；“预订这个航班”只能绑定本会话当前有效候选；酒店话题不能截获新租车任务。旅客说“订这班机票，顺便找落地酒店”时，若航班已明确且仍可提案，应给**一张机票待确认卡**，并对酒店执行只读搜索或定向追问；酒店房型和晚数未定时不生成酒店卡，也不阻断机票卡。两项结果在同一轮清楚分开，未确认订单不变。

这一小步不处理跨日期“最早”搜索、最贵产品、两晚日期语义、租车具体取还时刻或景点中文名；这些继续按 P3.1e 第 2、3 步分别计划。已选定的 `SIM-3831`／10 月 25 日等明确候选可用于本步验收，不把尚未实现的“最早”解析伪装成已完成。两个**写入请求**同轮的现有原子提案规则先保持，后续如需改变再单独商定。

3. 先检查模型路由实际输入与输出。当前源代码允许模型给出 `general`、`transaction` 等 JSON，但只读捷径和后续守卫可能覆盖。若固定模型与真实服务表现不一致，优先查请求文本、缓存轮次、运行进程版本和图检查点，而非靠添加更多提示词掩盖。

## 3. 具体代码操作

### A. 交易意图与任务切换

1. 在 `graph_chat/controlled.py` 和 `services/dialogue_context.py` 使用同一组受控交易表达识别“预订／预定／订机票／订房／下单”等，避免把“订单查询”误判为下单。明确交易意图在只读捷径之前得到保护；模型不能把用户明确的预订静默改成查询，也不能凭旧上下文把纯查询变成预订。
2. 将新任务的业务类型优先于旧只读上下文：租车、航班、酒店、天气、推荐分别有明确切换规则。只有“后天”“就这家”等真正承接上轮的话才继承该业务条件。后续针对租车时间的完整补全放在第 2 步，本步先保证不会再回答酒店列表。
3. 路由和回复应区分“想查询候选”“已选择候选、要求预订”“只表达意愿但缺对象”。缺产品时说出已掌握的出发地、目的地或日期以及唯一缺项，不再给与本轮不符的通用提示。

### B. 候选、日期与会话边界

1. 在服务端会话图状态保存按业务类型分开的任务条件与候选摘要，包括产品 ID、地点、当地日期、报价／产品版本和引用来源；兼容已有检查点的旧状态。切换话题时旧候选不会被自动当成本轮目标；旅客明确说“前面那班机票”可重新激活并复核，无唯一匹配则追问。
2. 调整 `services/agent_proposals.py` 的选择依据：`这个／前面那个／第一班／航班号` 仅在当前任务有唯一、仍有效的已展示候选时成立。不能只因为最近四轮某类型仅剩一个候选就静默选中不同日期或航线。提案前从数据库重查班次、报价版本和旅客归属；无法重查则不给卡。
3. 酒店／租车日期只能来自该任务中用户明确给出的条件或已明确选择的候选，不再仅因整段聊天历史出现过相同日期就视为授权。冲突、过期或已改题时清除错误条件并定向追问。确认接口的身份、价格、规则、版本及幂等复核保持原有强度。

### C. “机票预订＋找酒店”的混合结果

1. 受控图允许一轮内表示一笔明确的 `flight_book` 提案与一项 `hotel_search` 只读需求；酒店查询地点优先依据用户明确说的落地城市或已选航班的到达机场，不能从模型记忆猜目的地。
2. API 在成功创建机票卡后保留酒店的只读结果或缺项提示，答复明确分段：“机票待确认（尚未下单）”“酒店查询（仍需入住／退房条件或已有候选）”。酒店条件不足不撤销已正确生成的机票卡；如果机票目标本身不明确，则不建机票卡，酒店仍可给只读结果。
3. 仅当酒店产品、日期和旅客预订意图都明确时，之后才可单独生成酒店预订卡；这一步不自动选择酒店、不把找到房型说成已预订。两笔都明确要求写入的请求仍按既有逐笔卡和原子提案边界处理。

## 4. 验收

1. 固定模型和 API 连续回放：查询 10 月 25 日上海→伦敦 `SIM-3831`，说“我要预定这班机票”或“我要预订这个航班”，均只生成目标为该班次的机票待确认卡；改为别的日期／航线后，旧候选不可悄悄沿用。`request_key` 重放不多建卡。
2. “预订前面说的机票，顺便找伦敦落地机场附近酒店”在机票候选唯一时得到一张机票卡和酒店的针对性只读结果／追问。缺酒店晚数不能阻断机票卡；缺机票候选不得为了满足任务而编造班次。
3. 酒店后说“我要在上海租车，明天用大后天还车”，回复转入租车任务且保留城市与日期，至少准确追问取还车当地时刻；不返回酒店。该步不要求生成租车卡。
4. 负例覆盖“只是问怎么订”“查询订单”“取消旧卡”“改问别的城市”、跨账号会话和订单、错误模型 JSON、旧引用／过期报价、错误日期、明确两笔写入与未授权口头确认。所有卡仅为提案；确认前订单计数及版本不变。隔离库中再测试拒绝、确认、重复确认与重启后的状态一致性。
5. 运行全套自动化测试、两日期航线样本、Python 编译、前端语法（若改页面）、依赖、文档链接和差异检查；以**不超过 40 次**真实 DeepSeek 请求在隔离环境复核交易同义词、跨轮指代及混合任务，记录调用次数、可得 token 用量与估算费用。预计用量以供应商账单为准；若鉴权、费用或错误率异常即停。此步不需要天气联网搜索调用。
