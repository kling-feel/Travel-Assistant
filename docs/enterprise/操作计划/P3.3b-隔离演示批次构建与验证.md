# P3.3b：隔离演示批次构建与验证操作计划

> 2026-10-24 制定｜状态：已按计划完成；详见[验收记录](../P3.3b-隔离演示批次验收记录.md)。承接已完成的[P3.3a 安全预检](../P3.3a-演示批次安全预检记录.md)。本计划仅创建、验证独立新批次，**不切换 8000 正式演示入口**。结果写入[当前进度](../当前进度.md)。

## 1. 目标、输入与范围

用执行当天明确记录的演示日期，从可交付虚构样本生成一套新的 PostgreSQL 演示数据库；旧批次数据库、订单、会话、确认卡与审计原样保留。新批次使用独立 Compose 项目、端口、数据卷和登录密钥。P3.3a 静态预检建议项目名 `travel-date-next`、候选数据库端口 5436、候选 API 端口 8015；执行前以实际系统状态重新核对，不把候选值当成已占用或已可用的证明。

当前工作台没有可调用的 Docker 命令，且旧 5433／8000 未监听。若开工时仍如此，我会先完成全部不依赖 Docker 的代码与离线准备；确需启动、检查或备份容器时，再给旅客**逐条、可复制的普通 PowerShell 命令**，只要求回传无密码的状态摘要。旧数据库状态与实际卷名目前未知，不能在未知时执行任何导入。

## 2. 旅客确认后的操作顺序

1. **开工核对**：重读产品需求、架构、进度、本计划和 P3.3a 记录；核对本地功能分支、`main`、远端及工作区。记录执行日、目标演示日和预期未来 30 日查询窗。核对 Docker 可用性、5433／5436 与 8000／8015 端口、旧项目及卷标签；若与记录不符，先调整隔离端口和方案，不连接未知数据库。
2. **只读旧批次与备份**：在实际旧库可识别时，以只读查询记录 `demo_state.as_of`、账号、机票／酒店／租车订单状态、会话、动作、审计和迁移版本的数量，不输出消息正文、密码或令牌。对旧库做带时间标记的自定义格式备份并检查目录；在**第三个临时数据库**恢复它，核对日期、表和关键计数。若旧库不能辨认、备份或恢复，停止新批次写入并报告。备份和临时卷在 Git 忽略目录／独立项目，旧卷不改动。
3. **新库身份与密钥**：用专属 Compose 项目创建空新卷；同时核对实际卷标签、端口、数据库名称和有效连接目标。为新批次生成独立 JWT 签名密钥及两名演示账号密码，保存在 Git 忽略文件中，不打印、不提交。应用启动及导入时明确覆盖环境变量；若 `DATABASE_URL` 指向旧库、目标库并非空新卷或出现非预期账号，停止写入。
4. **迁移、预览和导入**：只对新库运行现有 13 个迁移版本及图检查点初始化；在空新库保存可恢复备份。用目标演示日先运行数据导入预览，列出目标标识、现有计数、预计 115 机场／33,121 航班／可售班次和将清理的表；核对后再显式导入。必要时为现有导入入口增加目标库指纹与“只允许指定隔离项目”的拒绝条件，不改变虚构排程、报价、政策和交易算法。
5. **验证与重复构建**：核对样本哈希、618 可售航线、窗口内班次、机场当地出发／到达日、酒店落地后两晚覆盖、租车产品、初始订单金额与政策版本。用第二个全新隔离卷、相同源样本和演示日重复构建，比对确定性供给、模拟报价与初始订单业务字段；密码哈希、创建时间和随机令牌不参与确定性比较。新旧库关键计数及旧库只读业务摘要保持一致。证明旧令牌在新批次返回 401，避免同一默认旅客 ID 跨批次误用。
6. **代码与结果验收**：补针对错误端口／卷、连接串覆盖、缺失或不可恢复备份、重跑同一批次、日期跨时区、旧令牌等真实风险的测试；运行相关定向测试及完整自动化回归，检查接口、迁移、文档链接和公开凭证。将命令、实际计数、旧库未变证据、备份恢复结果及新批次卷名写入单独验收记录和《当前进度》，只提交本地功能分支。独立 8015 页面完整交易旅程及正式 8000 切换留给 P3.3c 的新计划。

## 3. 停止条件与后续门槛

- 任何目标库身份、卷标签、连接串、备份恢复或旧库状态不明确时，不运行写入命令；只读已知部分继续并报告阻断点。
- 不执行旧库的 `--apply --reset-demo`，不覆盖旧卷，不执行 `docker compose down -v`，不修改正式 8000 页面或浏览器当前会话。
- 不调用付费模型或联网搜索；P3.3b 可用固定模型和离线数据验证，P3.3c 再按独立预算与方案做真实页面验收。
- P3.3b 不合并本机 `main`、不推送 GitHub。新批次构建通过也**不代表可以切换正式入口**；需先提交 P3.3c 具体计划并由旅客确认。
