# P3.4c3c1a 否定下单语义修复与隔离复测操作计划

> 2026-10-27 制定，**等待旅客确认后执行**。承接[P3.4c3c1 阻断记录](../P3.4c3c1-正式发布阻断与回退记录.md)。本计划只处理正式发布中发现的自然语言缺陷及隔离复测；不开放公网、不改正式云端订单、不合并或推送 `main`。

## 目标与边界

修复“先别下单，只告诉我航班时间和报价”被误识别为机票预订并生成待确认卡的问题。对话可以保留已查询候选，但只有旅客随后独立、明确地提出预订，才能生成待确认卡；任何新增、修改或取消仍须逐卡由旅客确认。保留“别确认这张卡”与“取消订单”的区别，不把普通否定误当成撤销已确认订单。原云端应用和代理当前关闭，数据库及五卷保留；此次从本机分支和隔离数据库推进。

## 执行步骤

1. **开工核对**：重读《产品需求》《软件架构》《当前进度》和本计划；核对本机 `main`、功能分支、GitHub 当前提交与工作区差异。复查 P3.4c3c1 的真实对话、卡片与原订单摘要，确认旧镜像已经恢复、公网关闭。无需再次读取或复制服务商密钥来做离线修复。
2. **统一只读意图边界**：在对话动作识别与 API 落卡入口共用一个有测试覆盖的中文否定判定，覆盖“先别下单／先不下单／暂时别订／不用预订／不要购买／只查价格／先看时间”等明确只读语义。对“别确认卡片”和“取消已确认订单”分别处理；沿用当前航班任务上下文，但不沿用过时的“预订目标”去覆盖本轮否定。对歧义句先追问，禁止先生成卡再解释。
3. **有意义的回归**：以本次三轮真实话术和临近变体建立端到端固定模型测试，断言否定语句无交易计划、无卡、订单不变，且随后明确“现在预订刚才那班”恰好生成一张待确认卡。覆盖机票／酒店／租车的“先别订”、历史查询、取消卡指代、跨会话和过期候选，检查没有误伤真实交易。运行完整自动化、`pip check`、编译、页面脚本与差异检查；没有新增数据库迁移或对外路由。
4. **隔离真实模型复测**：使用全新或已核验身份的隔离 PostgreSQL 卷，先备份再导入同批次虚构数据。仅在隔离应用调用现有 DeepSeek 少量轮次，重复“查询最早→先别下单→只问时间价格→明确预订→待确认卡→查询历史／改目的地”的路径，核对卡片、引用和服务端订单摘要；再抽查阿里云联网推荐。任一否定写卡、未确认写订单、越权或密钥泄露即停止。正式 `travel-cloud` 库仅只读对照，不接收新测试订单。
5. **结果与收尾**：停止隔离容器，保留数据卷、备份和脱敏证据，清理临时账号与密钥副本；更新《当前进度》和独立验收记录，在功能分支提交可审查的代码、测试和文档。若通过，再单独给出 `G-22` 主线与 GitHub 同步计划，待旅客确认后执行；之后重新制定正式云端发布、真实模型和准确视口验收计划。云端公网在此之前保持关闭。

## 验收标准与失败处理

- 本次原话和至少两种相近否定说法均无卡；“现在订这班”只有一张待确认卡，确认前订单不变；酒店与租车同样受保护。
- API 落卡前兜底与路由识别结论一致；历史问答、撤回待确认卡和已确认订单取消互不混淆。完整回归及隔离真实模型复测通过，原云端订单／供给摘要保持原样。
- 如果修复引起合法订票被拒绝、模型仍出错、账单异常或资源／日志检查失败，停止隔离调用，保留证据并修订方案；不推进主线同步或公网展示。

本阶段通常不需要旅客购买服务或提供新密钥；若工作台无法完成 Docker 隔离操作，会先自行核对可用入口，再只请求旅客代执行最少的容器命令。任何访问私有密钥的步骤提前说明用途，值不发到聊天或 Git。
