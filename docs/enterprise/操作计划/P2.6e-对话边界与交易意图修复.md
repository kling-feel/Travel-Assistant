# P2.6e：对话边界与交易意图修复操作计划

> 编写日期：2026-10-19｜状态：用户已确认，独立分支验收完成；本计划依据 P2.6d 隔离实测制定。

## 1. 为什么进入这一阶段

P2.6d 已完成 113 次真实 DeepSeek 请求、四段各六轮多轮旅程、隔离实库与安全核验。九类标准交易和九类不同说法均能生成待确认卡；未观察到绕过确认或跨账号写入。但 94 个可评分场景执行中只有 82 个通过（含重复稳定性检查），低于 90% 目标，且明确“撤回刚才未确认的酒店卡，不是取消已确认订单”仍生成已有酒店订单的取消卡。真实航司政策 5 个问法中 3 个误取本平台虚构政策；“第二班／第 2 班”短说法无法选中已展示的第二个候选；口头“同意”会重复生成租车预订卡。以上问题必须先修复，再讨论本机合并。

本阶段只修正**已实现的**对话、政策与待确认卡边界。继续保持 FastAPI、LangGraph 主助手和简洁的 Python 模块结构；所有金额、订单对象与最终写入仍由服务端规则和旅客逐笔确认 API 决定。暂不接联网景点推荐、前端页面、真实供应商或支付。

## 2. 开工与 Git / 数据安全顺序

1. 重新打开《产品需求》《软件架构》《当前进度》、P2.6d 结果及本计划；核对 `<历史功能分支>` 已提交且工作区干净、本机 `main` 和远端引用。获得本计划确认后，从评估分支建 `<历史功能分支>`；批准状态及开工记录单独提交，实现另行提交。暂不合并本机 `main`，不推送远端。
2. 仅在独立 `travel-eval` PostgreSQL 项目和 5434 端口复用已验证的虚构数据；执行脚本前校验 Docker 项目标识、数据库地址、基线记录与忽略的备份。不连接正式演示库，不改原 SQLite、迁移或产品库存。每次实库复测清理虚构旅客记录，失败则保留现场并报告。
3. 新增的真实模型复测需另设有上限的请求与费用账本。建议最多 **25 次 DeepSeek 请求、保守费用停机线 1 元**，零自动重试、25 秒超时、4096 输出 token；实际扣费以服务商账单为准。此费用安排随本计划一起请用户确认，不沿用 P2.6d 已结束的 8 元授权。

## 3. 实现步骤

### A. 外部真实政策与本平台虚构政策分流

- 在模型查询虚构政策前，增加确定性边界检查：出现具体真实航司／供应商或明确要求官网、实际规则、费用时，不读取虚构 `policy` 作为答案。中英文品牌、航空／Airlines／Airways、行李／退改等用例纳入回归；识别不确定时先问“你是查询本平台虚构规则，还是某真实航司规则？”。
- 没有已接入且可引用的真实官方来源时，统一说明无法核实真实规则并建议官网核对；普通“本平台机票取消费”仍给数据库内当前规则 ID、版本和模拟金额。防护应放在模型输出后的服务端边界，避免仅靠提示词遵循。

### B. 撤回待确认卡与取消已确认订单分开

- 对“刚才的卡不要执行／撤回待确认预订／先不订”先读取本人会话中的待确认卡，返回明确的卡片状态与拒绝动作说明，**不生成订单取消卡**。本阶段不把自然语言自动转换为 `confirm` 或 `reject` API 调用；拒绝仍由旅客对明确卡 ID 通过 API 操作。已经拒绝或失效的卡说明当前状态。
- “取消我已确认的酒店订单”才走订单取消提案；同时存在多张酒店订单或对象含糊时要求指定。新增“不是取消已确认订单”的否定表达、双卡撤回、跨账号卡 ID、无待确认卡等用例。卡片文字突出目标订单、后果、模拟金额与尚未执行。

### C. 候选序号与口头确认

- 扩展已展示候选的序号解析，覆盖“第二班”“第 2 班”“第二班航班”“第二个”等常见说法；仅允许选择当前会话近期真实展示的候选，序号越界、候选已失效或模型给出不一致 ID 时追问。
- 旅客说“同意了／直接付款／替我点确认”时，不重复生成同类卡、也不写订单；返回最近待确认卡 ID 和逐笔确认 API 的操作说明。若旅客同时提出新的明确交易需求，优先澄清后再建卡。

## 4. 验收与收尾

- 先跑不收费的固定模型、结构化输出故障注入、九类交易全链路、双卡原子性、未确认不写、跨账号与重放；再用小批量真实 DeepSeek 对本次失败场景、九类交易不同说法、四段多轮旅程与外部政策问题定向复测。记录卡 ID/对象、响应和数据库前后快照，不能只凭模型自述判定。
- 阻断项：撤回语句生成任何已确认订单的取消卡、外部政策问题返回虚构规则、口头同意写订单或重复建卡、序号选错真实候选、跨账号/无确认写入。已知失败用例须全部通过；60 项现有及新增测试、两日期全航线样本、编译、`pip check`、Git 差异检查均通过。
- 更新 `security_best_practices_report.md` 和《当前进度.md》，说明修复证据与仍未解决的限制。保持本机 `main` 与远端不动；待 P2.6e 验收后，另提交 G-14 本机快进合并计划请用户确认。
- 上线前另设限流、单账号费用上限、受信 Host、文档开放策略与反向代理验收阶段；不把本机隔离测试当作公网安全验收。随后按已确认方向做 P2.7 可达城市、带来源的经典地点联网推荐，再做简单页面与部署。
