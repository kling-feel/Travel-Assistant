## 目标和当前依据

从只读的 `travel_new.sqlite` 生成一个可随项目交付、可复现的**虚构航线数据样本**，供后续 P2.4b 导入 PostgreSQL。目标保留全部 115 个机场和 33,121 条航班记录，包括 15,383 条 Scheduled 及其他历史/取消状态，使 618 条航线都有可查的 Scheduled 班次。只抽取机场、航班需要的非个人字段；不导出票号、旅客、预订编号、酒店原始订单或租车原始订单。两名旅客的演示订单在 P2.4b 用合成身份与正式航班重新设定。

原库只读核对显示：机场 `coordinates` 为 `[纬度, 经度]` 文本，115 条坐标与时区都可解析；机场代码和航班 ID 无重复，机场引用缺失 0，航班计划起降顺序错误 0。原航班时刻统一带 `-04:00` 偏移，与起飞机场的真实时区并不一致；已有 P0 约定用 HAM→BSL 已有下午航班的**墙上时间**对齐演示日，再对全部航班施加同一个绝对时间差。此做法保持航班间隔，但其他机场显示的当地钟点可能与源文本不同，验收时需明确展示。

## 时间轴的确定规则

1. 在原库选定 2026-09-21 的 HAM→BSL 下午 Scheduled 航班作为稳定锚（只读盘点：源 ID 8144、源文本钟点 17:43）；同日另有源文本钟点 17:58 的候选（源 ID 8152）。实施时再次以数据校验确认，不只依赖硬编码 ID。
2. 对给定 `--as-of` 日期，把锚的源文本钟点定位到**次日汉堡当地 17:43**，算出一个 UTC 时间差；对所有计划起降和存在的实际起降时间应用同一差值。样本保存原始时刻，平移发生在后续导入/离线验证时，不因生成样本当天变化。
3. 保留原状态。只有平移后仍在未来、处于约 30 天展示窗内且状态为 `Scheduled` 的航班可供预订。`Cancelled` 等状态可用于历史/不可订展示，不能获得可订报价。
4. 用各机场 IANA 时区展示当地时间，并在 API/页面标明时区；跨夏令时仍以绝对时间间隔为准。源数据的 `-04:00` 是虚构样本格式，不解释为所有机场当地时间。
