# P2.5b：租车预订与取消操作计划

> 编写日期：2026-10-18｜状态：时间、计价与取消规则已获用户认可；实施仍待单独确认；本文件只记录事前方案，实施结果写《当前进度.md》

## 目标与待判断的业务规则

在现有 208 个虚构租车产品和受控确认链路上，补齐 `rental_book`、`rental_cancel`：内部服务生成具体卡片，本人逐笔确认后才创建或取消模拟租车订单；行程 API 可查看本人租车订单。保持原有 FastAPI、SQLAlchemy 服务层和简洁 Python 风格。普通对话还不能直接生成卡片，P2.6 接入助手时仍须走相同服务。没有真实车辆库存、供应商、付款或退款。

用户已认可以下规则；实施仍须单独确认，若需修改则先修订计划再开工：

1. **时间输入**：预订必须指定租车产品、取车和还车的当地日期与时刻。产品关联机场的 IANA 时区是唯一业务时区；卡片显示机场当地时刻、时区和 UTC 偏移，数据库以 UTC 时刻保存。请求时刻如遇夏令时的不存在/重复当地时间，应澄清或要求明确偏移，不猜测时间。未给具体时刻时，后续助手必须追问。
2. **计价**：还车须晚于取车；按 UTC 实际经过时间每开始 24 小时算一个模拟计费日，最少 1 日。例如 25 小时按 2 日。总额 = 当前产品日价 × 计费日数；卡片列出日价、日数、总额及“演示计价单位”，不由模型或客户端定价。
3. **取消**：取车时刻**之前**确认取消，模拟手续费为 0、模拟应退为原订单总额；到达或超过取车时刻则拒绝取消。取消不物理删除订单，不发生实际退款。取车后不提供修改或取消功能；本阶段不加租车改期。

这些规则与已确认的虚构平台方向及现有 v1 租车政策一致。若后续改为按当地自然日计费，应在实施前更改本计划、政策和验收示例。

## 拟改动模块与契约

1. G-08 完成且本机 `main` 干净后，从 `main` 建 `<历史功能分支>`。新增 **v009** 迁移和 `rental_orders` 表：订单 ID、旅客/产品外键、取还车 UTC 时刻、订单时采用的日价、计费日数、模拟总额、状态、版本及时间戳，并建立归属/查询索引与必要的状态、正金额/日期约束；将待确认动作类型扩至 `rental_book`、`rental_cancel`。不改写已应用的 v001～v008。原有产品仍无库存数，不产生库存扣减。
2. 新增虚构租车政策 v2，写明计费和取消边界，保留 v1 供历史审计。现有 `GET /api/v1/rentals` 继续用于日期级候选搜索；建卡时由内部服务对指定产品及精确时刻重新校验：取车在未来演示窗口、当地取车/还车日期位于产品可用范围、还车晚于取车、产品和机场时区有效。卡片包括产品、取还车当地时刻、模拟金额和政策版本。搜索结果的提示应从“订单未开放”改为与现状相符。
3. `rental_book` 确认时复核本人会话、卡片期限、产品、时区、时刻、当前日价及政策版本，并在同一事务中写一笔本人订单、结果和审计。任一依赖变化使卡片失效并要求重提案；同一动作重复确认返回同一结果。不同卡片的重复预订边界按**相同旅客、同一产品、取还车时段完全相同**防重复；不同产品或时段仍允许多笔订单，不宣称真实库存。用数据库约束或串行化事务保护并发。
4. `rental_cancel` 只针对本人已确认订单，卡片固定订单 ID/版本、取车时刻、模拟应退额和政策。确认时重新检查归属、状态、版本和当前 UTC 时间；只有取车前才能将状态改为已取消，写结果和审计。旧卡重放、双请求并发及另一会话的冲突只允许一次状态变化。本人行程 API 增加租车订单，其他旅客不可见；不开放客户端指定旅客 ID/价格的建单直写接口。
5. 调整显式演示重置、种子和相关验收脚本的清理顺序：有待确认动作继续拒绝重置；重置订单前先核验并备份，租车订单先于租车产品清理。正常启动和迁移不清理订单。README 补充 API、时区、计价、模拟退款、备份/重置与演示步骤。

## 完成判据与失败处理

- 预订和取消都只由本人确认具体动作执行；卡片、订单、行程、结果及审计金额一致，过期/越权/价格或政策变化时不写入。
- 计费和取消临界时刻可复现；并发不会生成完全重复的有效租车订单或重复取消；原有六类动作及产品搜索不回退。
- 迁移或实库验收失败时保留数据库、备份和现场；已应用迁移用新的修正版本处理，不改写 v009。禁止清卷、强推或自动合并。
