# P2.4b：全航线正式库导入、报价与演示订单操作计划

> 编写日期：2026-10-17｜状态：待用户确认；本文件只记录事前方案，实际结果写《当前进度.md》

## 目标、依赖与设计决定

在 G-05 本机合并完成后，以 `data/fixtures/network_source.sqlite` 为唯一航班源，把 115 个机场、33,121 班航班导入 PostgreSQL，形成全部 618 条 Scheduled 航线可查询的约 30 天演示窗。建立两个**合成**旅客、两张能在次日下午改签的演示机票，并让 P2.3 的确认流程在新航班号上继续可用。

现有 `import_demo_data.py` 固定 HAM→BSL 小样本并逐条拼接 SQL；`seed_p1.py` 逐行读取和插入，重置会话、动作、结果与审计；`services/demo_pricing.py` 只识别旧样本的 4 个航班号。新样本的编号均为 `SIM-<ID>`，故**本步建议同时生成全部可订 Scheduled 班次的确定性模拟报价**，否则导入后改签提案/确认可能无报价。原路线把报价放在 P2.4c，本计划将其前移；P2.4c 留给酒店/租车供给及政策清理。此边界调整需与本计划一起由用户确认。

本步不会接入 DeepSeek/Tavily，不开放旧图交易路由，不做真实支付/出票，不扩展酒店/租车至所有城市。无需配置模型或联网检索密钥。P2.4c 后再完成全城市产品覆盖。

## 拟修改的模块与具体规则

1. **迁移与模型**：新增 v005 迁移，在正式机场表保存纬度、经度，在航班表建立按起点、终点、状态和出发时刻的查询索引；迁移可重复运行且不破坏已有 v001～v004 数据。按 SQLAlchemy 模型同步字段。若旧数据库已有机场记录，新列允许先为空，在显式重置导入时填满；不得让普通迁移隐式删除记录。
2. **时间轴与导入**：读取版本化 SQLite 的机场/航班白名单，以源航班 8144 和 8152 校验 HAM→BSL 的下午锚/候选；按指定 `--as-of` 把锚对齐到次日汉堡当地 17:43，计算一个 UTC 差值并应用于所有计划时间及存在的实际时间。源统一 `-04:00` 只作带偏移的绝对时间解析，各机场的当地日期由 IANA 时区计算。批量写入有约束的暂存数据并核对数量、外键、状态和时间窗，避免 33,121 条逐条 SQL 字符串。失败时事务回滚，不留下半份网络。
3. **模拟报价**：只给演示窗内 `Scheduled` 班次生成报价，金额由稳定的航班 ID/路线等非模型输入及显式算法版本计算；同一数据、日期和规则重复生成相同整数金额。报价关联真实已导入航班，记 `rule_id` 与 `version`，不能用源票价或航司报价。演示已购机票的 `amount` 与其报价一致，保证改签只补/退新旧票价差、取消仍按原票价 30%。跨日重置会使旧确认卡失效，绝不沿用旧金额。
4. **合成演示订单**：创建两个虚构账号的两张 `confirmed` 机票；至少一张用源航班 8144，源航班 8152 是次日下午可改签候选。订单 ID、旅客 ID、金额和时间来自可复现规则及已导入航班，不导出原库的真实旅客、票号、订座号。暂时保留现有少量巴塞尔虚构酒店产品与订单，供 P2.3 五类动作回归；它们不代表本步已经完成全城市酒店覆盖。
5. **查询边界**：航班查询按起飞机场当地日期换算 UTC 起止时间，在 SQL 中筛选路线、`Scheduled` 状态、日期与约 30 天演示窗；超出日期、无班次或未知机场返回空。为 API 设置明确的分页/数量上限，避免全量扫描与过大响应；对话默认 3 个候选和“最便宜”排序留给后续智能体阶段，但底层查询应支持正确报价排序。确认服务仍用数据库报价复核，不采信客户端或模型金额。
6. **显式重置与说明**：提供清楚的初始化/重置命令及 `--as-of` 输入，普通 API、数据库重启或迁移不会自动重置。重置前显示当前正式表中旅客、订单、会话、动作、结果和审计计数、目标日期及清除范围；如有非演示账号则拒绝。只在明确触发的演示重置中清除两个账号的旧会话、订单和动作，保留数据库卷。更新 README 中完整命令、预计计数、首次导入/重复导入、备份与何时不应重置的说明。

1. 开工前重读三份核心文档、本计划和 G-05 实际结果；核对本机 `main`、工作区与数据库状态。用户确认后从干净 `main` 建 `<历史功能分支>` 短期分支。
2. 先用只读方式检查现有 PostgreSQL 表计数和是否仅有两个演示账号。启动数据库仅为本计划需要；在任何会清除演示状态的操作前，用本机 `pg_dump` 导出到被 Git 忽略的 `data/generated/`，验证备份文件非空且可读取结构，记录备份路径与导出时间。备份可能包含本机演示密码哈希和会话，故不提交、不贴入聊天。
3. 实现 v005、批量导入、统一平移、报价、合成订单与查询改造；分别检查空库首次初始化和已有 v004 数据库升级。数据暂存校验成功后才切换正式演示快照；若发现非演示账号或数量/引用异常，停止切换并保留原库。
4. 增加针对时间/时区、618 航线、报价重建、已有票价一致、改签/取消、重置后旧动作失效、首次/重复导入及 SQL 查询边界的必要测试。保留旧小样本单元测试的兼容性，修订不再成立的样本专属断言；运行全部现有自动化测试、编译、依赖检查和 `git diff --check`。
5. 在本机 PostgreSQL 执行 v005 与显式导入/种子；复跑导入并核对计数不翻倍，重启数据库后核对持久化。对两个演示账号实测登录、行程、全航线代表查询、无班次/超窗、模拟报价、机票改签和取消确认、现有酒店动作、跨账号拒绝与并发/重复确认。涉及写入的验收使用独立测试账号或可清理记录；最终演示账号恢复为两张有效机票、两张既有酒店订单，测试会话/动作清理干净，数据库停止但卷保留。
6. 检查导入耗时与代表性查询的执行计划/耗时（含跨时区路线），确认索引实际被利用或给出可复现的改进。审阅提交文件和敏感内容；只在短期分支提交代码与文档。真实结果、计数、性能指标和剩余风险写入《当前进度.md》。本步不合并 `main`、不推送远端；后续本机合并另写 G-06 计划。

## 验收门槛与失败处理

- 正式表有 115 个有效时区/坐标机场、33,121 个关联完整的航班；`Scheduled` 原始状态数 15,383，指定演示日的未来约 30 天保持 618 条有班次航线；不可订状态没有报价。
- 同一演示日重复导入不增加记录；两个合成账号、机票及报价保持一致。正常服务重启不改变订单；显式重置准确清理旧会话/动作，并在 README 明示。
- P2.3 五类已实现动作及确认边界仍通过：每笔写入需本人确认，价格/版本变化令旧卡失效，取消费 30%，重复确认无重复写入。
- 任一迁移、暂存校验或导入失败，则停止后续重置、保留旧可用数据和备份；若在切换后才发现问题，先报告实际状态和备份/修复方案，不自动覆盖或恢复用户数据。不执行 `docker compose down -v`。

用户确认本计划及“报价前移”后才实施。若数据库实际已有非演示数据，或备份无法验证，先报告并修订执行方案，不做清除操作。
