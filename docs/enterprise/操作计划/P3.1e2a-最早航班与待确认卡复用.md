# P3.1e2a：最早航班与待确认卡复用操作计划

> 编写日期：2026-10-21｜状态：用户已确认并在功能分支实施。承接 P3.1e1；不包含正式库重置、本机主线合并或 GitHub 推送。实施结果见《当前进度》。

## 1. 要解决的真实问题

旅客已说明“从上海去伦敦，明天没有航班，那就找最早能走的”，助手目前仍要求重新填写日期。`find_flights` 只能查指定的一天；之前的“最近可查日期”仅是提示，没有形成可选候选。另一个已观察问题是：第一张机票卡仍待确认时，旅客换一个请求键重复说“预订这个航班”，会得到第二张同目标卡。P3.1e2a 先解决这两项，继续遵守所有订单写入须旅客逐笔确认的规则。

## 2. 建议采用的产品语义

1. **“最早”搜索范围**：以用户明确指定的最早出行日为下界；未给日期时，从当前实际时刻起搜索。只查当前模拟库的未来 30 天可订窗口，且不早于 `demo_state.as_of + 1`。若上一轮明确要求“明天出发”但当天无班次，后续“那最早呢”沿用明天作为下界；本轮明确说“从 10 月 27 日起”则以新日期覆盖。窗口外如实说明，不挪动数据库时间。
2. **比较范围**：在明确的起终点城市所覆盖的全部机场组合中，查有有效模拟报价、状态可售且起飞时刻仍在未来的**直达航班**。按各班次真实 UTC 起飞时刻比较，向旅客显示出发机场当地日期与时间。不能先对每个机场组合或每天截取前三条，再宣称得到全局最早。没有直达结果就说明供给边界，不编造中转。
3. **查询和预订**：“最早什么时候能走”先给最早候选及覆盖的搜索日期窗；“就订最早的”或“我就预订最早班次”已明确授权选择排序第一的可售班次，可直接生成**一张待确认卡**，卡片展示机场、航班、当地时间、报价和政策，但订单仍未执行。如果同一最早起飞时刻有不同航班，先展示并请旅客选定，不用航班 ID 暗中打破业务歧义。
4. **重复卡**：同一旅客、同一会话内已有目标、交易类型和规范化参数都相同且仍有效的待确认卡时，新话轮指向原卡并说明尚待确认，不新建第二张。旧卡已过期、被拒绝、价格／规则／产品版本变化或参数不同，则不能复用；旅客须重新取得当前报价。不同账号或会话绝不共用卡。相同 `request_key` 的既有轮次幂等机制继续保留。

以上四项为本计划的推荐规则，待用户确认后写入《产品需求》和《软件架构》。这里的“30 天”继承当前模拟供给窗口，不新增航班或改变种子时间轴。

## 4. 具体实施顺序

### A. 全局最早航班查询

1. 在 `services/travel.py` 增加有界的跨日期只读查询：按城市解析得到的机场集合、下界时刻、模拟窗口和可售状态过滤，数据库全局排序后才截取显示数量；利用现有航线与起飞时间索引。返回查询范围、班次 ID、机场、UTC 起飞时刻、当地展示时刻、模拟报价和报价版本。
2. 在 `services/dialogue_context.py`、`graph_chat/controlled.py` 和 `services/agent_reads.py` 识别“最早／最近能走／什么时候能出发”，仅在航班任务且起终点已明确时继承上轮条件；缺出发地或目的地只追问缺项。新路线或新日期明确出现时覆盖旧任务条件。结果写入当前会话的航班候选检查点，不使用其他会话或旧路线候选。
3. “预订最早”由受控服务排序并选择目标，模型不能自行填写所谓最早的航班 ID。若并列最早、报价过期或旅客的时间下界含糊，先列候选或追问，不生成卡。建卡前和确认时继续复核报价、班次可售性与本人身份。

### B. 待确认卡复用

1. 在提案服务／会话 API 中查询本人当前会话的有效待确认卡，比较规范化动作参数、目标班次与报价／规则版本。仅在上述条件完全一致时返回原卡；不能依据模型文字或仅凭航班号复用。保持动作审计可追溯，并使新话轮明确指向旧卡状态。
2. 对过期、已拒绝或版本变化的卡给出明确说明，再按当前数据重新搜索／提案；不借重复话轮自动确认、拒绝或取消旧订单。两笔写入请求仍按现有逐笔确认和原子提案边界处理。

## 5. 验收用例与停止条件

1. 原话连续回放：“明天上海去伦敦”→“该日无直达，最近可查 10 月 25 日”→“最早能起飞的是什么时候”→“就预订最早那班”。结果必须是全机场组合、窗口内实际最早的可售班次，显示完整当地时间；最后只生成准确的一张待确认卡，确认前订单不变。另测“从 10 月 27 日起”不回退到 25 日。
2. 用并列时刻、跨时区／跨当地日期、今日已起飞、空航线、过期报价、同城多机场、窗口边界和模型伪造 ID 检验排序及拒绝；三个候选的展示限制不能影响全局最早判断。
3. 对同一请求键重放、不同请求键重复请求、拒绝后再请求、卡过期、报价或规则变化、两账号与两会话隔离做数据库验收。重复有效卡时 `pending_actions` 与审计提案数不增加；拒绝和确认仍由动作接口执行。
4. 运行全套自动化回归、编译、依赖、文档链接及 Git 差异检查；再以隔离数据做少量真实 DeepSeek 对话。真实模型请求上限建议 **20 次**，逐轮记录可得 token 用量，账单费用以提供方为准；异常认证、费用或错误率出现即停止。阿里云联网搜索与本步航班库存无关，不调用。
5. 任何错误目标卡、跨账号卡复用、未经确认的订单写入或无法解释的价格／时间差异，立即停止本轮实施并保留诊断证据，不进入主线发布。
