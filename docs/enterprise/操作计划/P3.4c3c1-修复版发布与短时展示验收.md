## 目标、现状与风险边界

- 本机与 GitHub `main` 当前均为 `69f2f9ec9ed2242431e74c18ba2911012a3d9e59`，功能修复已经公开审查；执行时重新核对本机、实时 GitHub 与准备部署的代码包哈希。云端数据库为 2026-10-27 虚构批次，有原有授权账号、订单、会话和五个持久卷；正式应用镜像仍是修复前代码，代理和应用已停止。**不运行 `init`、`empty-backup`、演示数据导入或日期平移。**
- 服务器为香港 Ubuntu 24.04、2 vCPU／2 GiB、约 40 GiB。沿用 `compose.cloud.yaml` 与 `compose.cloud.2g.yaml` 的同一个 `travel-cloud` 项目、既有私有环境、证书和卷。数据库只在容器网络，不开放 8000／5432；公网只由代理监听 80／443。登录只允许已有授权账号，不开放注册；所有供给和金额仍是模拟。
- 原库在备份与只读核对后保留；正式验收只使用专用临时授权账号创建会话和待确认卡，**不点击订单确认**。因此业务订单、报价和演示供给摘要应与发布前相同；预期新增的仅是临时账号、会话、卡片、审计及服务商用量。临时账号最后停用，审计保留。

## 执行步骤与逐段放行条件

1. **开工核对**：重读三份核心文档、本计划和两份前置验收；确认 `main`／GitHub 提交一致、工作区干净。通过已验证的专用 SSH 身份只读检查云端项目标签、五个卷、数据库健康、应用与代理关闭、当前镜像 ID、批次日与数据库摘要、私有配置权限、证书到期日、DNS、磁盘、`MemAvailable`、容器／内核 OOM。检查本机 8000 不被本阶段启停。若项目身份或原库摘要不符、已有 OOM 或空间不足，停止发布。
2. **服务器外升级备份和回退准备**：在原库创建**新文件名**的 `pg_dump -Fc`，校验 `pg_restore -l`、文件权限、SHA256，并把本批次清单和脱敏摘要一起按 P3.4c3a 的方式在旅客 Windows 电脑直接加密保存。使用本机恢复身份实际验证新密文可解开与归档可读，不在服务器或 Git 留恢复私钥。记录旧应用镜像 ID、旧代码提交与 Compose 配置，给旧镜像加本机回退标签；禁止镜像清理或删除卷。若备份不能从服务器外解密，停止发布。
3. **准备修复版而不覆盖原配置**：只从已审查的 `main` 跟踪文件制作发布包，核对压缩包清单和 SHA256，再通过专用 SSH 放入新的服务器发布目录。保持原私有 `cloud.env`、授权账号文件和持久卷在原位；新目录若需引用环境文件，使用经核对的受限引用，不把密钥复制进构建上下文或镜像。核对 `docker compose config` 和变更预览：项目名、数据库镜像／卷、代理证书卷和端口必须与原项目一致，且应用源代码包含本轮只读意图修复。若 Compose 打算新建或重置原数据库卷，停止。
4. **分时构建与私有启动**：在代理保持关闭时按 2 GiB 限额单路构建新应用镜像；监测内存、磁盘、构建退出码、镜像内容和 OOM。先仅让新应用连接既有健康数据库，使用内部容器网络或本机 SSH 回环通道验证 `/ready`、匿名 401、授权账号本人读取、跨账号 404、停用种子账号 401。核对原库供给／订单摘要未变，模型与搜索密钥不出现在日志、镜像层或终端输出。若新应用无法就绪，恢复旧应用镜像并维持代理关闭。
5. **修复版真实对话抽样**：用新的临时授权账号做约 6～10 轮真实 DeepSeek 对话：计划旅行但尚未订票、查询最早航班、“先不要下单”、明确预订后只生成一张待确认卡、查看已有卡、查询取消历史、修改目的地，以及落地酒店／租车日期冲突。另做一轮需阿里云联网搜索的经典地点推荐，核对返回来源或明确回退。逐轮比较 API 卡片、当前业务订单摘要和用量事件：否定／历史查询不得生成写卡，明确预订可出卡但**未确认不得写订单**。服务商失败、来源无法核实、异常用量或内容泄露时停止调用，记录可解释的降级；不设置金额自动停机线，实际费用由服务商账单核对。
6. **短时 HTTPS 与页面验收**：确认内部结果后才启动原域名代理。核对根域受信证书、HTTP→HTTPS、`www`→根域、匿名／错误／授权登录、内部文档与健康接口公网 404、宿主机没有 8000／5432 监听或映射。尽可能从真实外部网络核对阿里云控制台防火墙：只开放所需 80／443 和受限 SSH；不能把工作台代理的 TCP 测试当成独立端口证据。在浏览器准确设定桌面、375 与 338 像素，检查中文地点、当前行程与已取消历史、待确认卡对象／当地时间／金额／按钮、消息即时出现、等待时间、核验后逐段答复、刷新保持会话；**不操作确认按钮**。外部网络或控制台若只有旅客能访问，再请旅客提供不含账号资料的现象或截图。
7. **重启、资源与回退试验**：在可控时间分别重启应用和代理，核对证书、登录、会话、待确认卡及订单摘要保持；数据库重启只在新备份和连接恢复路径已确认后执行。观察 2 GiB 主机内存／OOM、磁盘、日志与模型／搜索错误。若新版本有错误，立即停止代理与新应用，使用记录的旧镜像与原 Compose 配置恢复服务；原数据库保持原样，不用旧备份覆盖正常数据库。若已经发生未授权订单写入，先关闭入口、保全审计并另定数据修复方案，不盲目回滚数据库。
8. **展示日流程与收尾**：写出可照做的“启动数据库→核对批次／证书／授权账号→启动应用和代理→一轮只读业务与服务商检查→演示→停代理和应用”的操作卡，并实际演练一次启动与关闭。最后停用本轮临时账号，关闭公网代理与应用，保留原数据库、五卷、新旧镜像与服务器外密文；清理本机临时登录副本、SSH 页面通道和服务器明文暂存。最终复核原业务订单／供给摘要、证书卷、日志泄露、OOM 与服务商调用记录，更新《当前进度》和独立验收记录。新增可复用代码仅在功能分支提交；本机 `main` 与 GitHub 同步另列 G 计划。
