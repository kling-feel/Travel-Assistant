1. **开工复核**：重读《产品需求》《软件架构》《当前进度》与本计划；确认用户已批准 G-14、工作区干净、当前分支与提交正确。先用 `git fetch origin` 刷新引用，只读核对 `origin/main` 以及本机 `main` 的祖先关系；若远端有新提交、工作区有他人修改、或不是快进关系，停止合并并重新给出方案，不强制覆盖。
2. **审查合并范围**：列出 `main..功能分支` 的提交和改动文件。确认没有 `.env`、原始 SQLite、数据库卷、备份、费用账本或脱敏评估报告进入 Git；确认只有 P2.6c～e 已审阅内容。检查 `git diff --check`、现有迁移文件差异和旧图路由注册情况。
3. **合并前回归**：使用仓库 `.venv` 运行全部自动化测试、2026-10-17 与 2026-11-01 两日期全航线离线校验、编译和 `pip check`。不再消耗 DeepSeek API 额度。隔离实库已经在功能分支验证并恢复基线、容器停止；本次 Git 合并无需重启数据库。

5. **合并后回归与记录**：在 `main` 重跑自动化测试、离线航线样本、编译、依赖及差异检查；核对新旅客 API 注册、旧图路由仍未注册。把实际合并点、测试、数据库保持停止、本机与远端状态写入《当前进度.md》并提交文档记录。若任一检查失败，不推送、不继续 P2.7；保留现场并报告修复或回退方案。

- 本机 `main` 先前已领先远端，G-14 只更新本机分支。远端推送是另一项操作，须单独列出待推送提交、远端分支状态和权限风险，再由用户确认。
