# P3.4b2：2 GiB 套餐本机容量验证操作计划

> 2026-10-26。旅客在询问 ¥56／月的香港 2 vCPU／2 GiB 套餐后，明确要求测试 2 GiB 限额下能否部署和使用。本计划先于测试建立；它不授权购买云资源、公开部署、切换本机 8000、合并主线或推送 GitHub。

## 目标与结论边界

在全新隔离 Compose 项目中按接近 2 GiB 服务器的资源预算运行现有云端镜像，验证初始化、授权账号、多轮 API 使用、确认卡、重启和备份恢复。测量容器内存峰值、响应时间、重启及 OOM 事件。测试模型和搜索使用不可调用真实服务的假密钥，不产生付费调用。

Docker Desktop 的容器限额只能模拟服务容器的资源约束，**不能等同于实际香港 2 GiB 主机**：Windows／Linux 虚拟机、宿主系统、Docker 守护进程、网络、磁盘性能和系统更新的开销不同。测试通过只能说明 2 GiB 套餐是可尝试的选项；购买后仍须在真实服务器上按相同项目复测，不能承诺多人峰值或长期稳定运行。

## 隔离与资源预算

- 新项目名 `travel-p34b-2g`，新数据卷、新私有测试配置；只在 `127.0.0.1:8021` 提供隔离 API，PostgreSQL 不映射宿主端口。先确认同名容器／卷不存在；不复用上轮 `travel-p34b-acceptance` 数据卷。
- 运行时让 API、数据库和代理容器分别限制在 768 MiB、640 MiB、128 MiB；合计 **1,536 MiB**，给 2 GiB 主机的系统与 Docker 预留约 **512 MiB**。CPU 约束为 API 1 核、数据库 0.75 核、代理 0.1 核；一次性初始化／账号管理在 API 停止时运行。代理只验证容器启动与配置，不尝试公网证书。
- 使用固定假密钥和虚构批次数据；不读取本机 `.env` 中的真实密钥。独立测试账号密码仅写 Git 忽略的本机文件，不输出到终端或文档。目标数据库为空库时先备份，再运行一次迁移和导入。
- 先对应用镜像的缓存构建和部署准备测时；由于本机镜像构建不受同一 2 GiB 容器总额约束，**不把本机构建成功当成 2 GiB 主机原地构建成功**。若运行通过但原地构建资源不足，须另拟在更大机器构建并安全交付镜像的方案。

## 操作与检查点

1. 只读核对当前功能分支和工作区、原 8000 健康、Docker 引擎、拟用 8021 端口及同名项目／卷。已有同名资源或端口占用则停止，不覆盖。
2. 创建私有测试环境和资源限额覆盖文件，检查 Compose 的实际服务、内存／CPU 限额、端口与数据卷；构建云端镜像。每一步记录时间及构建阶段是否因内存相关错误退出。
3. 启动独立数据库；空库备份并验证格式。运行 v001～v014 迁移和 2026-10-26 虚构全量供给导入，核对 115 机场、33,121 航班、15,374 报价、618 航线和批次清单。初始化期间周期采样容器内存、CPU 和 OOM 计数。
4. 创建两个授权账号并停用种子账号；启动 API 与代理。执行两账号登录、行程、航班／酒店／租车查询、至少一张待确认卡及确认前后核对；按 1、2、3 个并发旅客请求分别采样响应时间、内存与错误。真实模型响应的延迟和吞吐不在假密钥测试范围内。
5. 分别重启 API 和数据库，核对登录、会话和订单仍能读；进行 `pg_dump -Fc` 备份和目录检查，再恢复到**第二个新项目／新空卷**，比较迁移、批次、供给、订单、会话及动作摘要。备份／恢复时同样采样内存；若需要并行额外容器，要明确说明对 2 GiB 主机的影响。
6. 查看每个容器的退出状态、重启次数、OOM 标记、最大内存、总容器内存峰值和请求耗时。停止本轮测试容器但保留卷与 Git 忽略的备份和摘要；再次核对 8000 健康。结果写入《当前进度》和独立验收记录。

## 判断标准

- **可作为 ¥56 候选**：核心功能全部通过；容器无 OOM、异常重启或持续内存增长；运行和导入阶段的总容器峰值不超过 1,536 MiB，且常态明显低于此值；备份／恢复可以按分时步骤完成。最终仍以真实 2 GiB 香港实例复测为准。
- **需优化后重测**：功能通过，但出现内存紧张、明显慢响应，或只能靠本机预构建／分步停服务运行。先提出减内存、错峰维护或预构建镜像的具体改动及代价，不直接建议购买。
- **不建议 ¥56**：初始化、日常双账号使用、重启或恢复发生 OOM、数据不一致、频繁超时、容器重启；建议 4 GiB 或重新设计部署。

本轮测试只改隔离项目和文档，不改正式库或既有公开服务。若 Docker 命令权限受限，先记录原因并做可独立完成的静态检查；只有必要时再请旅客代执行只读命令。
