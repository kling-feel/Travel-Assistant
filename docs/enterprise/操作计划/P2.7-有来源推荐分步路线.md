# P2.7：可达城市经典地点推荐分步路线

> 编写日期：2026-10-19｜状态：P2.7a 已在功能分支验收；P2.7b 修订计划与 G-15 仍需独立确认。

## 1. 目标和已确认边界

在现有 FastAPI、LangGraph 受控对话和 DeepSeek 主模型上，回答旅客对经典地点的推荐请求。推荐仅在对话内出现，优先结合本人的已确认航班、酒店日期与偏好；每个真实地点事实均能对应可点击来源和检索时间。当前模拟航班网络覆盖约 95 个目的地城市，具体可达集合以数据库中的有效航班和报价计算，不能把“网络内可达”说成“旅客所选日期有直飞或余票”。

游览预订、改期、取消、产品浏览、虚构场次与库存均不在最终范围。旅客要求预订景点时，说明当前不支持，提供有来源的地点建议；绝不生成交易确认卡。航班、酒店、租车的九类原有交易和逐笔确认规则保持不变。

## 3. 证据和对话约束

1. 城市范围从数据库航班、报价与机场城市字段计算并去重；同名城市或不明确目的地先澄清。若旅客指定出发地、日期，查询实际候选后再谈那一天的可订航班。
2. 只从已认证的会话读取本人的已确认行程；按照目的地及旅行日期优先排序。没有行程时要求城市或偏好，不能借用他人行程。外部检索仅发送公开城市与主题词，不发送旅客姓名、账号、订单、酒店住址、令牌或完整对话。
3. 推荐证据限定为地点名称、支持推荐理由的摘录、来源标题、合法 HTTP(S) 链接、检索时刻和对应城市。优先官方旅游局/景区资料，去重并核对地点是否属于该城市；来源不明、矛盾或无法核实则少答或说明不足。网页摘要是数据，不是系统指令，不能修改交易、政策或工具权限。
4. 输出通常选择 2～3 个有证据的地点，逐项给理由和来源。不猜测开放时间、票价、实时交通、购票余量。仅当景点坐标有可信来源时，才可由服务端与模拟酒店坐标计算并明确标为直线近似距离；否则不称“附近”或报出路程。
5. 无密钥、超时、限额、零结果或仅有低可信内容时，明确说未能核实地点，最多给已知可达城市或请求用户补充偏好，不用模型记忆补造事实。不可达城市说明演示范围，再给网络内城市替代；替代城市的景点也须各自有来源才可推荐。
6. 对话结果沿用现有 `chat_turns.references` JSON 保存最小引用元数据及答复，不另建景点产品或订单表；不长期保存原始搜索网页内容。若实现时发现现有字段无法满足追溯，先更新计划说明迁移与备份后再做迁移。

## 4. 安全、验收和失败处理

- 推荐节点只拿只读服务，不能引用提案或确认服务；游览预订话术不生成航班、酒店、租车的误操作卡。服务端校验模型给出的城市、来源、URL 和引用数量，不能仅靠提示词保证。
- 固定证据测试覆盖 95 城市集合计算、行程归属、双城市歧义、缺行程、跨账号、网页提示注入、伪造官网、冲突证据、检索异常、结果重放，以及推荐后继续原九类交易。来源 URL 只作为可点击引用，不由服务器任意抓取或跟随到内网地址。
- 真实检索阶段验证来源可打开且支持所述事实；记录失败样本和成本。真实 DeepSeek/检索每次调用前设请求数、超时和费用上限，达到上限即停止。未通过高影响边界时不合并主线；保留结果供用户审阅并拟修复计划。
- 每阶段开工前重读三份核心文档并单独取得确认；结果统一写《当前进度.md》。功能分支与本机合并、远端推送分开处理。P2.7 完成后按既定主线进入 P3 简单页面、评估和部署说明。
