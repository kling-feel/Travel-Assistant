# P2.2：结构化动作提案操作计划

> 编写日期：2026-10-17｜用户已确认按 G-02 → P2.2 执行，并指定机票改签只补／退差价、取消收费 30%；本计划已按该要求修订。实际执行结果只写《当前进度.md》

## 目标、起点与范围

在 P2.1 合并本机 `main` 后，从干净主线建立 `<历史功能分支>`。让确定性的业务服务针对一名已认证旅客、其本人会话与真实演示订单／产品，生成并持久化一张**待确认卡**。覆盖五种动作：航班改签、航班取消、酒店预订、酒店改期、酒店取消。每张卡只代表一笔订单变更，展示操作对象、旧值、新值、模拟金额／费用、规则 ID 与版本、生成和失效时间。

本步不执行订单增删改，不开放确认或拒绝 API，不接 LangGraph／模型，不恢复旧图交易路由。智能体接入在 P2.4，逐笔确认和审计在 P2.3。P2.2 的提案入口先作为**内部服务**供测试和后续图工具调用；HTTP 仅提供登录旅客读取本人会话下动作列表及动作详情的接口。这样能验证持久化和隔离，同时避免一个临时的公开写入入口偏离最终交互。

## 建议的数据与确认卡契约

1. 新增版本迁移 `v003` 和 `pending_actions`：随机动作 ID、旅客 ID、会话 ID、动作类型、可空目标订单 ID、目标订单版本、规范化参数、旧／新快照、金额与费用摘要、规则 ID／版本、状态 `pending`、创建和过期时间，以及供 P2.3 使用的唯一幂等标识。外键、非空、类型和必要索引约束落在数据库；不保存令牌、密钥或完整模型推理文本。
2. 提案服务先核对会话归属与 `active` 状态，再按动作类型校验参数。涉及旧订单时必须核对旅客归属、`confirmed` 状态及当前版本；涉及候选航班或酒店产品时核对航线、日期、产品有效期。订单不存在和越权对外使用相同的不可见结果。规范化日期和时区后，才形成快照，避免仅展示模型原话。
3. 有效期建议为创建后 **15 分钟**，由服务端 UTC 时钟计算；读取已超时动作时明确显示“已过期”，不再把它当成可确认动作。P2.3 仍须在确认事务中复核有效期。卡片持久化后，应用进程重建仍可读取。
4. **按用户确认的机票计价**：原票价取当前机票订单 `amount`，新票价取数据库中候选航班的模拟报价。改签差额 = 新票价 − 原票价；正数显示“待补差价”，负数显示“预计退回差价”，零则无补退，额外手续费为 0。取消费 = 原票价 × 30%，模拟应退金额 = 原票价 − 取消费。所有金额都是整数演示计价单位；乘法用十进制定点数并按四舍五入到整数，避免浮点误差。卡片明确写“模拟核算，未发生支付或退款”。P2.3 确认改签时须将机票订单 `amount` 更新为新票价，并在事务内复核报价版本。
5. **补足候选航班报价**：现有匿名化样本只有两张已售机票的金额，未售候选航班没有价格。在 v003 中新增与航班一一对应的演示报价表，记录金额、规则／版本；对已有 PostgreSQL 航班做可重复的确定性回填，新演示日种子也生成相同报价。已售机票原订单金额不被回填改写。首版按样本中四种虚构航班号使用明示价目：`LH0130=6400`、`QR0055=6800`、`AF0137=6700`、`TK0081=7000`；未知航班号不猜价，禁止生成改签卡。报价仅用于演示，不声称来自航空公司；航班搜索 API 展示该报价，提案保存报价版本。这样已有 6700 的机票有补差和退差两个可演示分支。
6. 酒店预订展示每晚价 × 晚数；酒店改期展示原总价、新总价及差额；酒店取消展示原订单总价。酒店额外手续费继续为 0，取消卡不声称实际退款。所有价格和机票计算规则均由服务端执行并关联版本化演示规则，模型不得决定金额。增加明确的演示规则 v2，保留 P1 已有 v1 文档用于历史查询；迁移兼容已有数据库，种子兼容全新初始化。
7. 快照字段只包含旅客判断所需的订单、航班、酒店产品、日期与状态；金额、规则来源和“模拟交易”标识由 API 结构化输出。单张卡固定一类动作和一个目标，连锁场景后续生成两张独立卡。

## 计划修改的模块

| 模块 | 计划内容 |
| --- | --- |
| `db/travel_models.py`、`migrations/v003_*.py`、迁移入口 | 动作表、航班演示报价表、约束、索引、版本化演示规则；重复迁移可跳过 |
| `services/actions.py` 等简洁服务模块 | 五种动作的参数、归属、订单状态／版本、资源和规则校验；系统生成卡片和有效期；本人动作读取 |
| `api/travel.py` | 仅增加鉴权后的本人会话动作列表与动作详情；请求体不接受旅客 ID；无确认／执行端点 |
| `services/travel.py`、`scripts/seed_p1.py` 与演示重置脚本 | 航班搜索展示报价；现有库回填和新演示日种子产生相同的报价；重置顺序先清理动作与报价，避免外键失败 |
| `tests/`、`README.md` | 五类提案、越权和无效参数、迁移幂等、进程重建与调用示例；明确目前只读卡片、不能确认 |

## 执行顺序与检查点

1. 获得本计划确认后，再次读取三份项目文档，确认 G-02 已完成、`main` 与工作区干净；从本机 `main` 建 `<历史功能分支>`，记录起点和远端差异。
2. 先写 v003 迁移、候选航班报价与规则版本数据，检查对已有 P1/P2.1 表和重新初始化流程的影响；重复迁移不重复插入或改写已有动作／报价。
3. 实现系统生成的五类提案。调用 P1 查询与订单校验逻辑，但提案事务只写 `pending_actions`，不写机票／酒店订单。服务返回固定结构而非任意模型文字。
4. 实现本人动作查询 API，核对会话与动作的双重归属；通过服务器时间计算展示状态。可用服务层测试创建动作，再通过 HTTP 读取卡片，验证对外契约。
5. 自动化测试覆盖五类正常卡片、机票改签补差／退差／零差、取消费 30% 与整数取整、跨账号订单和会话、已取消订单、版本不符、错误日期／候选资源、过期展示、进程重建后可读，以及同一请求失败时不留下半张卡。核对订单行数、金额、版本和状态在所有提案测试前后不变。
6. 在本机 PostgreSQL 中执行 v003 首次与重复迁移，使用两个演示账号验证读取隔离和卡片持久化；检查旧图路由仍未注册。只清理本轮测试动作，不重置原始 SQLite 或演示数据；验收后停止数据库容器并保留数据卷。
7. 检查差异、敏感文件和测试结果，仅在 P2.2 短期分支创建本地提交；把实际完成、测试与遗留问题写入《当前进度.md》。是否合并本机 `main`、是否推送远端分别另立 Git 计划。

## 通过标准与失败处理

- 五类动作都能产生可读的结构化待确认卡；机票差价和 30% 取消费由服务端从订单和报价计算，展示规则版本与失效时间；不创建、修改或取消任何订单。
- 他人会话和订单无法用于提案，也无法通过 API 读取动作；无效参数不会留下动作记录。
- PostgreSQL 重启或应用重建后动作仍可读，重复迁移安全；P1 和 P2.1 回归测试通过。
- 旧 SQLite 写工具与文本 `y` 确认路线仍未重新开放；本步不调用外部模型或供应商，不推送 GitHub。

若迁移、隔离或零订单写入检查失败，留在短期分支分析和修复，不合并主线；不删除数据库卷、不覆盖原始数据。若规则金额或卡片字段在实施时需实质改变，先修订本计划并重新向用户说明。
