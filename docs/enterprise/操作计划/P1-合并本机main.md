# G-01：P1 合并本机 main 操作计划

> 编写日期：2026-10-17｜用户确认：已同意上一轮建议及本轮独立计划文档流程

## 目标与边界

将已通过 PostgreSQL 实库验收的 P1 分支 `<历史功能分支>` 快进合并至本机稳定主线 `main`，保留提交历史。此次不开发 P2、不改业务逻辑、不推送 GitHub。P1 的成果包括正式旅客和订单模型、迁移与种子、旅客身份绑定 API、内部订单服务、测试和 README。

当前已知 Git 基线：本机及远端 `main` 均指向 `fbb02bb`；P1 分支包含 `5ef5b4f` 与 `7cb5bf8`，工作区干净。合并前会重新核对这些事实；若状态变化，以检查结果为准并停止不符合条件的操作。

## 执行顺序

1. **保存本计划**：在 P1 分支提交本目录的计划与索引，让计划随项目保留。只暂存这两份文件，检查暂存清单和差异。
2. **合并前核验**：确认工作区干净，刷新 `origin/main`；确认远端无意外新提交，`main` 是 P1 分支祖先，检查待合并提交和文件清单；运行现有自动化测试与依赖检查。
3. **快进合并**：切换到本机 `main`，执行 `git merge --ff-only <历史功能分支>`。如果无法快进，立即停止，先分析差异，不执行强制推送、重置或自动变基。
4. **合并后核验**：确认 `main` 指向 P1 分支计划提交，工作区干净；复跑自动化测试，确认 `origin/main` 未变化。PostgreSQL 在上轮已完成实库验收，本次不重复重置演示数据，数据库保持停止。
5. **记录结果**：只在《当前进度.md》记录实际合并提交、验证结果、远端状态和下一步，并创建本机文档提交。结果不回填本计划，避免把事前计划和事后记录混在一起。

## 验收标准

- `git merge --ff-only` 成功；本机 `main` 包含 P1 的代码、测试、文档和本计划。
- 自动化测试通过，`pip check` 无依赖冲突，Git 工作区干净。
- `origin/main` 仍为 `fbb02bb`，没有推送行为；数据库容器保持停止。
- 《当前进度.md》如实记录结果；下一次 P2 开工前另立计划并等待确认。

## Git 与失败处理

选择快进合并，避免额外合并提交和重写既有历史。此次所有新提交仅保存在本机；后续是否推送 P1 需单独列出远端目标、提交范围并取得确认。任何检查失败时停止合并；若合并后检查失败，保留现场和失败证据，先提出修复方案，不使用 `reset --hard` 或强推掩盖问题。
