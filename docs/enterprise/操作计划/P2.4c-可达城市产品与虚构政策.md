# P2.4c：可达城市酒店、租车产品与虚构政策操作计划

> 编写日期：2026-10-18｜状态：待 G-06 完成后由用户单独确认；本文件只记录事前方案，实际结果写《当前进度.md》

## 目标与范围

在已导入的完整航线演示库上，为有 `Scheduled` 到达航班的机场生成可复现的模拟酒店、租车产品，并把旅客可查政策和交易计算统一到版本化虚构平台规则。只读核对版本化样本得到 104 个可达目的地机场、95 个不同目的地城市；城市与机场不是一对一，因此以机场为生成锚，城市作为查询维度。执行时重新计算覆盖数，以正式库与样本一致为验收前提。

建议每个可达机场生成 3 个酒店/房型产品和 2 个机场取车租车产品，基线为 **312 个酒店产品、208 个租车产品，覆盖 95 个可达城市**。产品均标明虚构，价格和位置由固定算法产生；酒店至少一个选项覆盖完整演示日期窗，其他选项可有不同房型、价格和日期窗。租车只提供搜索和政策，不创建租车订单、确认动作或旧 SQLite 租车写入；这些放在 P2.5。智能体对话和 DeepSeek 接入在 P2.6，联网景点推荐在 P2.7，本步不需要模型或检索密钥。

## 设计与拟改模块

1. **模式迁移 v007**：为酒店增加所属/邻近机场与坐标，建立正式 `rental_products` 表及按机场/城市、取还车日期检索的索引和约束。明确产品价格单位、取车地点、日期可用区间、虚构标识和生成规则版本；SQLAlchemy 表定义与迁移同步。现有巴塞尔酒店订单继续可解析。多机场同城产品按机场 ID 唯一生成，不靠城市字符串去重。坐标只用于近似直线距离，响应注明不是道路距离或耗时；不生成真实街道地址。
2. **确定性数据生成与显式重置**：以正式机场坐标和 `demo_state.as_of` 为输入，用版本化算法生成稳定 ID、酒店/房型/租车名称、机场关联、坐标、整数模拟价和可用日期。不得从航班源臆造供应商、库存或真实价格。扩展 `scripts/import_network_data.py` 的显式重置流程，保证下次平移时间窗时酒店、租车和政策同步重建，不能被旧导入器清空；保留两张演示机票及两张巴塞尔酒店订单的有效关联。正常服务启动和迁移不重置订单或会话。现阶段只表示日期可用，不展示尚未实行并发扣减的“剩余房间/车辆数”。
3. **搜索 API**：保留既有按城市和入住/退房日期搜索酒店的契约，增加受限分页及可选机场筛选/距离排序，返回坐标、距离计算基准、模拟价与可用区间；增加本人认证的租车产品只读搜索 API，可按目的地机场、取还车日期和价格筛选。校验 `check_out > check_in`、`drop_off > pick_up`、演示时间窗、城市/机场归属、限制与排序，未知地点和无供给返回空列表，不让模型补齐。现有五类交易服务必须仍以数据库产品和确认时价格/日期复核为准；如果返回的排序或 ID 改动影响旧巴塞尔产品，补齐相应兼容处理。
4. **政策唯一来源**：将本平台机票、酒店和租车规则整理成经审核的虚构政策语料，带规则 ID、版本、范围和适用条件。机票维持改签只补/退票价差、无额外改签费，取消收原票价 30%、模拟应退 70%；租车政策为取车前免费取消、取车后不得取消。酒店先维持已实现的“按晚数计价、改期按总价差、取消不收额外手续费”，不在本步凭空承诺具体退款额或新增取消时限；酒店退款档位仍需在后续交易规则确定前由用户判断。`policy_documents` 保留旧版本供历史动作引用，API 默认仅返回当前有效版本；确认服务按当前规则重新核价，旧版本卡片不得静默通过。
5. **旧 FAQ 隔离**：原 `order_faq.md` 含真实航司品牌、链接及互相矛盾的条款。建立版本化虚构知识文本，令 `tools/retriever_vector.py` 的 `lookup_policy` 只读取已审核内容；旧 FAQ 可作为历史素材保留，但不得进入 API、模型政策提示或交易规则。政策查询开放 `flight`、`hotel`、`rental`，答复可追踪 ID/版本；无匹配时明确无法确定。用规则一致性检查防止语料、数据库政策与交易常量漂移。
6. **说明与安全边界**：更新 README，说明产品纯模拟、数据如何由航线样本生成、如何备份/显式重置与重建、查询示例、直线距离局限和后续 P2.5 边界。旧 `tools/car_tools.py` 的 SQLite 写工具及旧图路由不得开放或接入新租车 API。此步不增加真实库存、预订、退款、支付或联网供应商调用。

## 执行顺序

1. G-06 完成后，开工前重读三份核心文档与本计划，核对本机 `main`、`origin/main`、工作区、演示库状态和版本。经用户单独确认，从干净主线建立 `<历史功能分支>` 短期分支。
2. 只读盘点正式库机场、城市、现有酒店/订单/政策及会话动作计数。数据库操作前保存到 Git 忽略的 `data/generated/`，用 `pg_restore -l` 验证备份可读；若有非演示账号、待确认动作或不明业务记录，停止显式重置，先报告影响并修订方案。保留现有 Docker 数据卷。
3. 先实现可单独验证的确定性产品生成器、v007 迁移和只读搜索；再更新导入器的事务性显式重置和种子兼容，使重复重置不会翻倍或留下半份产品，失败回滚。政策内容审核后再替换默认查询与检索源；更新现有确认服务的政策版本校验和文档。
4. 增加有必要的测试：104 目的地机场/95 城市覆盖、多机场同城区分、稳定 ID/价格/坐标及两日期重建、日期/分页/距离排序、未知地点、旧酒店订单兼容、政策 ID/版本和冲突语句清理、旧卡失效、跨账号与五类现有确认动作。运行全部自动化测试、编译、依赖检查及 `git diff --check`。
5. 在本机 PostgreSQL 顺序执行迁移、备份后的显式导入和 API 验收；核对 115 机场、33,121 航班、618 可订航线和 15,374 窗口内报价不退化，并核对新产品数量、城市覆盖、演示订单关联、重复导入与重启持久化。两次演示日期分别验证生成和搜索；P1/P2.1/P2.2/P2.3 实库回归顺序运行，避免测试脚本并发改写同一演示记录。验收后清理测试动作，数据库停止而数据卷保留。
6. 审阅提交清单和敏感数据，只在短期分支提交实现与必要文档；真实计数、测试结果、偏差和遗留决策写入《当前进度.md》。本步不合并本机 `main`、不推送远端；后续合并及推送另出计划。

## 通过条件与失败处理

- 104 个有 `Scheduled` 到达航班的目的地机场及其 95 个城市均有酒店和租车可搜索；建议目标是 312 个酒店产品、208 个租车产品。数量如因样本核对而改变，先解释差异，不直接放宽覆盖要求。
- 产品查询有边界、位置和价格透明；旧五类事务、两账号隔离、逐笔确认和模拟费用规则不回退。政策默认只展示当前虚构版本，历史卡片不可因规则替换而误确认，旧品牌/冲突 FAQ 不进入检索。
- 若迁移、备份、样本核对或事务性重建失败，停止后续写入并保留原数据及备份；切换后发现问题，先记录现场并给修复计划，不自动覆盖或删除用户数据。不执行 `docker compose down -v`。

用户需在 G-06 完成后单独确认本计划；如决定同时确定酒店具体退款额或变更租车规则，应先修订政策、计算和测试范围，再执行。
