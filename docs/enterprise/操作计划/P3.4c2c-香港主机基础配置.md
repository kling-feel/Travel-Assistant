## 已核对的基线

- 阿里云 Workbench 与旅客 PowerShell 首次 SSH 显示的 ED25519 主机指纹一致，专用 RSA 私钥可登录。
- 只读 SSH 检查：Ubuntu 24.04、x86_64、2 vCPU、根盘约 40 GiB／可用约 35 GiB，`ssh` 服务 active；Docker 未安装，尚无应用监听端口。
- 实际可见内存 **1,613 MiB**，当前约 1,224 MiB available，**无 swap**。它小于套餐标称的 2 GiB；现有 2 GiB Compose 三个容器限额相加为 1,536 MiB，不能把容器限额之和当成实际占用，也不能保证同时达到上限时主机不发生 OOM。后续构建、导入、恢复必须分时监测。当前不创建持久明文 swap；若实测内存不足，先暂停并选择调整限额、预构建镜像或升级规格。
- 服务器侧只读 DNS 查询：根域与 `www` 均指向所购实例；页面暂未启用 HTTPS。当前只看到 SSH 在 22 端口监听，阿里云轻量服务器防火墙规则仍需从控制台核对；不修改 80／443／5432／8000 规则。

## 操作顺序

1. 记录仅含系统版本、可用内存／磁盘、监听端口和 SSH 状态的基线。确认运行用户和目标主机身份；不把主机 IP、私钥或详细实例 ID 提交到仓库。
2. 创建专用非 root 管理用户 `travelops`，复制已核对的**公钥**到该用户的 `authorized_keys`，生成独立随机 sudo 口令并保存在本机 Git 忽略的私有凭证文件。通过新会话核对 `travelops` 密钥登录与 sudo；没有验证前保留现有 root 会话。
3. 新用户可恢复后，再在独立 SSH 配置片段中关闭远程密码与 root 登录。先运行 `sshd -t`，再 reload 服务；从新会话验证 `travelops` 可登录、root 登录受拒。异常时用保留的 root／Workbench 会话撤回片段，绝不盲目关闭唯一可用入口。
4. 只升级 Ubuntu 24.04 当前发行版内的安全／软件包索引与必要补丁，不运行 `do-release-upgrade`。检查冲突的旧 Docker 包；按 Docker 官方 Ubuntu `apt` 仓库安装 Engine、CLI、Buildx 与 Compose 插件，检查服务、版本与架构。不给 `travelops` 加 `docker` 组，因为该组拥有近似 root 权限；需要时通过 sudo 管理。
5. 核对 `docker compose version`、空闲内存／磁盘、容器守护进程监听与日志轮转设置；执行一次小型官方测试镜像或等效容器健康检查。确认 8000／5432 不对宿主机发布，应用与数据库尚未启动。若下载 Docker 官方包或镜像受网络限制，停止并记录具体错误，改用可审计的官方包路径，不运行来源不明的一键安装脚本。
6. 将真实主机结果记入《当前进度》，更新云端操作指南。只在本地功能分支提交代码／文档；主线合并和 GitHub 推送由后续单独 G 计划执行。下一检查点再准备云端私有配置、双域名跳转、数据库初始化和公网 HTTPS。
