# P3.4a：本机容器化与恢复验收操作计划

> 2026-10-25 制定并获旅客确认；实施结果见[验收记录](../P3.4a-本机容器化验收记录.md)与[当前进度](../当前进度.md)。承接[P3.4 总路线](P3.4-容器化与云部署分步路线.md)。本步只在本机隔离环境构建和验收容器，不切换当前 8000，不部署云服务器，不合并或推送 Git。

## 目标与已核对现状

当前 `compose.yaml` 只有 PostgreSQL 17.11；`main.py` 可启动完整页面和 API，`/health` 只表示进程存活。数据库连接默认指向宿主机 `127.0.0.1`，现行专用启动器固定 5436→8000 且校验新批次摘要，不能直接放入容器网络使用。`requirements.txt` 已锁定直接依赖版本；运行中所需的可信地点目录在 `data/fixtures/`，约 5.2 MB 的 `network_source.sqlite` 是可交付的虚构导入样本，`data/source/` 和 `data/generated/` 是本机原始／生成数据。现有 5436 曾异常退出，重启后校验无数据变化；根因未知。

本步验收目标：新机器可按文档在**独立 Compose 项目和卷**构建应用镜像、显式初始化模拟数据库并启动页面；停启应用或数据库后，旅客会话、已确认订单、待确认卡和审计仍一致；备份可以在另一空卷恢复。现有 8000 入口配置、5436、旧 5433 及其卷、凭证和备份均不作为试验目标。规划时本工作台未检测到 8000 监听，实施前必须重新确认实际状态。

## 按顺序执行

1. **开工核对**：重读三份核心文档、本计划和 P3.3c2 验收；检查 Git 分支与工作区、Docker 引擎、现有 8000／5436／5433 的监听和容器身份、现有备份是否仍在。只读取配置的键名、是否设置及目标类型，不在输出中暴露值。若 Docker 在工作台不可用，先核对普通 PowerShell 的能力；确实必须由旅客执行的命令再逐条给出。记录候选隔离端口，建议 API 8018、数据库 5440，但执行前检查空闲，不能占用当前演示入口。
2. **建立独立代码线**：从当前 `main` 建非公开功能分支，保持工作区起点清洁。实施期间只提交本功能分支；不合并 `main`，不推送 GitHub。若开工有来源不明的改动，先核对并保留，不混入容器化变更。
3. **构建应用镜像**：新增清楚的 `Dockerfile`、`.dockerignore` 和本机容器运行配置。镜像使用已核对的 Python 基础镜像与锁定依赖，应用进程以非 root 身份运行，统一容器工作目录；页面静态资源、已审核地点目录和运行时用于核对推荐覆盖的 **5.2 MB 脱敏虚构样本**进入镜像。只有显式初始化命令能把样本写入新数据库；正常启动只读该样本，不导入。原始 SQLite、`data/source/`、`data/generated/`、`.env`、虚拟环境、Git 历史、备份、日志和测试凭证不得进入构建上下文或镜像。构建后检查镜像中文件、运行用户及镜像体积，避免仅依赖 `.gitignore`。
4. **拆分启动职责**：让容器内应用通过独立 `DATABASE_URL` 连接 Compose 网络中的 `db`，监听容器网络地址；保留现行 5436→8000 专用守卫给本机原入口使用，不削弱批次身份核对。迁移和导入作为**一次性显式命令**，先核对目标项目、卷、数据库空状态与批次日，再生成新模拟批次；普通 `up`、API 重启和数据库重启均不能再次导入或重置。初始化失败时停止，保留卷与日志供核查，不对非空库重跑恢复或导入。
5. **运行配置与健康**：Compose 的隔离项目提供数据库命名卷、数据库健康检查、应用依赖数据库就绪、应用存活与数据库就绪检查以及清楚的重启策略。API 映射只绑定本机回环地址；数据库仅限 Compose 内部访问，确需本机验收端口时只映射至回环地址。凭证用 Git 忽略的独立环境文件，在日志中只输出脱敏目标。就绪检查不能把“进程活着”等同于“数据库可处理请求”；先验证异常数据库目标会拒绝服务，而不会静默连接旧库。
6. **隔离初始化与验收**：用新 Compose 项目／新卷和新 JWT、数据库及演示账号凭证，先备份空库，运行现有迁移与虚构样本显式导入，核对 13 版迁移、演示基准日、115 机场、33,121 航班、618 可售航线及酒店／租车覆盖。用 8018 页面和 API 验证登录、本人行程、会话、来源约束推荐、未登录拒绝、跨账号拒绝；抽查航班、酒店、租车三类待确认卡与逐笔确认。真实 DeepSeek／阿里云搜索不是容器持久化证明所必需，默认不产生付费请求；若启动时发现必要的联网配置缺失，按功能降级记录，不向聊天索取密钥。
7. **重启与恢复演练**：先在隔离库创建会话、卡片及一笔已确认模拟订单，记录不含密码的业务摘要；分别重启应用、数据库及整个隔离 Compose 项目，核对登录、消息、卡片有效期、订单版本、审计和供给摘要。容器重启策略采用明确的正常停止／异常退出试验，记录 Docker Desktop 关闭时的实际表现，不声称它能覆盖主机断电或引擎故障。执行自定义格式备份并校验头、目录、哈希；在**另一个全新卷**恢复一次，对比业务摘要。备份或恢复不通过，本步不验收。
8. **回归、文档与收尾**：跑必要的容器配置检查、部署定向测试和完整业务回归；复核构建上下文、镜像、Git 跟踪树、日志无凭证或本机路径泄露；更新 README 的本机容器启动、停止、备份、恢复和故障排查说明，另写验收记录并同步《当前进度》。隔离试验结束仅停止验收容器，保留卷和备份，不执行 `down -v`。再次只读核对当前 8000／5436 与旧 5433 未被改动。完成后只在功能分支提交，公开合并和 GitHub 同步另拟 G-19 计划。

## 失败停止点与回退

- 端口、容器标签、挂载、批次身份或凭证目标与预期不符：停止初始化或试验，查明实际对象；不得凭端口号终止来源不明的服务。
- 非空隔离库、迁移失败、镜像包含密钥／原始库、未确认订单发生变化、跨账号可读、重启丢会话／订单、恢复摘要不一致：停止本步验收并记录证据；保留隔离卷和备份以排查，当前 8000 演示继续按原方式运行。
- Docker Desktop 停止、工作台无法连接 Docker、镜像拉取失败：记录具体阶段和错误。只有必须在普通 PowerShell 执行的操作才请旅客代运行；不要求旅客发送 `.env`、账号密码、数据库文件或密钥。

## 完成标准与后续决策

通过时须同时有：隔离页面和 API 可用、完整业务回归通过；镜像不含敏感或原始数据；明确初始化不会在重启时重复运行；会话、订单、动作和审计经重启保持；备份在新卷实际恢复；现有 8000、5436 和旧 5433 保持原状态。记录容器异常退出是否复现及所能解释的原因；未定位时列为运维风险，不宣称已根治。

随后再向旅客展示 P3.4b 的云厂商／地域、月预算和访问范围选项，核对当时官方规格与价格后制定云端实施计划。P3.4a 的确认**不授权**云资源购买、公网开放、覆盖现有卷、切换 8000、合并 `main` 或推送 GitHub。
