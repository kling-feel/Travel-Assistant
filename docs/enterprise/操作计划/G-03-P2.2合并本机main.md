# G-03：P2.2 合并本机 main 操作计划

> 编写日期：2026-10-17｜性质：待用户确认的事前计划；实际结果只写《当前进度.md》

## 目标与当前基线

把已通过 13 项自动化测试和 PostgreSQL 实库验收的 `<历史功能分支>` 快进合并到**本机** `main`，作为 P2.3 的稳定起点。计划编写时，P2.2 实现提交为 `f7b82f0`，本机 `main` 为 `ae92228`，已知 `origin/main` 为 `fbb02bb`；计划文档的本地提交会改变 P2.2 分支末端提交号，执行时重新核对。当前工作区干净。

本次只做本机 Git 合并及核验；不推送 GitHub，不开发 P2.3，不重置 PostgreSQL、匿名化样本或 Docker 数据卷。v003 已在本机演示库应用，数据库容器目前停止；纯 Git 合并无需再次运行种子。

## 执行顺序

1. 重读《产品需求》《软件架构》《当前进度》和本计划；核对当前分支、未提交文件、`main`、P2.2 分支与 `origin/main` 的提交号。
2. 执行 `git fetch origin` 刷新远端信息。若远端 `main` 有新提交，先展示差异并暂停，重新制定安全合并方案；不自动拉取、覆盖、变基或强推。
3. 确认本机 `main` 是 P2.2 分支祖先，列出待合并提交和文件清单；检查没有 `.env`、原始大型 SQLite、生成 SQL、真实密钥或临时数据。运行 13 项自动化测试、Python 编译及 `pip check`。
4. 切换到本机 `main`，执行 `git merge --ff-only <历史功能分支>`。不能快进时立即停止分析，不擅自创建合并提交或重写历史。
5. 合并后核对 `main` 等于 P2.2 分支末端、工作区干净、`origin/main` 未变化；复跑自动化测试。明确标记：P2.2 只会生成和读取待确认卡，确认执行仍未实现。
6. 只在《当前进度.md》记录实际提交号、检查结果、远端与数据库状态，并创建本机文档提交。P2.3 若随后获准，必须从这个文档提交后的干净 `main` 建短期分支。

## 通过标准与失败处理

- 本机 `main` 线性包含 P2.2 的迁移、报价、动作服务、API、测试及文档；工作区干净，回归测试通过。
- `origin/main` 不被修改；PostgreSQL 容器和数据卷不因本次合并发生变化。
- 《当前进度.md》只写实际结果，不把待确认卡误称为已可执行交易。

前置检查失败则不合并。合并后检查失败时保留现场和失败证据，先提出修复方案，不使用 `reset --hard`、自动变基或强推。只有用户确认本计划后才执行上述 Git 操作。
