# P3.1e6：正式演示库排程更新操作计划

> 2026-10-22｜事前计划，等待用户确认。本计划只供审阅，未授权执行数据库重建、本机 `main` 合并或 GitHub 推送。

## 1. 目标与现状

P3.1e5 的新虚构时长规则、落地酒店供给和页面时间展示已在独立 PostgreSQL 数据库验证，但默认正式演示库仍是基准日 2026-10-20 的旧航班到达时间。代码发布后旧库不会自动改变；直接使用正式页面可能继续显示不合理的上海至伦敦时长。下一步建议在用户确认后，先保存旧库完整快照，再把正式库整体重建为执行当日的演示日期，并复核真实页面。

2026-10-22 只读盘点：33,121 条航班、2 张机票订单、2 张酒店订单、0 张租车订单；8 个会话、135 条消息、6 张历史动作卡（2 已确认、4 已拒绝）、2 条动作结果和 12 条审计事件，**没有待确认动作卡**。执行时必须重新盘点，以当时数据为准。

## 2. 明确影响和备份

重建会替换正式演示库中的两个示例账号和所有航班、报价、酒店、租车及政策数据，并清除现有订单、8 个会话对应的聊天／图检查点、动作卡、结果与审计，重新生成 2 张机票和 2 张酒店基础订单。旧账号密码从本机 `.env` 再生成哈希；不会读取、输出或上传密钥。上面的数量只是当前盘点，执行前若新增会话或动作，须展示新数量。若发现非演示账号或仍待确认的卡，停止重建，先让旅客处理。

完整 `pg_dump -Fc` 备份保存到 Git 忽略的 `data/generated/`，检查文件头、体积和 `pg_restore -l` 目录；备份可能含账号哈希、聊天、订单和审计，只在本机保留。执行前记录默认 Compose 项目、端口 5433 和 API 端口占用，停止或暂时隔离连接正式库的 API，避免重建时继续写入。不得删 Docker 卷，也不对备份执行覆盖写入。

## 3. 拟执行顺序

1. 重读三份核心文档、P3.1e5 验收记录和本计划，确认功能分支提交、工作区、Docker Desktop、正式数据库项目与端口。只读复盘基准日、账号、订单、会话、动作状态和源样本校验值。
2. 创建带时间戳的正式库完整备份，在容器内和本机分别核查，并记录恢复所需的数据库项目、版本和文件名。先运行导入预览，核对将导入的 115 机场、33,121 航班、15,374 报价、618 可订航线。
3. 在确认无未处理动作和非演示账号后，明确执行一次 `--apply --reset-demo --backup`，以执行当日作为 `--as-of`。导入脚本在单一事务中替换数据；失败时回滚，备份仍保留。
4. 将现有仅允许隔离端口的 P3.1e5 审计脚本扩展出需显式指定的正式库只读模式，保持默认拒绝误连正式库；然后运行完整航线核验、全量排程审计、跨洲和窗口末端酒店查询、账号隔离以及一段机票＋落地酒店对话。对正式库的验收操作如会生成新卡，应使用测试会话并明确记录或清理；绝不代旅客确认真实页面的动作。
5. 在桌面和窄屏页面核对出发／到达当地日期、偏移、金额、酒店两晚和确认前订单不变。若需真实 DeepSeek 和阿里云调用，提前记录请求次数；本阶段规则和对话意图未变，优先使用固定模型，只有页面证据不足时做少量真实调用。
6. 将备份、重建前后计数、失败及回退情况写入《当前进度》与验收记录。通过后再单独更新 G-16 合并与 GitHub 同步计划，待用户再次确认。

## 4. 停止与回退

备份不可读、端口／项目不符、出现非演示账号、仍待确认卡、正式库在操作中有新写入或导入后航班 ID／出发时间／报价变化，立即停止。若导入事务失败，先检查数据库是否保持旧快照；若已成功提交但验收失败，停止 API，使用本次备份恢复到独立数据库验证后，再决定是否恢复正式库。不得在未核验备份和用户未确认的情况下覆盖正式库或推送 GitHub。

## 5. 需要用户确认的取舍

建议选择**备份后整体重建**，让航班到达日、酒店供给、基础订单和会话状态属于同一规则版本。确认此计划即同意上述旧演示会话与历史记录在正式库中被清空、只保留本机备份；G-16 本机主线合并和 GitHub 推送仍须另行确认。
