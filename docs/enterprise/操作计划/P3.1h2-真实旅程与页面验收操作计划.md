# P3.1h2：真实旅程与页面验收操作计划

> 制定日期：2026-10-23｜状态：已按用户确认执行，部分通过且发现发布阻断；结果见[独立验收记录](../验收记录/P3.1h2-真实旅程与页面验收记录.md)。本计划不授权修改正式演示库、接管 8000 服务、合并本机主线或推送 GitHub。

## 1. 为什么需要这一轮

此前用户在旅客页面记录了连续订票失败、跨话题丢条件、取消范围识别不准、已取消订单混入当前行程、国家目的地卡住、附近景点不承接所在地，以及答复等待体验差等真实问题。P3.1e、f、g、h1 已分别提交修复：目前有 218 项自动化测试通过；隔离环境做过部分真实模型、数据库重启和桌面／窄屏验收。但最新流式页面只做过一轮真实模型对话，且该轮未开启联网检索；不能据此认定原先的整段用户旅程都已解决，更不能断言用户正在打开的 8000 页面运行的是当前功能分支。

本轮目标是用**同一版本、同一隔离数据库、真实旅客页面**连续走完原失败话术和交易闭环。记录每轮用户原话、服务端理解的目标与条件、实际候选、待确认卡、订单前后状态和页面结果。只把有逐轮证据的项目判为通过；发现缺陷就列出可复现步骤和修复计划，暂不进入 G-16 发布。

## 2. 事前核对与环境隔离

1. 开工前重新打开《产品需求》《软件架构》《当前进度》及本计划，核对功能分支、工作区、最新提交、密钥配置状态和 8000／正式数据库端口。仅检查密钥是否配置，绝不输出密钥内容。读取 8000 的健康与版本信息；若不能确定运行提交，就明确标记“未知”，不把旧页面现象当成新分支验收结果，也不停止用户自己的进程。
2. 使用独立 PostgreSQL Compose 项目、独立命名卷及独立 API 端口。建议数据库宿主端口 5435、页面 8014；先检查占用，再确定实际端口。旧的 `travel-ui-acceptance` 卷保持原状；正式 5433 数据库、8000 页面、原 SQLite 不重置、不导入、不确认测试卡。若工作台无法调用 Docker，由用户在普通 PowerShell 按届时提供的逐条命令启动隔离容器，并回传不含秘密的状态；此条件未满足时，PostgreSQL 重启项标为未测，不能用 SQLite 代替。
3. 在隔离库迁移、导入可复现虚构供给并创建一次性旅客甲／乙。固定验收开始日，同时依据出发与到达机场的当地时区计算“明天”“最早”“落地当天”；不沿用旧聊天中已经过时的具体日期。测试账号、原始对话、截图、调用明细与数据库备份仅保存在 Git 忽略目录，公开文档只记录脱敏结论。
4. 先用固定模型回放确定性边界，再用现有 DeepSeek 和默认开启的阿里云 `GlobalBasic` 走真实旅程。计划上限为 30 次 DeepSeek 请求尝试、15 次搜索请求尝试；逐次计数并记录模型 token 与服务商可查费用。模型费用达到人民币 8 元即停止后续模型调用；`GlobalBasic` 的专属单价未显示，不能承诺联网费用的人民币上限，因此同时用次数限制并观察账单异常。预算或调用上限达到时未完成项标为未测，不写成通过。无需用户在聊天中提供任何密钥。

## 3. 按用户原话执行的旅程

### A. 连续订票与任务记忆

从“我要去伦敦旅行，帮我购买机票”开始，分轮补“我在上海”“明天出发，没有就最早”“我要去伦敦”“订最早那班”。核对助手只追问真正缺少的条件，保留城市、日期下界和预订目标；无明天直达班次时展示窗口内实际最早可售班次，不能把推荐日期当已订机票。唯一候选可生成**正确航班的待确认卡**，确认前订单数不变。接着说“预订前面说的机票，顺便找落地酒店”，核对机票卡与酒店追问分别推进，落地机场及当地到达日来自该班次。穿插天气或景点话题后，再问“我们刚才说到哪了”，核对只回顾本会话已确认的条件和卡状态；另开会话不能继承旅客自述所在地或旧候选。

### B. 国家目的地、当前位置与推荐

先自述“我在伦敦”，随后要求“从这里去中国，订最早的机票”。助手应说明伦敦来自本会话自述，按实际模拟可售直达班次列出最多五座中国城市和各城最早班次；实际供给不足五城就如实显示，不能补造城市。选城市后重新核价，唯一班次只生成待确认卡。“我周围有什么景点”用唯一可信自述城市给城市级、有来源的中文地点；出现所在地与航班目的地两种合理解释时才澄清，不宣称精确距离。中国城市天气只在官方页面核验城市、日期和发布时间后回答；境外天气按已确认范围说明无法核实，不调用未经验证的网页摘要报温度。阿里云搜索超时或资料不足时应明确降级。

### C. 当前行程、取消与交易边界

用隔离旅客的有效机票、酒店、租车订单询问“最近有什么行程”。答复须用中文起终地点、两端当地时间、状态，默认完全排除已取消订单；只有明确询问历史才列出已取消记录。分别提出“取消汉堡机场出发的航班”“保留伦敦，其余行程取消”“取消所有酒店”：只筛本人有效订单，先列保留／拟取消／不可办理项目；多笔或跨城含糊时给具体选项，每轮最多两张独立卡。只确认一张后复核其余订单仍有效；放弃、过期、重复确认与报价／规则变化不得多写。页面中待确认、已确认、已取消历史须有文字和视觉双重区别。

### D. 机酒车完整动作与页面反馈

在固定模型和 API 层回归机票预订／改签／取消、酒店预订／改期／取消、租车预订／改期／取消九类动作。真实模型页面重点走订票、落地酒店两晚、最高价房型、租车取还车当地时刻和逐笔确认／放弃。核对金额、时间、规则与数据库一致；模型或搜索文字不能替旅客点击确认。

桌面与约 338 像素窄屏实际检查：发送后先出现旅客原文；等待态与经过时间真实，不伪装模型内部推理；核验并保存后答复逐段出现；来源、候选与卡片在完成后加载。刷新、断线、切换会话及原请求键重试只保留一条用户消息、一组提案，旧流不能写进新会话。短答可立即结束，不人为延迟。页面不得横向溢出，键盘操作和减少动画偏好可用。

## 4. 故障、权限与恢复

1. 旅客乙尝试读取、选择或确认旅客甲的会话、候选及卡片时必须拒绝；同一请求键换文本、跨会话重放也必须拒绝。外部网页和模型输出中的指令、脚本片段只作为不可信数据，不能修改政策、订单或页面结构。检查 API 与脱敏日志无密钥、令牌、内部推理或他人订单泄露。
2. 人为造成模型失联、搜索失败、候选过期、报价变化、网络断开与重复提交，核对页面明确告知状态，且没有错误对象卡或未经确认写入。
3. 在隔离库保留一张待确认卡及一笔已确认订单后，依次重启独立 API 和独立 PostgreSQL 容器；重新登录后核对会话、检查点、卡、订单、审计一致。保留独立卷供复核；收尾仅停止本次 API 与容器，不删除卷。

## 5. 判定、交付与后续

逐轮报告分为通过、失败、未测，记录版本、日期、隔离端口、实际供给、预期／实际状态、卡和订单前后值、模型及搜索调用数和可查费用。**发布阻断项**包括：明确订票请求卡在重复追问；错误城市、日期、产品或金额的卡；取消范围误选；普通行程泄露已取消目的地；未经逐笔确认写入；越权读取；模型／检索无证据却给肯定事实；断线重试重复建卡；真实页面无法完成核心旅程。出现任一阻断项，先保存脱敏证据、更新《当前进度》并另拟修复计划；不把 HTTP 200、自动测试通过或单轮模型成功当作整体通过。

通过标准为 A～D 核心旅程、交易和恢复均有真实页面及数据库证据，九类动作与权限边界的固定模型回归通过，完整自动化套件及 Python／页面脚本／依赖／差异检查通过。结果同步《当前进度》，必要时更新产品需求、架构和本机操作指南；只在功能分支提交公开安全的文档与代码。随后重新审查 G-16 并**单独**提交本机主线合并和 GitHub 同步计划供用户确认。本计划本身不执行合并或推送。
