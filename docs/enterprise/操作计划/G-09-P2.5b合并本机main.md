## 执行顺序

1. 重读《产品需求》《软件架构》《当前进度》及本计划；查看 `git status`、分支/提交图、`main...HEAD` 清单和本轮文档差异。仅将 G-09、P2.5c 事前计划、索引和本次规划记录暂存，在 P2.5b 分支单独提交。先过 `git diff --check`；遇到未知修改先查明，不顺带提交或覆盖。
2. `git fetch origin` 并复核 `origin/main`。若远端已偏离上次核对的 `fbb02bb`，先说明变化和影响，暂停合并；不自动 `pull`、变基或强推。再次确认本机 `main` 仍是分支祖先、工作区干净，合并可快进。
3. 审阅 v009 表/约束、租车计价与机场当地时间转换、夏令时边界、取车前模拟退款、本人归属、两卡并发、行程读取、政策版本、重置清理及 README。核对未改写 v001～v008、未把 `.env`/私有配置/备份/数据库文件纳入提交，旧图路由未注册。合并前运行全部自动化测试、2026-10-17 和 2026-11-01 离线样本校验、Python 编译、`pip check`；实库验收沿用 P2.5b 已记录的结果，不宣称本步骤重新验证数据库。
4. 检查全部通过后切换本机 `main`，执行 `git merge --ff-only <历史功能分支>`。不能快进时停下分析，不制造合并提交或改写历史。
5. 合并后确认 `main` 与审阅的分支末端一致，复跑自动化测试、两日期离线校验、编译/依赖和旧路由检查。把实际提交、结果、数据库未触碰及下一步写入《当前进度.md》，在本机 `main` 单独提交结果记录，最后检查提交图和工作区。

## 通过条件与失败处理

- 本机 `main` 线性包含 P2.5b 及本轮两份计划；合并前后离线回归通过，旧图路由仍关闭。
- PostgreSQL 容器、卷、备份与远端 `main` 不因 G-09 改变。P2.5c 必须另获确认才开始。
- 合并前检查失败，留在原分支排查；合并后检查失败，保留现场并提出修复计划。不执行 `reset --hard`、强推或 `docker compose down -v`。

用户确认 G-09 后才执行。远端推送需要另拟计划并单独确认。
