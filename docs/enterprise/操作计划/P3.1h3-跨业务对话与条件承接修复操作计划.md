# P3.1h3：跨业务对话与条件承接修复操作计划

> 制定日期：2026-10-23｜状态：待用户确认。此计划只授权功能分支修复与隔离验收；本机 `main` 合并和 GitHub 同步仍需另行确认。

## 1. 目标与依据

依据 [P3.1h2 验收记录](../验收记录/P3.1h2-真实旅程与页面验收记录.md)，真实旅客说“预订刚才最贵的那辆车”时，助手错误沿用旧航班候选；租车自然时刻和落地酒店晚数又被重复追问。本步保持既有旅行助手框架、确认卡协议和简明代码风格，修复以下四点：**本轮业务类型锁定、同类候选承接、用户时刻／晚数承接、最终文案去重**。价格、政策、订单归属和确认仍由服务端核对。

## 2. 开工前与数据保护

1. 再读《产品需求》《软件架构》《当前进度》及本计划；核对功能分支、工作区、当前提交和 8000／正式数据库状态。只在功能分支修改代码、测试及文档；不覆盖用户正在使用的页面。
2. 固定重演 P3.1h2 的原句和预期对象，检查对话图的任务上下文、模型输出、候选集合、服务端提案守卫和页面最终回复。保留失败基线，先找到根因再改动。
3. 复用隔离验收库前确认端口与现有备份，或新建独立库；不重置正式演示库。测试账号和真实模型原始响应仅保存在 Git 忽略目录。

## 3. 实施步骤

### A. 交易业务类型与候选隔离

- 从旅客本轮明确文字及当前同类任务状态确定可写动作集合；模型建议若属于其他业务，如租车话语给出 `flight_book`，不得进入旧航班候选验证，也不得展示旧航班列表。返回贴合本轮租车任务的澄清，记录不含隐私的拒绝原因。
- 候选按航班／酒店／租车分别保存有效范围、查询条件和产生时刻。“刚才最贵的那辆车”只在有效租车候选中按服务端价格唯一选择；候选过期、报价变化、并列最高或城市／日期改口时重新查或要求明确选择。不能跨会话引用旧候选。
- 对“订”“取消”“改期”等明确意图维持现有逐笔确认；模型和搜索结果不能直接修改订单。跨领域请求可以拆为独立子任务，但各卡只绑定各自证据。

### B. 日期、时刻与酒店晚数

- 解析“明天 10 点取车、大后天 18 点还车”、`10:00/18:00`、上午／下午等自然表述；按取还车地点当地时区组成完整时刻，遇到不存在或有歧义的当地时刻才追问。不从模型补出旅客未说的时间。
- 在同一租车任务内合并先前明确的地点、日期、时刻和价格偏好；切换至航班或酒店后再回到租车时，只复用未过期、无矛盾的租车条件。
- 已有唯一航班卡且旅客说“落地附近酒店、住两晚”时，以该班当地到达日为入住日，退房日为入住加两晚；地点仍以实际落地机场／城市核对。只有航班卡不唯一、时区日界或旅客给出冲突日期时再问。现有机票确认卡不因酒店查询自动确认。

### C. 答复与页面

- 在最终答复中只保留一次卡片数量、待确认提示和政策摘要；多张卡逐张列清对象，不把旧查询结果拼到无关交易。页面卡片加载与立即显示旅客消息、真实等待态、核验后流式答复保持一致。
- 保留已取消订单默认从普通行程和推荐上下文排除、明确问历史才显示的现有规则。若本轮发现它被跨业务修复破坏，作为同一回归立即修正。

## 4. 验证与交付

1. 先做固定模型和 API 回归：原失败话术、`10 点` 与 `10:00`、两晚、最贵／并列、过期候选、跨会话、航班和租车交叉、报价变化、取消已确认订单以及重复请求键；断言每轮候选和提案类型、对象、金额、订单前后值。完整自动化套件与页面脚本语法、Python 编译、依赖及差异检查通过。
2. 再在独立页面用真实 DeepSeek 重演至少两条核心链：上海至伦敦机票→落地酒店两晚，上海租车→最贵车辆→待确认卡。阿里云搜索只在推荐／中国天气需要时调用。为真实测试建立本地逐请求计数、token 和已知费用记录；模型最多 20 次尝试、搜索最多 10 次，模型累计估算达到 ¥8 即停止，搜索单价未知则按次数硬停。原始密钥和模型响应不写公开文档。
3. 追加独立记录，逐轮标通过、失败或未测；修复失败要继续处理，不以“模型偶尔答对”作通过。同步《当前进度》和必要的架构说明，在功能分支提交公开安全的改动。随后再规划 P3.1h2 未测的多笔条件取消、故障注入、宽屏／窄屏验收。**G-16 本机合并与 GitHub 同步仍另列计划并等待确认。**

## 5. 完成标准

上述原话在独立真实页面不再串到其他业务，不重复追问已明确的时刻或晚数；机票、酒店和租车分别只生成正确待确认卡，确认前不写订单；模型误判时服务端仍阻止错误卡；自动化及安全边界均通过，付费调用有可核对的计数记录。若任一条件未满足，本步继续修复，不申请主线发布。
