# P3.2c2：配置、数据库与通用模块归位操作计划

> 2026-10-24 制定｜状态：旅客已确认，本地功能分支已实施；结果见[当前进度](../当前进度.md)。承接已完成的 [P3.2c1](P3.2c1-项目路径与页面资源归位.md) 与 [P3.2c 分步路线](P3.2c-应用目录归位分步路线.md)。

## 1. 目标与当前依赖

P3.2c1 已建立 `travel_assistant/paths.py`，页面资源原样归位。下一步把根目录的 `config/`、`db/`、`utils/` 共 9 个 Python 文件收进应用包，使配置、正式数据模型、会话依赖、密码哈希及 HTTP 通用处理的位置可一眼辨认。当前仍有约 130 处相关导入分布在启动、API、助手、服务、迁移、脚本和测试里；直接移动而不改调用方会使应用启动失败。

建议映射如下，文件名尽量沿用原意，避免在搬迁时同时重写业务：

| 现位置 | 目标位置 | 处理 |
| --- | --- | --- |
| `config/__init__.py`、`config/log_config.py` | `travel_assistant/core/config.py`、`travel_assistant/core/log_config.py` | 保留 `Settings`、`settings`、`init_log` 的行为；`.env` 继续由 `PROJECT_ROOT` 定位 |
| `utils/cors.py`、`handler_error.py`、`password_hash.py`、`dependencies.py` | `travel_assistant/core/` 同名文件 | 保留 CORS、异常响应、密码校验和数据库会话关闭语义 |
| `utils/__init__.py` | `travel_assistant/core/__init__.py` | 只保留包标记，不承载隐式副作用 |
| `db/__init__.py`、`db/travel_models.py` | `travel_assistant/db/` 同名文件 | 保留引擎创建条件、表定义、约束和元数据对象 |

根目录 `main.py`、`api/`、`graph_chat/`、`services/`、`migrations/`、`scripts/`、`tests/` 在本步仍保留原位置。其使用方需同步改为新导入路径，但不移动它们。数据库迁移的现有版本文件只允许改 Python 导入语句；**版本 ID、次序、升级 SQL 和表定义不得因本步变更**。迁移记录按版本 ID 判断已应用状态，不能用新路径生成另一套迁移历史。

## 2. 确认后的执行顺序

1. 重读《产品需求》《软件架构》《当前进度》及本计划，确认本地功能分支 `dc036ce` 之后没有其他未提交业务改动。盘点九个待移动文件、全部静态／动态导入、测试中的字符串补丁目标、迁移版本和 README 已公开命令。记录 230 项完整测试、31 条路由、数据模型表与列的结构摘要，作为搬迁前基线。
2. 在 `travel_assistant/core/` 和 `travel_assistant/db/` 建立清楚的包结构，按上表移动实现，保持配置从根 `.env` 加载。对内部代码、13 个迁移版本、当前脚本和测试进行机械式导入更新；字符串形式的 `patch(...)` 目标也须核对。不得创建同名根目录兼容包装以掩盖遗漏，也不得顺手重构认证或交易逻辑。
3. 从根目录及非项目工作目录分别导入 `main.Server`、配置、数据库模型与当前脚本模块，核对注册路由、CORS、异常处理、`get_db` 和原 `.env` 定位。只读比较移动前后的表名、字段、约束和迁移版本列表；不连接正式 PostgreSQL 运行迁移。
4. 先跑配置／数据库／身份／接口定向测试，再跑完整自动化、两日期全航线样本核验、Python 编译、页面脚本语法和依赖检查。核对 README 中现有 17 个脚本入口仍在、迁移及导入脚本可导入、`/app` 与静态资源仍能通过内存客户端读取，检查所有本地 Markdown 链接和 Git 差异。
5. 通过后删除空的根 `config/`、`db/`、`utils/` 文件夹，更新 README、软件架构和脚本索引中有关当前位置的说明；历史计划及验收记录正文保留。把实际映射、测试数和证据边界写入《当前进度》，只在当前本地功能分支提交。之后另给 P3.2c3 的独立计划。

## 3. 验收、停机与 Git 边界

- `python main.py`、README 中的迁移／导入／核验命令及完整测试发现命令仍可从项目根运行；API 路径、响应契约、页面资源 URL、九类动作和确认边界不变。
- `.env` 的读取位置、配置缺失时的报错、数据库连接目标、SQLAlchemy 元数据结构和全部迁移版本保持一致。仅移动 Python 文件及更新导入，不运行 `migrate.py` 或导入／重置脚本。
- 若发现字符串导入、循环依赖、模型元数据差异、迁移版本变化、路由数量变化或完整回归失败，先停在本步修复；不能带着旧根包与新包并存的半迁移状态进入 P3.2c3。若范围必须扩大，先修订计划再确认。
- 本步不启动或写入正式／隔离 PostgreSQL，不改变演示日期、订单或数据样本，不调用付费模型或联网搜索，不触碰用户 8000 页面。提交只在当前功能分支；本机 `main` 合并和 GitHub 推送仍需 G-17 单独确认。
