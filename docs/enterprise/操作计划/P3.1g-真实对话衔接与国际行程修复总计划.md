# P3.1g：真实对话衔接与国际行程修复总计划

> 制定日期：2026-10-22｜状态：三项产品规则已由用户确认；P3.1g1 已单独确认并实施，g2～g4 待各自计划与确认。本文不授权后续业务代码修改、正式数据库写入、合并本机 `main` 或推送 GitHub。

## 1. 背景、基线和发布判定

用户在 8000 页面连续对话时发现：当前行程摘要缺起终点；“我们前面说过了什么”未进入回顾；自述在伦敦后“周围”景点仍要求城市；“从伦敦到中国、订最早机票”反复索要出发地和目的地，无法前进；境外天气只返回覆盖限制。两张取消待确认卡的生成本身符合逐笔确认协议，但在切换话题后还需清楚表达其状态。

当前功能分支为 `feature/p31-traveler-ui`，计划制定时最近提交 `63df78b`，工作区干净；本机 `main` 和上次保存的远端基线尚未合并本分支。计划期间当前工作台连接不到 8000 服务，无法证明用户贴出的页面当时加载哪一版 Python 进程。首步将只读核对进程和版本，不能把代码预期当成 8000 的实测结果；若服务已关闭，则用独立预览和相同对话复现。用户的 8000 调试进程及正式演示库不得为了版本检查被停止或重建。

这些真实使用缺陷作为新的 G-16 发布阻断项。此前完成的 200 项自动化测试和独立数据库恢复验收继续有效，但不能替代本轮跨话题、国家目的地和自然表达的验收。

## 2. 用户已确认的产品规则

1. **国家目的地**：旅客说“从伦敦去中国、订最早的机票”，同一会话明确自述的伦敦可作为出发地，且答复注明“按你先前自述在伦敦”；中国先作为国家范围。服务端从伦敦全部出发机场、演示可售直达航班和 30 天窗口查中国目的地城市，每城取实际最早可售班次，按起飞绝对时刻排序，最多列 5 座供旅客选择。国家、城市映射来自受控机场地理资料；没有可售班次就说明范围和空结果，不凭通用城市推荐目录补航班。选定城市后重新查询路线、日期、报价和可售；原先明确“预订最早”且唯一最早班次时才可生成该班待确认卡，并列则再选班。仅说“中国”时绝不自行选择城市或写订单。
2. **自述所在地**：只在同一会话将“我在伦敦”保存为旅客自述，不冒称设备定位。后续机票、天气和城市级地点查询在语义明确时谨慎复用；旅客改口覆盖旧所在地，存在“当前所在地／航班目的地”两个合理锚点时定向澄清。新会话不继承自述位置。
3. **境外天气纳入本轮，并严格核验**：阿里云联网搜索可以帮助发现公开资料，但不能把搜索摘要或模型文字直接当作天气事实。先研究可合法使用、覆盖演示境外城市且有城市、当地目标日、发布时间和来源可复核的预报数据接口或官方页面，再就接入方式和新增密钥单独请用户决定；来源不可用时继续明确无法核实。

## 3. 缺陷清单与修复边界

| 编号 | 缺陷及目标 | 核对点 |
| --- | --- | --- |
| D15 | 国家目的地无法变成可选择的实际可售城市，跨轮订票卡住 | 航班候选必须由当前演示库、城市国家映射和 30 天窗口支持；不能自动选城市或虚构中转 |
| D16 | 所在地已记住却不稳定地服务下一任务 | 保存字段来源、会话作用域、改口和歧义；不得把自述当设备位置 |
| D17 | “周围／周边／附近”等表达分流不一致 | 使用可信自述城市给城市级地点；无精确坐标时不声称距离最近 |
| D18 | 行程简报省略中文起终点、到达时刻与状态 | 由本人有效订单生成一致的概要；已取消仅在明确查历史时出现 |
| D19 | “我们前面说过了什么”等自然问法未触发回顾 | 语义变体进入受控回顾；会话状态和待确认卡准确、不过度复述全部历史 |
| D20 | 取消卡与有效订单在连续对话中可能被混淆 | 说清卡仍待确认、何时过期及订单当前状态；任何口头陈述不确认订单 |
| D21 | 自述伦敦与次日汉堡出发机票潜在不连续 | 只在相关规划时提示核对，不能推断旅客必然赶不上，更不能自动取消 |
| D22 | 境外天气覆盖与“明天”的当地日期边界 | 境外来源单独核验；航班以出发机场、天气以目标城市的当地日历解释 |
| D23 | 模型标识易被误读为底层精确版本 | 保留提供方及配置标识的透明答复，明确其不是底层版本证明；不暴露密钥或内部地址 |
| D24 | 相同问题反复追问且不给可行动选项 | 回答已知条件、具体缺项与可选择路径；连续重复时给更明确的澄清 |

## 4. 分阶段实施方案

### P3.1g1：版本取证、国家目的地与跨任务出发地

开工前重读三份核心文档、本计划及公开发布规则，检查分支和工作区。只读核对 8000 的可达性、进程启动时间与代码版本；若不可达，记录“无法判断此前页面版本”，不触碰用户进程。用隔离测试库重放原始失败对话并逐轮记录本轮输入、会话所在地、航班目标、缺项、候选、卡和订单数量。先建立失败回归，再让“伦敦 → 中国 → 最早可售城市 → 选择城市 → 唯一最早航班待确认卡”走完；中文国家、城市、机场和更正目的地要区分。完成后固定模型回归及原有相关测试通过，确认前订单增量为零。此步不做境外天气接入、不改正式库。

### P3.1g2：行程简报、自然回顾与城市级“周围”

统一当前有效行程的中文起终点、当地起飞和到达时刻、状态及次级航班号；长列表有明确省略数量和查看方式。扩展回顾的自然问法，并核对它只从本会话状态和本人卡片中总结。把“周围”纳入当前位置或目的地的安全分流；有两个锚点时澄清。待取消卡的状态与订单有效状态分别展示，检查自述伦敦与汉堡机票的提醒不误判。模型标识答复补上配置标识与底层版本的区别。桌面和窄屏核对文案，不让订单 ID 替代主信息。

### P3.1g3：境外天气来源与当地日期（以用户选择为准）

先做只读来源评估：覆盖城市、可核验字段、稳定性、调用额度与条款、是否需要新增 API 密钥、故障降级。单独给用户可选来源和费用，再写具体接入计划并确认；不擅自申请或配置新服务。接入后按目标城市时区解析“明天”，只在核验城市、目标日、发布时间和预报数值后给出天气；无证据、搜索超时、错误国家或过期页面均降级。阿里云搜索内容不能触发任何交易。

### P3.1g4：隔离环境整段验收及 G-16 重新评估

在独立 PostgreSQL 项目和独立 API 端口，用一次性旅客回放用户这段完整对话及近义变体；核对每轮任务、已知条件、候选、卡、订单与审计。至少覆盖跨话题恢复、改口、国家空结果／多个城市／并列最早、在候选展示后报价变化、过期卡、两张取消卡、普通行程与明确历史、天气来源失败、跨账号访问、API 重启。先固定模型，再在另行确认的调用额度内用真实 DeepSeek 和阿里云搜索复测；记录调用数和费用上界，不提交密钥或完整私人对话。验收页面桌面与窄屏以及取消卡状态。任何错城市、错对象卡、未经确认写入、跨账号泄露或订单与审计不一致均阻断发布。

各小步均在开始前生成独立操作计划并获得用户确认；完成后同步《当前进度》，必要时更新《产品需求》《软件架构》和 README。G-16 只有在本轮阻断项通过、重新审查发布计划且用户单独确认后，才可执行本机 `main` 合并或 GitHub 同步。

## 5. 数据、费用和 Git 边界

优先使用内存／独立数据库和固定模型。正式演示库、旧 SQLite、用户的 8000 调试服务只读或不接触；若需独立 Docker 容器，先验证项目名、端口和卷，保留旧验收卷，不执行跨项目 `down -v`。P3.1g1、g2 不需要付费模型或联网接口；g3、g4 的真实调用次数、可能费用和停止线在各自操作计划中列出并由用户确认。所有公开提交说明、文件和文档避免用户指定的工具品牌字样；功能分支可提交，主线合并与远端推送仍遵循单独授权。
