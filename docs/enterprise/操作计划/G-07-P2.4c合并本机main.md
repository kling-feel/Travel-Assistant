# G-07：P2.4c 合并本机 main 操作计划

> 编写日期：2026-10-18｜状态：待用户单独确认；本文件只记录事前方案，实际结果写《当前进度.md》

## 目标与当前依据

把已在 `<历史功能分支>` 分支验收的可达城市酒店与租车产品、虚构政策，以及相应的迁移、查询和回归脚本，快进合并到本机 `main`，作为 P2.5 的稳定起点。编写本计划时，实现提交为 `6632156`，本机 `main` 为 `b353859`，上次核对的 `origin/main` 为 `fbb02bb`。执行时必须重新检查这些引用，不能以本段的旧快照直接操作。

P2.4c 实库已应用 v007，演示基准日为 2026-10-18：115 个机场、33,121 班航班、15,374 个窗口内模拟报价、618 条可订航线、312 个酒店/房型、208 个租车产品，覆盖 104 个可达目的地机场和 95 个城市。两名演示旅客的机票与酒店订单继续保留，待确认动作及审计记录为零；28 项自动化测试、两日期实库重建/查询、旧五类交易和重启持久化已通过。PostgreSQL 容器目前停止，数据卷与三份被 Git 忽略且已核验的本机备份保留。

本步骤仅改变**本机 Git 主线和文档**。数据库模式已经领先旧 `main`，因此合并前不从旧主线启动 API、运行迁移/导入或重置演示库。本步骤也不开始 P2.5 业务代码，不推送远端。

## 执行顺序

1. 重读《产品需求》《软件架构》《当前进度》和本计划；检查当前分支、工作区、提交图，以及 `main...HEAD` 的提交与文件清单。先用 `git diff --check` 核对本轮 G-07、计划索引、路线状态和进度记录；只暂存这些计划文档，作为独立提交保留在 P2.4c 分支。出现意外修改先调查，不覆盖或顺带提交。
2. 执行 `git fetch origin`，重新核对远端和本机 `main`。若 `origin/main` 已不同于上次核对的 `fbb02bb`，先报告新增提交及其对合并的影响，暂停本次合并；不自动拉取、变基或强推。确认 `main` 仍是 P2.4c 分支祖先、分支工作区干净且可快进。
3. 审阅本次纳入的文件及提交：v007 迁移、确定性产品生成与查询、虚构政策版本、旧 FAQ 隔离、导入/重置的显式备份和待确认动作保护。检查暂存和跟踪文件中没有 `.env`、本机数据库/备份或其他凭证，已应用迁移没有被改写。运行 28 项自动化测试、2026-10-17 与 2026-11-01 两日期离线航线样本校验、Python 编译与 `pip check`；核对旧 `/api/graph/` 交易路由仍未注册。这里不启动 PostgreSQL；实库结论沿用 P2.4c 已记录的验收，不把离线检查表述为重新实测数据库。
4. 全部检查通过后，切换本机 `main` 并执行 `git merge --ff-only <历史功能分支>`。若分支不能快进，停止并分析分叉，不自行制造合并提交、改写历史或覆盖他人改动。
5. 合并后核对 `main` 与已审阅的分支末端一致，复跑自动化测试、两日期离线校验及必要的编译/依赖检查，并检查工作区与旧图路由。将实际提交、检查结果、数据库未触碰和后续 P2.5 状态写入《当前进度.md》，在本机 `main` 单独提交进度记录，最后复核提交图与工作区。

## 通过条件与异常处理

- 本机 `main` 线性包含 P2.4c 实现及 G-07 计划文档；合并前后 28 项现有测试与两日期离线校验通过，旧图交易路由没有重新开放。
- PostgreSQL 容器、数据卷、备份和 `origin/main` 不因 G-07 改变；本步骤不运行数据库导入、演示重置或远端推送。
- 合并前检查失败则停在原分支并记录原因；合并后检查失败则保留现场、分析并提出修复方案。不使用 `reset --hard`、强推或 `docker compose down -v`。

用户确认 G-07 后才执行。本机合并完成后，另写 P2.5 航班新预订与租车交易的详细计划并单独取得确认；远端推送也需独立计划和确认。
