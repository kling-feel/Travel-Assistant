# P3.3a：日期更新安全预检与演示批次方案

> 2026-10-24 制定｜状态：旅客已选择新演示批次并保留旧记录；本子步等待单独确认。承接[P3.3 分步路线](P3.3-演示日期维护与部署分步路线.md)；结果写入[当前进度](../当前进度.md)。

## 1. 目标与本步范围

在任何日期更新实现或正式库操作前，给出可以复核的演示批次切换方案。当前导入脚本虽有预览、备份文件头和待确认卡保护，但应用只有一个 `demo_state`，正式重置会清除订单、会话及审计；`compose.yaml` 的默认库使用本机 5433 与命名卷。P3.3a 只做代码、配置和必要的数据库**只读**盘点，确认哪个数据卷是当前正式演示库、现有演示日、账号及订单／待确认卡数量。若当前库未运行或工作台无法访问 Docker，不要求旅客为本步启动服务；先完成静态方案，运行态读数标明待核对。

## 2. 旅客确认后的执行顺序

1. 重读产品需求、软件架构、当前进度及本计划，核对本机 `main`／远端状态和工作区；另建中性命名本地功能分支。按已确认的“旧批次保留、新批次隔离构建”固定方案，不在 P3.3a 中改变旧库。
2. 只读梳理 `compose.yaml`、环境配置、迁移、`demo_state`、现行导入脚本及页面/API 的演示日期读取点，列出会受日期平移影响的航班、报价、酒店、租车、初始订单、会话、确认卡、审计与检查点。记录默认端口和数据卷名称的识别方法，不读取或输出密钥值。
3. 如果正式库可读，只执行不会写入的状态查询：演示基准日、有效／历史订单数量、待确认动作、非默认账号、会话／审计数量及数据库版本；如不可读，在结果中写清未知项，不据此假定可安全重置。对于后续隔离库，明确独立 Compose 项目、端口、卷名、API 端口、备份路径和恢复演练步骤。
4. 形成 P3.3b 的明确输入／输出和停止条件：仅在新隔离库迁移、导入和测试；预览先显示目标日期、将改写的实体及预计数量；写入前核对目标库身份、备份可读性、无其他演示用户占用；写入后比较供给计数、当地时间、种子订单与价格。旧库与 8000 页面始终作为回退点。
5. 输出操作手册草案、风险表与测试矩阵，补进度记录；只提交本地功能分支。P3.3b 的代码实现、正式库切换和 GitHub 发布另拟计划并分别确认。

## 3. 完成标准与停止条件

- 明确旧批次的保存位置、新批次的目标端口与数据卷、切换时机、回退方法和要核对的订单／会话边界；不把“备份成功”仅等同于文件存在，后续须检查格式并演练恢复。
- 不执行 `--apply --reset-demo`、迁移或任何数据库写入，不启停 8000 页面，不调用付费模型／搜索；本步不合并 `main`、不推送 GitHub。
- 不把旧批次清空或把新批次直接导入旧卷；如果后续需要清理旧卷，必须重新列出记录、备份恢复办法并取得针对具体目标的确认。
