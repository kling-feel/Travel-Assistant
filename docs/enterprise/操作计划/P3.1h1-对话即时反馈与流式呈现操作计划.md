# P3.1h1：对话即时反馈与流式呈现操作计划

> 制定日期：2026-10-23｜状态：用户已确认并实施于功能分支，结果见《当前进度》。用户已取消境外天气接入方向，并选择“核验后流式答复”。本计划不授权本机主线合并或远端推送。

## 1. 目标与现状

目标体验：旅客按下发送后，自己的消息**立即出现在当前会话末尾**；助手在真实处理期间显示“已收到／正在查询或核对／正在整理答复”等简短状态和运行时间；最终答复通过流式连接逐段出现，完成后再呈现来源、候选和待确认卡。等待反馈只说明可观察的处理阶段，不展示所谓“内部思维链”，也不插入固定假延时。滚动位置、键盘操作和窄屏排版要自然，视觉上保持现有中文旅行工作台的简洁风格并提升质感。

当前 `static/app.js` 的 `sendTurn()` 等待 `/api/v1/sessions/{id}/turns` 返回完整 JSON 后才清空输入并重新加载消息；因此处理期间对话框里没有新消息。后端在 `api/travel.py` 内执行 `begin_turn → graph.invoke → 业务证据／提案核对 → finish_turn`，最终回答与卡片一次提交。这个顺序保证交易准确，但没有中途传输能力。继续保留现有 JSON 接口供 API 客户端使用；页面新增流式路径，不绕开既有逐笔确认协议。

参考成熟方案：FastAPI 支持用 [`StreamingResponse`](https://fastapi.tiangolo.com/advanced/custom-response/) 分批发送响应；浏览器 [`fetch()` 的响应体可逐块读取](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch)，并用 `TextDecoderStream` 解码。DeepSeek 也支持[流式增量事件](https://api-docs.deepseek.com/api/create-chat-completion/)，但本项目的模型输出仍须经过数据库、政策和确认卡核验，不能把未经核验的模型文字直接展示。因此第一版采用 **POST + fetch 流式读取 + SSE 格式事件**：可携带现有登录令牌和请求键，服务端先发送状态，再在完整答复落库后发送最终文本片段。`EventSource` 的 GET 自动重连不适合直接提交当前带令牌和请求体的回合。后续如需普通闲聊真正逐 token 推理输出，另作限定范围评估。

## 3. 实施顺序

### A. 页面即时反馈

发送时锁定当前会话与 `request_key`，立即在消息列表末尾添加旅客气泡，将输入框清空并保留重试所需文本；随后加入带轻量动态点和经过时间的助手等待气泡。按钮与状态清楚区分“发送中”“正在处理”和可重试。仅在用户原本接近底部时自动跟随新内容；浏览旧消息时不强制滚到底。会话切换、退出登录或页面刷新时撤销当前页面流并按服务器历史重建，不把旧会话片段画到新会话。窄屏不产生横向滚动，长中文、航班号和长订单号可换行；支持 `prefers-reduced-motion`、键盘焦点与有节制的读屏状态播报。

### B. 共用后端回合与流协议

抽出 JSON 接口和新流式接口共同调用的单一回合处理函数，保留本人会话校验、输入长度、`begin_turn` 请求键幂等、LangGraph 检查点、事实来源、提案核对、`finish_turn` 原子提交与失败标记。新增 `POST /api/v1/sessions/{id}/turns/stream`，在完成身份和输入校验后返回 `text/event-stream`；约定版本化事件：`accepted`（同一请求键已登记）、`progress`（有限白名单阶段）、`delta`（已核验最终答复的后续文本）、`completed`（最终回合状态及引用／卡片索引）或 `failed`（可恢复错误码）。事件使用 JSON 数据，流中不含密钥、订单私密原始字段或模型内部推理。设置禁止缓存与代理缓冲，必要时心跳；状态文本仅由服务端控制，不采用模型自述。旧 JSON 接口的请求和响应继续兼容。

当前模型和业务图调用为同步处理。流式接口须把阻塞工作放入受控工作线程，由独立数据库会话完成事务并经队列传递有限状态，不能阻塞事件循环，也不能把请求作用域中的数据库会话带到响应生成器之外。客户端断开时不直接中止可能已开始的订单提案事务；最终以持久回合状态核对结果。

最终答复先经过现有 4000 字上限、业务证据和动作卡检查并成功保存，再按文本边界分段发送；服务端不人为固定等待，也不把未核实金额、班次、政策或“已预订”字样提前流出。前端逐段用 `textContent` 更新气泡；收到 `completed` 后重新核对本人会话消息、来源、候选和动作卡，消除展示与持久状态的差异。若答复很短或模型很快完成，仍可直接迅速结束，不故意拖慢。页面样式不制造虚假的“思考步骤”。

### C. 中断、重试与异常

请求断开、页面刷新或 70 秒等待超时后，页面用原 `request_key` 查询本人回合状态，再决定恢复已完成答复、提示仍在处理，或给原键重试入口；不得生成第二条旅客消息或第二组卡片。服务端应明确断连后的执行与最终状态规则：完成提交的回合可直接恢复；未完成的回合在旧租期内不得并行重跑，超期标记失败后才能明确重试。流已开始后的异常用 `failed` 事件及数据库状态表达，不能再假装 HTTP 200 代表交易成功。网络在最终提交之后断开时，以持久状态为准；确认卡仍须旅客另点确认。对其他账号、其他会话和重放不同内容的同一请求键继续拒绝。

## 4. 验收矩阵与费用

| 场景 | 必须满足 |
| --- | --- |
| 按发送后立刻观察 | 旅客原文先出现在当前对话，助手显示真实处理状态；输入框可立即清空，失败可找回原文 |
| 普通问答及有证据的航班／酒店／租车查询 | 最终文本逐段显示，完成后与数据库保存答复完全一致；来源和候选只属于本轮 |
| 批量取消与订单卡 | 卡片在服务端核验并保存后才出现；确认前订单仍不变，不因流或断线自动确认 |
| 重复提交、超时、断网、刷新、切换会话、退出 | 相同请求键不重复建消息／卡；旧流不污染新会话；恢复时以本人持久记录为准 |
| 故障与安全 | 模型失败、坏事件、错账号、XSS 文本、代理缓冲和早期断连有明确状态；不泄露令牌或模型内部推理 |
| 页面 | 1280 像素桌面及约 338 像素窄屏实际验收等待态、流中、完成、失败与卡片；键盘和减少动画偏好可用 |

先增加后端事件协议和前端状态回归，再跑完整现有自动化测试、Python 编译、页面脚本语法、依赖和差异检查。固定模型模拟慢回复、分块边界拆开中文字符、重复键、断连前后、并发回合和两张提案卡。实际联网模型联调建议最多 **10 次 DeepSeek 回合**，只验证流式体验和结果一致性；不调用阿里云搜索作额外收费测试，实际金额以服务商账单为准。若服务器或代理把全部片段缓冲到末尾，视为未达到流式验收，先定位缓冲层再判断完成。
