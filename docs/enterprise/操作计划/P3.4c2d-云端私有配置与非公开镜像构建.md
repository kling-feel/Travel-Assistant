# P3.4c2d 云端私有配置与非公开镜像构建操作计划

> 2026-10-26 制定并获旅客确认，**已执行并验收镜像产物**。承接已验收的 [P3.4c2c 香港主机基础配置](P3.4c2c-香港主机基础配置.md)。本阶段只准备可追溯的代码、私有配置和镜像，没有创建正式数据库批次、启动应用或代理、签发公网证书、开放网站或调用付费模型／联网搜索。

## 已有条件和本阶段目标

- 旅客已购买中国香港 Ubuntu 24.04 服务器及 `adzyforever.com`，根域与 `www` A 记录已由服务器侧核对。主地址拟用 `adzyforever.com`，`www` 最终跳转到根域；公网 DNS、证书和跳转仍须上线阶段实测。
- 专用非 root 管理账号和 SSH 密钥登录已验收；远程 root／密码认证关闭。Docker Engine 29.9.2、Compose 5.6.1 可运行，当前没有应用或数据库容器。主机实际可见内存 1,613 MiB、无 swap，不能把本机 2 GiB Docker Desktop 测试当作真机结论。
- 仓库已有 `compose.cloud.yaml`、`compose.cloud.2g.yaml`、云端配置生成和预检脚本、固定基础镜像摘要、一次性初始化及账号管理入口。当前 Caddyfile 只配置根域，尚未实现已约定的 `www` 跳转；本阶段先在代码中补齐并验证语法。

## 开工前由旅客准备

1. **证书联系邮箱**：旅客已提供用于自动 HTTPS 的邮箱；具体地址只写入服务器私有配置，不写入公开计划、进度或提交。该地址不用作登录账号。
2. **服务密钥**：旅客选择暂用本机已有的 DeepSeek 与阿里云联网搜索密钥。执行获确认后，仅从本机私有配置读取所需的两项值，以不显示内容的传输方式写入服务器的 Git 忽略私有配置；不复制整个本机 `.env`，不在聊天、截图、命令行参数、Git 或日志中输出。云端和本机共用密钥，后续展示稳定后建议换成可单独轮换的云端密钥。
3. 不需要再购买服务器或域名；本阶段不要求支付新服务费用。实际模型与搜索费用只在后续独立验收获确认后产生。

## 执行顺序与每一步检查

1. **本机发布基线**：重读产品需求、架构、当前进度和本计划；核对当前功能分支、提交及工作区，禁止把未审查改动混入部署包。复核 Git 跟踪清单、`.dockerignore`、固定基础镜像摘要、迁移版本和 2 GiB 资源覆盖文件；扫描待发布差异，避免私钥、`.env`、备份、真实账号或用户要求避免的公开字样进入仓库或构建上下文。记录确切提交和包的 SHA256，不在公开文档记录公网 IP 或私有文件路径。
2. **双域名代理配置**：按 [Caddy 官方 Caddyfile 示例](https://caddyserver.com/docs/caddyfile/patterns)增加 `www.adzyforever.com` 到根域的跳转，同时保留根域的内部端点屏蔽、HTTPS、安全响应头和证书持久卷。用无真实密钥的配置验证 Caddyfile 和跳转规则；这一步只改代码，不启动服务器公网代理。若测试指出原有单域名验收配置受影响，先修正再打包。
3. **生成干净发布包**：在功能分支提交通过审查的改动后，从该**确切 Git 提交**生成只包含受跟踪文件的发布归档，写入本机 Git 忽略目录并计算 SHA256。通过已核对的 SSH 密钥送至服务器，比较两端哈希后解包到固定的非公开部署目录；私有 `data/generated/` 留在该目录，后续升级不能覆盖或随归档替换。服务器上确认归档没有 `.git`、`.env`、账号文件、备份或原始 SQLite。保留本次提交归档供代码回退，不用 `git pull` 隐式改变服务器代码；本阶段不合并 `main`、不推送 GitHub。
4. **准备独立私有配置**：只在服务器 Git 忽略目录调用现有生成器，指定真实根域、旅客已提供的联系邮箱和执行当天的演示基准日；生成独立数据库、JWT 和初始账号随机值。目录仅管理员可进入，配置文件权限为 `0600`。在确认本机已有配置中两项服务密钥的字段来源后，只把这两项值通过私有传输写入对应云端字段，不复制本机其他密码、账号或数据库连接。运行只报告字段名称的预检，不打印配置内容；核对公开地址、DeepSeek 模型标识、阿里云 GlobalBasic 参数、固定镜像摘要、资源限额及 Compose 服务清单；避免运行会展开密钥的完整 `docker compose config` 输出。[DeepSeek 当前官方文档](https://api-docs.deepseek.com/quick_start/agent_integrations/)列出的 `deepseek-flash` 与现有模板一致，部署前仍按官方文档和账户可用模型复核。
5. **真机受控镜像构建**：先拉取并核对固定 Python、PostgreSQL、Caddy 基础镜像是否对应本机架构；仅构建应用、初始化和账号管理镜像，不执行 `db-up`、`init`、`app-up`。按服务顺序单路构建，[Docker Compose 并行度](https://docs.docker.com/reference/cli/docker/compose/)限制为 1；记录开始／结束的 available 内存、磁盘、镜像大小和 OOM 事件。Compose 并行度只约束多个服务任务，BuildKit 单个构建内部仍会占资源；不得将它写成内存硬上限。若内存不足或拉取失败，停止重试与公网步骤，优先在本机受控构建、校验镜像并传输至服务器，或提出 4 GiB 升级选择；不自动加明文 swap、不改套餐。
6. **收尾与文档**：核对服务器仍无应用／数据库容器，宿主机仍未发布 80／443／8000／5432，Docker 守护进程没有 TCP 管理端口；保留代码归档、可验证镜像和私有配置，不删除旧资源。将实际哈希、构建结果、资源峰值、失败及后续门槛写入《当前进度》与云端指南。仅在当前功能分支提交公开代码／文档；主线合并与 GitHub 同步另按 G 系列发布计划确认。

## 通过标准和后续边界

- 发布包可追溯到唯一提交且两端 SHA256 一致；私钥、环境文件、账号和备份不在归档或镜像内。
- 根域及 `www` 代理配置语法通过，实际跳转和受信证书仍留给公网阶段；完整私有配置预检通过后才能进入下一阶段的数据库初始化。若本机已有的任一密钥不存在或已失效，停止对应配置步骤，告知旅客需要补充可用密钥，不能声称本阶段全部通过。
- 镜像在香港主机完成构建或通过可复核的本机预构建交付；无 OOM、磁盘不足和意外公网端口。若未达到，先给旅客具体失败证据与备选方案。
- 下一检查点 P3.4c2e 才会建立全新空数据库卷、先备份再显式初始化、创建授权账号并停用种子账号；P3.4c2f 才启动应用／Caddy，开放与验收 80／443、HTTPS 和真实模型／搜索。两步都先各自出独立计划并等待旅客确认。
