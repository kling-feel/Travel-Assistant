## 目标与现状

正式云端网站保持在线，但当前授权账号没有已确认演示行程；原有 2 笔机票和 2 笔酒店订单属于已停用的初始账号。为面试展示补一套时间与地点连贯的虚构行程：从上海出发到伦敦，抵达机场附近住两晚并租车。既有上海虹桥机场至伦敦盖特威克机场航线存在于交付样本，**不凭源样本推断云端当天的可售日期或最终报价**；执行前必须从现有云库只读核实。

## 执行步骤与检查点

1. **只读现场核对**：确认本机／GitHub 主线一致，云端应用、数据库、代理健康且仅代理暴露 80／443；核对 2026-10-27 批次、5 个卷、现有账号、原订单及加密备份哈希。只读查询从 2026-10-28 起演示窗口内的上海→伦敦可售直达航班，核实实际出发与到达机场、两端当地日期、UTC 偏移和模拟报价。以**实际抵达日及抵达机场**筛选连续两晚可订酒店，并筛选同机场可订车辆，核实取车时间晚于到达并有合理缓冲、还车时间与退房日一致。优先选时间较近且价格明确的组合；若没有完整组合，停止写入，向旅客报告候选和调整建议。
2. **写入前恢复点**：在原云库执行新的 PostgreSQL 自定义格式备份，校验 `pg_restore -l` 和哈希；沿已验收流程在旅客本机用公开接收密钥加密，不落本机明文。验证密文可由本机恢复身份解密并核对归档；保留旧备份。备份或身份／容量检查失败时停止，不创建账号或订单。
3. **建立干净演示账号**：用已有云端账号管理入口建立一名独立、随机口令、已授权的展示账号；密码只写服务器私有目录及旅客本机 Git 忽略的受限文件，不在聊天、日志、文档、截图或 Git 出现。确认其登录后行程为空、无法读取原账号的会话、卡片和订单；不复用已停用账号、不迁移原订单。旧授权账号的待确认卡留在原账号，展示账号看不到。
4. **先给旅客核对具体行程**：把只读选中的航班号、两端当地时间及偏移、到达机场、酒店名称与入住／退房日、租车取还时间、各项模拟金额和政策摘要发给旅客判断。若路线或时间不合适，重新只读选择，不生成卡。
5. **按正常对话建立三张卡**：在展示账号的新会话中按“机票→落地酒店→租车”分步查询与明确预订。每步核对卡片对象、时间、金额、有效期、规则及账号归属，再请旅客在公网页面亲自确认该张卡；前一笔确认后才推进下一笔。助手或脚本不代点确认，也不把“确认计划”当作交易授权。每张卡约 15 分钟有效；若过期或产品／价格变化，放弃旧方案并重新查询、重新展示。任何一步生成错误卡、跨账号可见、未确认即改订单或出现多张歧义卡，立即暂停交易并按已确认的故障流程关闭公网入口。
6. **验收与备份**：确认每笔订单只创建一次，状态均为已确认，展示账号“我的行程”按时间列出上海→伦敦机票、两晚酒店和匹配租车；普通对话也能正确叙述这三笔，历史与取消记录不混入有效行程。核对原 4 笔订单、原授权账号、批次和供给未变；审核审计、用量、日志、内存、OOM。完成后再制作一份服务器外加密备份并实际解密校验；如本机隔离 Docker 可用，再从**新备份**恢复到新卷比对订单与审计。网站维持在线，所有动作和局限写入《当前进度》及独立验收记录。

## 必须由旅客操作及敏感文件边界

- 旅客唯一必须亲自完成的业务动作是：看清每张待确认卡后，分别决定是否点击“确认”。我会提前给出该笔的对象、时间和金额；如果旅客不确认，就不继续后续依赖该订单的步骤。展示账号口令只在本机私有文件中交接，不通过聊天发送。
- 执行时需使用本机专用 SSH 私钥连接服务器，读取服务器私有的账号文件以做授权登录，并用本机私有的备份恢复身份验证新密文；现有应用在处理对话时使用服务器私有模型配置。具体文件位置在执行前单独告知旅客；本次计划确认视为对上述**限定用途**的访问授权，不包含把文件内容发送到聊天或公开仓库。无需新增模型或搜索 API、域名、防火墙端口，也无需旅客购买服务。

## Git、失败处理与完成标准

本步优先使用既有业务和管理入口，预计不改应用代码或数据库迁移；如发现代码缺陷，停止正式订单写入，先单独提出修复计划。可复用的非敏感辅助脚本和验收记录放功能分支，私有账号、备份、日志、截图与订单细节只留 Git 忽略目录。完成后另给主线与 GitHub 普通快进同步计划；无强推、无历史改写，公开内容不含开发工具品牌字样。

只有三笔独立确认完成、账号隔离正确、行程连贯、原订单不变、前后加密备份可用且网站健康时，才标记本步完成。若旅客选择只确认部分卡片，按实际结果记录为“部分完成”，不伪称完整行程；绝不自动补单或替旅客确认。
