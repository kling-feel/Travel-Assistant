# P3.2c3：业务服务与助手入口归位分步路线

> 2026-10-24 制定｜状态：P3.2c3a 与 P3.2c3b 均已执行。承接已完成的 [P3.2c2](P3.2c2-配置数据库与通用模块归位.md)；实施结果记入[当前进度](../当前进度.md)。

## 1. 为什么继续拆步

当前 `services/` 有 28 个 Python 文件，`graph_chat/` 有 2 个，`api/` 有 4 个；跨这三组的现行导入和测试补丁目标约有数百处。业务服务被 API、助手、迁移、脚本和测试共同引用，一次搬迁全部三组会使失败原因难以定位。因此 P3.2c3 拆成先业务服务、后助手与 API 的两次独立确认；每次完成可运行状态和全量回归，不保留双份实现。

| 子步 | 移动和引用范围 | 检查点 |
| --- | --- | --- |
| [P3.2c3a](P3.2c3a-业务服务归位.md)（已执行） | `services/` 原样迁到 `travel_assistant/services/`，同步更新当前 API、助手、迁移、脚本、测试的导入及字符串补丁目标；`api/` 和 `graph_chat/` 位置暂不变 | 应用启动、31 条路由、18 张表、13 个迁移版本、230 项自动化基线、九类交易与页面均保持；只读离线验证 |
| [P3.2c3b](P3.2c3b-助手与旅客API归位.md)（已执行） | `graph_chat/controlled.py` 迁到 `travel_assistant/agents/`，`api/` 迁到 `travel_assistant/api/`，同步更新 `main.py`、脚本、测试的导入和字符串补丁目标 | 根 `main.py` 仍是启动入口；API 和流式协议、本人身份与逐笔确认不变；完整回归通过且旧根目录不再有可运行实现 |

`travel_assistant/services/` 中先保留当前文件名和职责；改名、拆分庞大文件及业务优化属于另行评审的工作，不与路径迁移叠加。根 `migrations/`、`scripts/`、`tests/` 和交付数据保持现有入口；P3.2c4 再整理脚本与测试的可视性。

## 2. 共用边界

- 每步先重读《产品需求》《软件架构》《当前进度》，单独写计划并取得旅客确认；只在本地功能分支提交，结果回写《当前进度》。
- 业务事实、报价算法、政策、订单事务、会话检查点与确认协议不得因移动改变；迁移文件只允许修改导入，不增删版本或改 SQL。
- 使用固定模型与内存数据库做自动化，核对离线样本、页面资源、路由和 API 契约。不运行正式库迁移或导入，不写 5433／5435，不调用付费模型或联网搜索，不操作用户 8000 页面。
- 如果发现循环依赖、动态补丁遗漏或测试退化，先停在当前子步修复；若不得不扩大功能范围，先修订计划并再次确认。G-17 的本机主线合并和 GitHub 同步仍须单独确认。
