# P2.6c2：DeepSeek 剩余场景补测操作计划

> 编写日期：2026-10-19｜状态：被 P2.6d 完整评估计划取代，未执行；本文件保留规划历史

## 起点与目标

P2.6c 已在功能分支 `<历史功能分支>` 提交为 `ec21abe`。30 次真实 DeepSeek 请求已用完；修复后已验证九类交易中的七类，以及双卡、真实政策边界、跨账号与未确认订单不变。尚缺酒店取消、租车取消，以及在**实际返回两班以上**的航线中选择第二班的真实模型证据。初轮的“第二班”测试样本只返回一班，评估脚本现已改为从数据库查找真实多候选路线，但未再次付费调用。

本补测只补证据及修正由补测暴露的对话路由/澄清问题；不改变交易政策、确认 API、演示数据生成规则，不接联网推荐和页面，不合并 `main` 或推送远端。DeepSeek 本机 `.env` 已配置，本计划不要求在聊天中提供密钥。

## 新调用额度与操作顺序

1. 用户确认本计划后，才追加**最多 10 次**真实 `deepseek-flash` 请求；与上一阶段的 30 次分开记录，总累计上限 40 次。每次请求仍为 25 秒超时、自动重试 0 次。10 次额度优先安排：酒店取消 1 次、租车取消 1 次、多候选查询与“第二班”选择 2 次、无效产品及日期含糊反例各 1 次；余下至多 4 次用于针对性修复复测。若无需复测，不用满额度。
2. 开工先重读三份核心文档和本计划，核对功能分支、工作区、模型配置布尔值及数据库停止状态。启动 PostgreSQL 后只读核对 13 版迁移、2 个演示旅客/机票/酒店订单、0 临时记录；新建 Git 忽略的 `pg_dump` 并用 `pg_restore -l` 核验。备份前不写测试数据，绝不运行演示重置。
3. 运行改进后的有界评估脚本，仅使用临时虚构账号和订单。用响应中的 `actions`、`references`、正式订单计数与服务端动作详情判定，不凭模型自述判断成功。不得调用真实模型生成卡片的确认接口；同请求重放、跨账号 404、未确认订单不变不额外消耗模型调用。失败决策只保存在 Git 忽略的本机报告，不保存密钥或真实旅客资料。
4. 如果两类取消或多候选仍失败，先按具体模型决策和正式服务拒绝原因修复提示词或安全澄清，运行针对性测试及全部回归，再在剩余额度内复测。修复不得放宽产品、本人订单、日期、金额和政策的服务端校验；需要改交易规则或超过 10 次请求时停止并单独请用户决定。
5. 清理临时会话、检查点、动作、订单和账号，逐表与备份前基线比较；若清理失败保留现场与备份，不重置数据库、不提交合并。通过后停止容器、保留卷和备份。运行全部自动化测试、两日期样本、编译、`pip check`、路由与 `git diff --check`，把实测通过率、请求/用量/官方价格估算、剩余问题写入《当前进度》，仅提交到功能分支。

## 验收与后续 Git

九类交易各有修复后真实模型生成正确待确认卡的证据；真正的多候选选择引用第二个正式候选；无效产品和缺日期不会生成卡。双卡仍全有或全无，未确认不改订单，跨账号、重放和数据库重启后的固定模型回归正常。若达不到，记录失败并保持本机 `main` 不变。补测通过后另行编写 G-14 本机合并计划，向用户说明并取得确认；远端推送仍为独立决定。

新增调用费用按服务商返回 token 用量及执行当时的 [官方价格](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)估算，实际账单由 DeepSeek 账户决定。本计划尚未执行任何新增请求。
