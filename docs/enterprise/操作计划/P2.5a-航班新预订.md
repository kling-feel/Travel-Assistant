# P2.5a：航班新预订操作计划

> 编写日期：2026-10-18｜状态：待用户单独确认；本文件只记录事前方案，实施结果写《当前进度.md》

## 目标、范围和建议

在当前五类受控动作上增加 `flight_book`，使内部提案服务能按真实数据库中的虚构航班和确定性报价生成机票新预订卡；旅客通过已有的指定动作确认 API，才会创建一张属于本人的模拟机票订单。建议一个旅客同一班次最多一张**有效**机票，取消后可重新订；并发不同卡片也不得重复下单。此步不开放旅客直接提交新订单或自定金额的接口，普通聊天暂不能生成卡片，P2.6 才接入智能体。

当前 `main` 为 `e43d189`，工作区在计划编写时干净，PostgreSQL 停止且 v007 已应用。执行时重新核对状态。P2.4c 数据有 618 条可订航线和 15,374 个窗口内模拟报价；本步使用现有数据，不重建演示日期或改动原始 SQLite。

## 拟改动模块与动作契约

1. 从干净 `main` 新建 `<历史功能分支>`。新增 v008 迁移：扩展 `pending_actions.action_type` 数据库约束，允许 `flight_book`；给有效机票的 `(traveler_id, flight_id)` 增加数据库级防重复约束，并与现有测试用 SQLite 模式保持一致。已应用的 v001～v007 不改写。先核对现有演示订单不会违反新约束；现有机票改签若改到本人已持有的班次，也须在提案和确认时明确拒绝。
2. `services/actions.py` 增加严格参数 `{flight_id}`。提案时查 `Scheduled` 且尚未起飞、位于演示基准日未来约 30 天可订窗的正式班次、当前 `flight_offers` 与虚构机票规则 v3；卡片 `before=null`，`after` 给航班号、起降机场与带时区的当地起降时间、模拟票价和待创建订单状态，金额显示一次应付、不显示真实支付。不得由调用方传旅客 ID、票价或规则版本。新提案本身不写机票订单。
3. `services/confirmations.py` 在已有身份/会话锁和 15 分钟期限内，锁定影响报价的航班、报价和规则；重新计算卡片，检查版本和现有有效机票。仅在同一事务中调用 `services/travel.py` 创建订单，写动作结果与审计。重复确认同一动作返回原结果；另一个新预订动作或旧改签动作导致同一旅客同一班次重复持票时，应得到明确冲突并不新增/改动订单。取消后的重订依旧按当前报价重新提案。
4. 更新必要的行程/API 文档和验收脚本。继续复用现有 `GET /api/v1/me/itinerary`、卡片读取以及确认/拒绝 API；用内部服务或隔离验收脚本建立卡片，再通过真实 API 确认。不给浏览器客户端开放可绕过智能体边界的提案创建或订单直写路由。

## 执行与检查顺序

1. 重读《产品需求》《软件架构》《当前进度》及本计划；检查工作区、迁移表、现有五类动作和演示库状态。记录数据库旅客、订单、待确认动作数量；在任何迁移前创建 `pg_dump` 并以 `pg_restore -l` 核验，备份保存在 Git 忽略目录。不运行旧小样本导入/种子或整体重置。
2. 实现迁移、提案、确认与内部订单写入；保持金额由数据库报价决定、取消费与原五类逻辑不变。不同会话可能同时为同一旅客建卡，确认时须统一锁定旅客并重查有效机票，数据库唯一约束作最后防线；若约束冲突，用可回滚的事务边界转为明确冲突，不能让 PostgreSQL 留在错误事务状态，也不能留下半写入结果或重复审计。
3. 增加有针对性的测试：正常下单、本人/跨账号隔离、无班次或无报价、已起飞/已取消、报价或政策变化、拒绝/过期、同动作重放、两个动作并发、新预订与旧改签争抢同一班次、取消后重订；确认前后分别核对订单数和价格。运行现有 28 项及新增测试、离线航线校验、编译、`pip check`，确认旧图交易路由仍未注册。
4. 启动 PostgreSQL，顺序执行 v008 首次应用与重复跳过、内部提案加真实 API 确认/拒绝、两账号隔离和 P1～P2.4c 回归。测试脚本使用临时旅客及会话并在成功后清理；核对两个原演示账号的订单、33,121 航班、15,374 报价、312 酒店/房型和 208 租车产品未被重置。最后停止容器并保留卷与备份。
5. 检查变更文件、`git diff --check`、忽略文件和敏感信息；在 P2.5a 分支提交已验收代码与说明，将真实迁移、测试、数据库状态和遗留问题写入《当前进度.md》。本阶段只完成分支验收；本机 `main` 合并和远端推送各另出计划、另待确认。

## 完成判据与失败处理

- `flight_book` 卡片显示的班次、当地时间、政策和模拟金额均可从数据库重算；未确认不新增订单，确认后行程与结果一致；拒绝、过期、越权、报价变化均不写入。
- 同一动作重复确认只返回同一订单；两个不同动作并发订同一旅客同一班次至多成功一笔。原五类动作及 P2.4c 产品查询保持可用，数据库重启后结果仍可读。
- 迁移/测试失败时停止实施，保留数据库、备份和现场，分析修复；已应用迁移需要后续新版本修正，不重写旧版本。不强推、不清卷、不自动合并或推送。
