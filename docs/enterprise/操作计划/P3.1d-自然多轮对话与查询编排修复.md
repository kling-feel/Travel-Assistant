# P3.1d：自然多轮对话与查询编排修复操作计划

> 编写日期：2026-10-20｜状态：用户已确认实施，并要求本轮通过现有阿里云搜索提供有来源的天气查询；本计划不授权数据库重置、主线合并或推送。

## 1. 触发问题与已核实原因

旅客在真实页面连续提出行程状态、上海出发的跨国旅行、中文城市及相对日期航班／酒店查询、机场酒店和天气问题。当前答复重复追问、把所在地当推荐目的地、把已取消订单仍列作当前行程，并将查询不到的房型直接说成没有供给。

- 当前 `.env` 的公开配置标识为 `AI_PROVIDER=deepseek`、`AI_MODEL=deepseek-flash`；仅凭标识不能断定供应商底层版本。温度为 0 不是这些固定话术的主要原因。
- `graph_chat/controlled.py` 每轮只要求模型返回一个 `intent/params/answer` JSON；图随后只走一个查询节点或一个固定回答节点，没有读取查询结果后的模型组织答案。最近对话仅以文本拼入提示词，没有可靠的来源地、目的地、日期、待澄清字段状态。
- 航班查询要求模型给三字机场代码和 ISO 日期，酒店查询要求数据库英文城市名及完整日期；`services/agent_reads.py` 不负责中文城市／多机场／“明天、后天、大后天”的规范化。`find_hotels` 精确比较英文城市，未转换的“上海／伦敦”会得到空结果。
- 推荐器只检测消息中是否出现某城市；“我在上海，想去其他国家”把上海误认为目的地。中国国家名加推荐词的特殊规则又会把“我人在中国，去其他地方”继续解释成中国境内推荐。已取消订单可在行程历史中查到，但当前行程答复没有按有效状态分组。
- 本机源样本中上海有浦东／虹桥两机场，伦敦有三机场，存在 `SHA → LGW` 的 Scheduled 航线；从上海也有多座境外直达城市。酒店产品生成器为可达机场生成房型。因此这组对话不能仅凭“无结果”推断数据缺失；具体 2026-10-22 是否有可订班次仍须按正式库和日期核实。
- 阿里云检索当前仅用于经典地点推荐中的候选／来源核验，不提供航班库存或天气实况。用户已明确要求本轮把该联网 API 用于天气查询；搜索结果需要比地点推荐更严格地核对城市、预报日期、发布时间、来源与时效，不能把普通网页摘要当权威实况。

## 2. 目标与边界

让用户按自然中文补全条件，助手能区分“我在哪里”“我要去哪”、承接最近查询条件，调用本人订单和正式产品数据，针对实际结果给出清楚的中文答复。所有金额、班次、房型、订单状态和交易规则仍由确定性服务核实；模型不得直接写订单。新增／修改／取消保持逐笔确认。演示航线和酒店不冒充实时供应商库存。

本阶段同时接入阿里云联网天气查询。单次请求只发送公开城市和日期，不发送旅客、行程、订单或密钥；只采用能明确核对城市、目标日期和发布时间的气象来源，结构化引用保留来源与检索时间。搜索结果不足时明确降级，不编造温度、降水或天气状态。若 GlobalBasic 实际返回质量长期不足，后续再评估专用气象 API，不用降低证据门槛换取表面答复。

## 3. 分步实施

### A. 记录真实失败与数据边界

1. 重读三份核心文档、核对工作区与 8000 服务，保留现有数据库和聊天记录；只读核对用户这组会话的订单状态、确认动作历史、演示基准日、上海—伦敦目标日期的班次，以及两城该日期的酒店供给。不要重置或覆盖用户正在看的数据。
2. 将用户原话做成脱敏、可重复运行的回归脚本。记录每轮模型 JSON、规范化参数、工具结果、最终答复和是否产生动作卡；日志只保留必要字段，不记录密钥和完整隐私内容。

### B. 建立明确的对话状态与参数规范化

1. 在会话内保存有限的结构化状态：当前任务、出发城市／机场、目的城市／机场、日期范围、最近候选及正在追问的条件。新消息先判断是在补全、改题还是推翻旧条件；“我在上海”记录为所在地／出发地，不自动成为推荐目的地。已取消／已拒绝的对象不能沿用为有效行程。
2. 由服务端对中文／英文城市、机场别名、相对日期做规范化。相对日期以当前演示日或本机真实日期的明确规则解析，并显示计算后的具体日期；跨城市按出发机场当地日筛选。一个城市多机场时汇总受控数量的机场组合及候选，显示实际起降机场；无直达结果时说明当前模拟网络与日期的边界，不捏造中转。
3. 先校验模型返回的结构化字段，再执行只读查询；字段缺失时只追问真正缺失的项，保留已知条件。无结果要区分：未识别地点、超出可查询时间窗、航线不存在、指定日期无班次／房型、查询服务异常。

### C. 改造回答编排和用户体验

1. 模型负责理解请求与组织有证据的自然回答；工具负责事实。允许一轮内完成受控的多项只读查询，再将短、带类型的结果交给回答层。输出前复核订单、价格、时间、地点及政策事实是否来自工具；无依据不输出肯定陈述。
2. 行程区分“当前有效”“历史／已取消”。对“我现在还有行程出发吗”直接回答是否存在未来已确认航班，再按需列出取消历史；待确认卡与已确认取消要分别说明，避免把卡片生成说成取消成功。
3. 目的地推荐按出发地、目标区域／国家和偏好筛选本演示航班可达城市。对“上海去其他国家”先给少量确实从上海可达的境外选项及理由，地点介绍仍只引用已审核目录；对未指定目的地的推荐可合理给选项，不强迫用户先选城市。当前所在地、已取消行程不得凌驾于用户本轮的出境意图。
4. “哪个机场有酒店”可回答本演示网络中有酒店产品的机场范围，结合最近讨论的上海／伦敦缩小范围，并追问入住日期以查询具体房型。天气节点通过阿里云 GlobalBasic 检索公开城市与目标日期，严格筛选可核查气象来源、发布时间与预报日期；不合格时说明未能核实。联网能力答复准确区分地点／天气检索与仅来自模拟数据库的机酒库存。
5. 保持通用寒暄和离题短问可自然回答。删除把所有未识别旅行问题压成同一句“请说明业务类型”的粗粒度兜底；失败时给出下一步可补充的具体信息。

### D. 验收与发布边界

1. 用隔离库与固定模型测试原始逐轮对话、中文地名、多机场、相对日期、跨轮补全、改题、取消后行程、推荐出发地与目的地、空结果原因、错误模型 JSON、两个账号隔离及无确认不写入。天气测试覆盖可信来源／过期日期／错城／提示注入／API 故障，确认未合格时不输出天气事实。
2. 以当前本机正式库只读检查上述真实场景；需要做真实 DeepSeek 页面联调时，先确认现有订单状态和是否会产生卡片，优先拒绝测试卡，不自动确认任何订单。记录调用次数、耗时、模型响应成功率和费用估计；联网推荐可能产生阿里云费用，以控制台为准。
3. 回归九类交易、确认权限、动作幂等、来源审查和历史恢复；完成后更新《产品需求》《软件架构》和《当前进度》中的实际能力、测试结果和限制。只在当前功能分支提交实现与结果，不合并或推送。
4. 现有 G-16 发布方案先暂缓。P3.1d 验收后重写 G-16 的代码范围、安全核对、主线合并与 GitHub 同步步骤，仍由用户单独确认。公开文件、提交说明和标签遵守既有用词要求；密钥、日志和数据库备份不进入 Git。

## 4. 验收样例

- “我要从上海去伦敦”应保留起终点，仅问日期；接着“后天查航班”应解析日期并查询两城机场组合，若当日无班次则说明实际查询范围和结果。
- “去上海明天到后天”应承接酒店查询并规范化城市和入住／退房日期；存在产品时列出真实数据库候选，不把中文别名造成的空查询说成无房。
- “我在上海，要去其他国家旅行”应提供从上海可达的境外选项，不推荐上海本地地点；指定伦敦后可继续介绍伦敦已核查地点。
- 两张取消卡只有旅客逐张确认后才改变订单；“现在还有要出发的行程吗”应先回答未来已确认订单数量，历史取消单另列。
- “明天上海天气”应尝试阿里云搜索；只有同城、同日期且时效合格的来源才能给出预报并保留引用，否则明确说未核实。 “你能联网吗”应准确说明可进行地点与天气检索，机酒库存来自模拟数据库。

## 5. 停止条件与后续建议

如正式库与源样本不符、模型输出不能被安全校验、会话状态串到其他旅客、存在未经确认的写入或费用异常，停止对应联调并先修复。GlobalBasic 只提供网页检索，不能保证天气源及时、权威或结构化；若严格筛选后的真实联调无法得到可用预报，明确记录结果与下一步专用气象源建议，不假装查询成功。
