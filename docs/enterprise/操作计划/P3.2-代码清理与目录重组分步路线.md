# P3.2：代码清理与目录重组分步路线

> 2026-10-24 制定｜状态：P3.2a～P3.2d 已在本地功能分支完成；各步结果见[当前进度](../当前进度.md)，G-17 发布另行确认。

## 1. 目标与已核对的现状

P3.1 已发布。下一阶段先让仓库呈现清楚、可维护的开发结构，再规划演示日期更新和云服务器部署。保留 FastAPI、LangGraph 主助手与业务专门助手、PostgreSQL、现有旅客页面及九类逐笔确认交易；不改变用户可见的业务规则。

当前注册入口 `main.py → api/routers.py → api/travel.py → graph_chat/controlled.py`，未注册旧 `api/graph_api/` 与 `api/system_mgt/`。仓库同时保留旧图、SQLite 写工具、旧用户表、历史小样本、约 55 个脚本和约 94 份企业文档；根目录还有两份各 114,442,240 字节、未纳入 Git 的原始虚构 SQLite。旧代码使读者难以分辨真实入口，旧导入脚本误运行还可能覆盖正式演示数据。删除前须逐项核实引用，不能仅凭文件名判断。

旅客明确要求：**历史计划、规划和进度内容全部保留**；已完成资料可归档并修复链接。两份原始 SQLite 移入 Git 忽略的 `data/source/` 保留，不提交、不导入正式库、不删除。

## 2. 目标目录与保留边界

目标是让仓库根目录主要保留 `README.md`、`main.py`、`compose.yaml`、环境配置样例、依赖声明，以及 `travel_assistant/`、`migrations/`、`scripts/`、`tests/`、`data/`、`docs/`。应用包建议逐步形成：

```text
travel_assistant/
  api/             登录、本人会话、只读查询、动作确认
  agents/          当前受控主助手与专门助手
  services/        价格、政策、候选、交易、行程、推荐等确定性逻辑
  db/              当前模型和数据库连接
  core/            配置、身份与共享错误处理
  web/static/      同源旅客页面
migrations/         原版本迁移，历史版本不改写
scripts/            当前可执行的初始化、导入与核验命令
tests/              当前能力的单元与接口／交易回归
data/fixtures/      可交付、去个人信息的虚构样本
data/source/        本机原始 SQLite，Git 忽略
docs/               当前入口、操作指南及完整历史资料
```

这只是目标结构，不在一轮中机械搬移。`main.py` 保留简单启动入口；数据库表、迁移版本、API 路径和页面地址不因整理改变。原始 SQLite、`.env`、备份、费用流水和用户当前订单不进入 Git。

## 4. 推荐的实施边界

- 先缩减旧代码，再移动当前模块。若发现文件在当前路径、测试或数据再生成中仍被引用，先替换或保留，不能让旧导入悄悄指向空模块。
- 历史文档先通过导航整理，不搬动、不删正文；以后若需要物理归档，另拟文件和链接迁移计划。已发布 Git 历史不改写。
- 整理期间不重置、迁移、平移或写入正式 5433 数据库；不调用付费模型／联网搜索。若需要数据库级回归，另用隔离环境并先核对端口与备份。
- 基线是 G-16 的 228 项自动化、两日期全航线样本、页面语法、依赖与正式库只读状态。每一步记录保留、新增与有意删除的测试覆盖，不要求机械保持测试数量。
- 目录整理完成后，另拟演示日期更新与部署计划；当前正式库含用户操作后的订单与会话，不能静默重置。
