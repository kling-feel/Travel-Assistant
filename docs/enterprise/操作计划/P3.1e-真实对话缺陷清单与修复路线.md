# P3.1e：真实对话缺陷清单与修复路线

> 编写日期：2026-10-21｜状态：缺陷基线；第 1、2 步及第 3 步中的 P3.1e3a 已按独立计划实施，自然答复与地点中文展示另行规划。本文件本身不授权重置数据库、合并主线或推送。

## 1. 诊断依据与边界

用户提供了同一页面的完整对话，覆盖行程、天气、上海至伦敦航班、机票预订与落地酒店、上海酒店和租车、附近景点。本次重读《产品需求》《软件架构》《当前进度》，只读核对当前 `feature/p31-traveler-ui` 的对话图、参数规范化、候选选择、交易提案、查询和页面。将用户原话交给纯解析函数复现，不连接正式数据库或调用付费模型。检查时本机 8000 端口没有监听，无法确认该段对话的服务进程版本或逐轮原始请求；一条回复与当前源码的条件分支不一致，须在下轮先核实。

以下“观察”直接来自用户对话；“代码证据”指当前源码的确定性行为；“风险”是据代码推断、尚未在用户会话中观察到的可能后果。127 项既有测试通过，但没有覆盖这条完整旅客旅程，也不能证明交易对话可用。

## 2. 缺陷清单

| ID／优先级 | 观察或风险 | 当前代码证据／原因 | 期望行为 |
| --- | --- | --- | --- |
| D01／阻断 | 多次明确说“预定机票”，始终没有确认卡 | 意图守卫和只读编排主要识别“预订”，漏掉常见“预定”；原话“我要预定最早的从上海到伦敦的机票”被解析为只读航班查询 | 统一预定／预订／订票等同义表达；明确交易请求必须进入受控提案流程，缺条件时准确追问 |
| D02／阻断 | “预定最近的从上海到伦敦的酒店”被回答为航班加酒店两项查询 | `read_request` 的组合只读短路发生在模型路由前；排除交易词的规则漏掉“预定” | 写入意图优先于只读捷径；混合任务分别识别订票、查酒店或订酒店 |
| D03／阻断 | “我要在上海附近租车，明天用大后天还车”重复返回酒店 | 上一任务为 `hotel_search` 时，只要新句含城市／日期且非航班，就会沿用酒店上下文；没有租车的同等级规范化分支 | 新租车任务立即切换上下文，保留上海和取还日期，只追问缺失的当地取还车时刻 |
| D04／高 | “就这个航班”“前面说的机票”不能稳定承接已展示候选 | 检查点只保留有限的只读条件；交易参数与只读上下文分离。候选解析只认近四轮引用中的序号、唯一候选、最便宜／酒店最近或明确 ID | 为当前任务保存候选 ID、机场、当地日期、报价版本和选择状态；指代只能绑定当前有效候选，并在建卡前重查 |
| D05／高，安全风险 | 旧航班／酒店候选或日期可能被带进新提案 | `recent_references` 按类型从近四轮找第一组；`prepare_actions` 用整段最近用户发言做日期依据，不限定当前任务。用户对话尚未生成卡，风险来自源码 | 候选和日期按任务及本轮明确条件绑定；冲突或过期时追问，绝不为旧条件生成看似合理的卡 |
| D06／高 | 已知 10 月 25 日是最近可查日期，却仍要求用户提供日期；“最早什么时候”无法直接完成 | 航班只读查询必须有单日 `travel_date`；最早／最近跨日期窗口查询未实现，既有建议日期也未形成可选择候选 | 在受控未来窗口按出发机场当地时间搜索真实最早可订班次，说明直达及日期范围；再让旅客选择／确认 |
| D07／高 | “预订机票，顺便找落地附近酒店”只得到酒店缺条件，机票意图丢失 | 单轮模型只能选一个路由；交易节点即便查两项，提案阶段目前对计划列表整体回滚；没有持续的多任务状态 | 对可独立完成的机票先生成待确认卡，酒店只读查询按落地机场继续；酒店入住晚数未定则仅追问酒店，不阻断机票卡 |
| D08／高 | “明天和后天都要住”“住两晚”只沿用一天的酒店日期 | 日期解析把“明天、后天”作为入住、退房两天；没有住宿夜数语义，后续“住两晚”不更新退房日期 | 若旅客明确两晚，入住 10 月 22 日应退房 10 月 24 日；回答及确认卡显示夜数与总额 |
| D09／高 | “最贵的酒店”“贵的那个车”只重复列表，不能选中 | 酒店和租车默认按价格升序最多展示 3 个；候选选择仅支持“最便宜”，不支持“最贵”，且未区分全部可售与已展示范围 | 在明确城市／日期和产品类型后按全部符合条件的产品排序，说明排名范围；选择后仍逐笔确认 |
| D10／高 | 租车“明天用大后天还”未继续追问时刻；“两天”没有处理 | 租车只读条件和交易时刻是两套参数；当前服务可查日期但预订须有带当地偏移的具体取还时间，缺少跨轮补全 | 保留日期，询问取还车当地时刻；计算实际计费日数、总额和取还车地点后生成卡 |
| D11／中 | “我附近有什么酒店／景点”反复要求城市 | 上下文没有可靠的旅客当前所在地、目标城市与落地机场的区分；推荐又要求目的地在本轮明说 | 基于旅客本轮声明的“我在上海”和最近任务澄清地点；若上海与伦敦都可能，明确问“上海附近还是伦敦落地后” |
| D12／中 | “最近有什么行程安排”仍逐条列出已取消机酒 | 当前行程快捷判断只覆盖“现在／还有／要出发”等词；“最近”落入列出全部订单的历史模板 | 先回答未来／进行中的有效安排，再把已取消订单单列为历史，不让旅客误以为仍有行程 |
| D13／中 | 回答显得像表单，一再重复缺条件，无法推进任务 | 模型主要被当作单次 JSON 意图路由；事实答复来自固定模板，查询后没有受控的下一步规划或自然语言组织 | 让模型基于结构化证据组织有限自然答复，并验证订单／日期／金额／政策事实；追问只针对真正缺失的信息 |
| D14／中 | 景点显示英文名称，豫园被标成“自然主题”，与中文旅客体验不一致 | 地点目录及主题字段直接进入模板，推荐器不继承明确的当前城市 | 对目录补中文展示名及主题人工审查；结构化来源继续保留，不以无来源自由生成替代 |
| D15／诊断 | “我要预订这个航班”对应的固定“不会自动重试订单操作”答复无法从当前源码的该原文分支推出 | 当前源码的该固定句只在模型输出 `transaction` 且**本轮文本不含**“预订”等词时返回；用户引述的原文含“预订”。检查时 8000 无监听 | 下轮先记录运行代码提交、请求原文、模型意图 JSON 和服务端路由结果的脱敏轨迹，核对是否为旧进程／不同输入／会话重放；不凭猜测归因 |

天气回答在本次样本中成功，并非这一轮的主要缺陷。现有逐笔确认门槛也没有被绕过；但“没有生成错误订单”不等于“能完成用户授权的订票”。

## 3. 建议实施顺序与验收门槛

### 第 1 步：可复现的诊断与交易路由修复

在隔离数据库和固定模型回放用户原话，并用少量真实 DeepSeek 对话核对实际 JSON 与路由。记录脱敏的输入、任务状态、查询结果和动作卡状态，不保存密钥。先修 D01～D05、D15，并完成 D07 的基本“机票预订＋酒店只读查询”：统一交易表达、先保护写意图、按任务隔离上下文与候选、限定日期依据。验收“预定 10 月 25 日已展示航班”和“预订这个航班”都能生成**正确目标**的待确认卡，确认前订单不变；缺酒店信息不得阻断已明确机票卡；旧候选、跨账号和冲突日期不得建错卡。

### 第 2 步：真实查询与选择能力

修 D06、D08～D10：按日期窗搜索最早可订航班；补齐夜数语义、最贵／最便宜选择与租车当地取还时刻。核对最早是全窗口最早而非第一页最早、最贵是全部符合条件的产品而非已展示三项中的最高；报价和夜数由数据库与服务计算。交易卡仍须逐笔确认。

本步拟再拆两次：先按 [P3.1e2a](P3.1e2a-最早航班与待确认卡复用.md)处理最早航班与 P3.1e1 遗留的重复待确认卡；住宿、价格选择和租车时刻另写 P3.1e2b 计划，分别确认后实施。

### 第 3 步：混合任务、位置与自然答复

修 D07、D11～D14：机票预订与酒店查询分任务推进，落地酒店绑定目标机场和当地到达日期；“附近”来源可解释，不明则定向追问。当前行程与取消历史分开展示。模型只能依据工具结果组织答复，输出前核对地点、日期、金额和状态；地点目录中文名与主题人工复核。

### 第 4 步：整段旅程验收与发布决策

把用户提供的整段对话改为端到端验收脚本：包含交易同义词、跨轮指代、任务切换、最早／最贵、两晚、租车取还车、落地附近酒店、当前位置景点及天气。固定模型、真实 DeepSeek、两账号、重复轮次、模型错误、搜索失败、订单确认／拒绝和数据库重启均需覆盖。明确的订票请求若未生成卡，或生成与本轮意图不符的卡，视为失败；未确认时所有订单必须不变。记录成功率、成本与残留缺陷，更新三份核心文档和《当前进度》。G-16 主线合并及 GitHub 同步排在验收通过后，仍另行确认。

## 4. 需要与用户共同确定的产品细节

1. **已由用户确认**：“订机票并找酒店”可先给准确的机票待确认卡，同时继续只读查酒店；酒店预订在明确入住晚数与房型后另给卡。两卡各自确认，不让缺酒店条件阻断机票。落实步骤见 [P3.1e1 独立操作计划](P3.1e1-交易路由与任务状态修复.md)。
2. “附近”：建议优先采用本轮明确的“我在上海”或已选航班落地机场；两处都可能时只问一次地点，不使用设备定位或臆测人在何处。
3. 旗舰演示航线频次：上海至伦敦当前样本在 10 月 22 日无班次，最近 10 月 25 日才有。建议先把查询与解释修好；是否另外增加确定性、明确标记为虚构的高频班次，作为后续独立的数据方案决定，不在本轮静默改库。

## 5. Git、数据与停止条件

本文件为诊断和建议，不执行实现。若用户确认修复方向，再为第 1 步单独写细化操作计划，开工前重读三份核心文档并核对功能分支和正式库状态。先在隔离库验证；正式库只读联调不得确认任何动作卡。任何越权、错对象卡、未经确认写入或不能解释的版本差异立即停止对应联调。修复结果提交功能分支；本机 `main` 合并及 GitHub 推送继续单独征求确认。公开内容避免用户禁止的开发工具品牌字样，密钥、原始对话日志和数据库备份不进入 Git。
