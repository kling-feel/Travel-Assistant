# P3.1a：旅客页面中文化与报价展示操作计划

> 编写日期：2026-10-20｜状态：用户已确认并在功能分支实施、验收；主线合并与推送仍须单独确认 G-16。

## 1. 背景、目标与已确定选择

P3.1 页面已在 `feature/p31-traveler-ui` 验收，尚未并入本机 `main`。当前页面反复出现“演示／模拟／虚构”和“演示计价单位”，查询表单要求手填 `HAM`、`BSL`、`Basel`，行程及卡片以英文城市、机场三字码和内部 ID 为主要信息。这影响旅客理解，也不利于作品展示。

用户已确认：金额以 **人民币样式**展示，例如 `¥4,258`，页面统一说明其为示例报价；中文城市、机场名为主，航班号与机场代码缩小放在详情里供核对。本阶段处理所有旅客直接可见的页面区域，包括登录、查询、对话周边、本人行程、候选、确认卡、操作历史与窄屏。现有整数价格只改变展示含义和格式，不重算报价、改写订单或假装真实收付款。

产品仍是虚构平台。登录页和工作台各保留一处清晰、克制的常驻说明，例如“作品体验环境｜行程与报价为示例数据，不产生真实预订或付款”；每笔确认前再明确提示没有真实付款、退款或供应商操作。API 中的 `simulation_notice`、规则标识与交易审计保留；不把安全边界从实际确认流程中拿掉，不暗示真实航司或平台合作。

## 2. 改动范围与实施顺序

1. **开工核验**：重新读取三份核心文档、本计划、P3.1 和 G-16 计划；核对工作区、功能分支、本机与远端 `main`。保留已验收的 P3.1 提交为恢复点。只在现有功能分支继续开发，不启动或重置正式演示数据库。
2. **中文地点目录**：从已人工确认的 95 个中文城市别名出发，补齐航班资料中其余机场所属城市的中文名，并为现有 115 个机场建立可核对的中文展示名。中文名与三字码、数据库英文名建立确定性映射，不由模型临时翻译。覆盖率检查要求现有机场 115/115、可达城市 95/95；发现同城多机场时必须显示足够信息以区分，未知代码保留原值并明确兜底。避免在前后端复制两套相互冲突的映射。
3. **中文查询入口**：提供登录后只读的地点选项，页面按中文城市／机场名称搜索或选择，实际请求仍传既有机场三字码和数据库城市值。机场同名或同城多个机场时让旅客能区分；酒店和租车也不用再要求英文城市名。旧 API 的代码参数继续兼容；新增只读字段或接口仅用于展示，不向浏览器开放任何交易写入能力。
4. **旅客可见信息整理**：航班候选和本人机票以“中文出发地 → 中文目的地、当地出发／到达时间、报价”为主，现有虚构航班号 `SIM-…` 和三字码放在次级详情，绝不伪装成真实航司航班号。酒店、房型、租车类型、地点与已生成的产品名称改为自然中文展示；订单号、产品 ID、规则 ID 和版本保留在可展开的核对详情，不在卡片标题堆叠。新旧金额、需补差价、可退金额及取消费分别用 `¥`、千分位和明确标签表示；零金额显示 `¥0`，空值显示 `—`，不做汇率换算。距机场数值仍明确为近似直线距离，不能写成驾车距离。
5. **文案与对话统一**：清理页头、登录、空状态、提示、查询结果和历史中的重复“演示／模拟”等词，采用“查询航班”“参考报价”“待确认”“已完成”等自然表述。确定性助手查询答复同步使用中文地点、清楚的当地时间和人民币样式示例报价，减少让旅客手输英文代码的提示。模型答复及已存历史不得靠不受控的字符串替换改写事实；版本化的虚构政策正文与 API 安全声明保持原义，若需要修改规则正文，必须另立政策版本和迁移计划。对话和页面仍保留足够的示例数据说明。
6. **视觉及交互验收**：对桌面和手机检查信息层级、卡片留白、金额对齐、长地名／长订单号换行、中文输入、键盘操作和对比度；避免依赖 CDN 或第三方字体。选择城市／机场后，查询结果、对话引用、确认卡和最终行程指向同一代码与订单，不允许仅换标签导致选错候选。前端继续以文本节点显示用户、模型和产品内容，不将未可信文本插入 HTML。
7. **回归和记录**：增量测试覆盖地点映射完整性、同城多机场、中文选择到旧 API 参数、金额格式、三种产品的候选／订单／确认卡展示和两张卡逐笔处理。运行完整自动化测试、两日期全航线校验、Python 编译、JavaScript 语法、依赖、文档链接及差异检查。用隔离数据进行浏览器桌面和手机检查；确有必要才启动独立测试库，先核对或备份，测试后清理，不修改正式演示库。本阶段默认不调用 DeepSeek 或付费联网搜索；若浏览器闭环必须新增真实模型联调，将先报告调用范围与预算。将实际结果写入《当前进度》，同步更新产品需求中的展示约定、架构中的地点展示契约和 README 操作示例。

## 3. 验收门槛

- 登录、工作台及逐笔确认前都能看清示例数据和无真实付款边界；主内容不再反复堆砌“演示／模拟”，金额没有“演示计价单位”字样。
- 旅客可以用中文选择地点查航班、酒店和租车；115 个机场的显示名有确定性来源，航班、订单、卡片和详情的中文地点与原代码一致。
- `¥` 金额只代表既有整数示例报价；补差、可退、取消费与 API 计算一致，确认前后订单仍由服务端控制。航班号、三字码、订单／产品／规则 ID 可在详情中核对，不会被误认成真实供应商编号。
- 同城多机场、未知代码、长中文地名、窄屏、空结果与错误状态可读；原有两账号隔离、逐笔确认和浏览器安全处理不退化。
- 不新增数据库迁移或真实支付／库存接入，不改历史订单金额、报价算法、政策规则与已存对话内容。

## 4. 与主计划及 GitHub 的关系

本阶段插在 **P3.1 与 G-16 之间**。原 G-16 的发布范围和提交快照需要在 P3.1a 验收后重写；目前不能按旧快照直接合并或推送。完成 P3.1a 后先在功能分支提交中性说明的代码和验收记录，再更新 G-16 的确切提交、差异与检查结果，并将新版本给用户单独确认。只有 G-16 获确认且发布前复核通过，才快进合并本机 `main` 并普通推送 GitHub；不强推，不推送功能分支。公开文件、路径及新提交说明继续避免用户指定的旧工具品牌字样。

G-16 发布后回到 P3.2 主路线：优先补候选查询与对话的衔接、单轮多项只读问题、来源历史恢复，再制定固定展示脚本、Docker 本机启动和云部署说明的单独计划。每一步仍先给事前计划，获确认后执行，结果写入《当前进度》。
