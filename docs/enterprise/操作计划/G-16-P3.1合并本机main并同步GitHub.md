## 2. 用户确认后的执行步骤

1. **开工复核**：重新读取《产品需求》《软件架构》《当前进度》、本计划及已确认的 [发布规则](G-发布同步与公开内容规则.md)。确认当前工作区干净、分支末端、目标仓库地址和本机 `main`。运行 `git fetch origin`，再次核对 `origin/main` 是否仍为预期提交且是 P3.1 分支祖先；若远端新增提交或关系改变，暂停并重新给出整合方案。
2. **发布范围审查**：列出 `origin/main..feature/p31-traveler-ui` 的全部提交、文件和差异，核对没有额外改动。检查提交说明、作者与提交者、最新文件内容和路径均无用户要求避免的旧工具品牌字样；检查 `.env`、原始业务库、数据库备份、测试截图与费用记录未被跟踪。再次以本机已配置凭证值作不输出密钥内容的定向匹配，并检查明显的私钥／令牌形态。历史远端提交保留，不改写。
3. **合并前回归**：在功能分支运行完整自动化测试、两日期航线校验、Python 编译、`node --check`、`pip check`、文档相对链接与 `git diff --check`。核对 `/app`、`/api/v1/demo-state`、`/api/v1/locations` 和旅客路由可注册，旧图交易路由仍未注册。任何失败先修复功能分支并更新验收记录，不带故障合并。
4. **本机合并**：记录主线提交以便恢复，切换到 `main`，仅执行 `git merge --ff-only feature/p31-traveler-ui`。若不能快进，停止，不自动解决冲突或重写历史。合并后确认本机主线与功能分支提交／树一致。
5. **合并后回归**：在本机 `main` 重跑第 3 步的发布门槛。此步不需要启动或重置数据库，不会调用 DeepSeek 或阿里云搜索；P3.1 的独立实库结果由《当前进度》保存。若回归失败，停止推送，保留状态并先报告修复方案。
6. **同步 GitHub**：再次确认远端 `main` 未偏离第 1 步，执行普通 `git push origin main`。不使用强制推送、不推送全部分支或标签。用远端读取确认 GitHub `main` 与本机 `main` 提交相同，并检查公开最新文件树。若推送失败，明确记录本机已合并而远端未同步，先处理同步原因，不继续下一个主线阶段。
7. **记录实际结果**：将真实合并哈希、推送结果、检查项和数据库状态写入《当前进度》，形成中性说明的结果提交，再通过普通推送让该进度记录也在 GitHub `main` 可见；再次核对远端与本机相同。公开记录不写演示密码、API 密钥或本机绝对路径。
