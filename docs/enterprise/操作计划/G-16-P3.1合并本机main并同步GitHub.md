## 2. 用户确认后执行的顺序

1. 重读《产品需求》《软件架构》《当前进度》、本计划和[公开发布规则](G-发布同步与公开内容规则.md)。确认功能分支干净；独立验收脚本、一次性账号文件、备份、报告均位于 Git 忽略目录。只读检查 8000 API 和正式库 5433 的状态。若 8000 正由用户调试，不中断该进程；正式 PostgreSQL 不停止、不重置、不导入。
2. 获取远端最新 `main`，核对 URL、远端哈希与分支祖先关系。若远端新增提交、无法快进或工作树被其他操作占用，停止并给出新的整合方案，不自动解冲突或覆盖远端。
3. 列出 `origin/main..feature/p31-traveler-ui` 的全部提交、作者／提交者、路径及内容差异。逐项扫描新增提交说明、作者、路径和公开文本，确保不出现用户要求排除的工具品牌字样；既有已公开历史不改写。确认 `.env`、密钥、数据库卷／备份、临时账号、截图、日志与服务商账本都没有被跟踪。密钥比对只报告命中位置，不打印值。
4. 在功能分支运行完整自动化、两日期源样本校验、Python 编译、页面 JavaScript 语法、依赖及差异检查；只读复核正式库基准日、全量排程审计、账号／订单和临时记录计数。任一关键项失败即停止发布并修复，不以测试数量替代实际交易核对。
5. 记录本机 `main` 合并前哈希，切换 `main` 并仅作快进合并，核对合并后提交与功能分支一致。若不能快进，停止并让用户审阅新的方案。
6. 在本机 `main` 重跑发布关键检查，再次确认远端未移动后普通推送 `origin main`。不用强推、不推送其他分支或标签；读取 GitHub `main` 哈希核对一致。若推送失败，记录“本机已合并、远端未同步”，停止后续发布步骤。
7. 若 8000 空闲且正式库健康，在合并后的代码上启动本机 API，核对 `/health`、`/app`、登录和只读行程；若用户正在使用 8000，先保持其会话不动并另约启动验证。把实际哈希、检查和数据库状态写入《当前进度》，以中性说明单独提交并普通推送，再核对远端最终哈希。

## 3. 停止条件与确认边界

远端分叉、凭证或禁止字样命中、测试失败、数据库与验收基线不符、不可快进或推送失败时停止相应步骤。不得自动强推、改写公开历史、重置数据库或上传备份。用户确认 **G-16** 后才执行本机主线合并和 GitHub 同步；P3.1f4b 的确认只覆盖隔离恢复与页面验收。
