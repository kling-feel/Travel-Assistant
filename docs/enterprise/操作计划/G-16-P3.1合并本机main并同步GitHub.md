## 2. 用户确认后执行的顺序

1. 重读《产品需求》《软件架构》《当前进度》、本计划和[公开发布规则](G-发布同步与公开内容规则.md)。确认功能分支无未提交改动，备份及测试报告被 Git 忽略。记录当前运行中的 8000 API，合并前正常停止旧代码进程；不停止或重置 PostgreSQL。
2. 获取远端最新 `main`，核对仓库地址和当前分支关系。若远端新增提交、无法快进或发现其他人在使用同一工作树，停止并给出新的整合方案，不自动解决冲突或覆盖远端。
3. 列出 `origin/main..feature/p31-traveler-ui` 的全部提交、路径和差异。扫描本轮新增的提交说明、作者／提交者、路径、公开最新文件树与文档，避免用户要求排除的工具品牌字样；检查 `.env`、数据库备份、临时账号、截图、日志、服务商账本和密钥未被跟踪。使用本机密钥做只报告命中位置的定向比对，绝不打印密钥值。既有历史不改写。
4. 在功能分支再运行完整自动化、两日期源样本校验、Python 编译、页面脚本语法、依赖和差异检查；只读复核正式库基准日、排程审计、账号／订单和 0 临时记录。失败即停止发布。
5. 记录本机 `main` 合并前哈希。切换到 `main`，仅用快进合并功能分支，核对合并后代码树、哈希和功能分支一致。若不能快进，停止并交用户审阅新的合并方案。
6. 在本机 `main` 重跑发布关键检查；再次核对远端未移动后普通推送 `origin main`。不用强制推送，不推送所有分支或标签。读取 GitHub 上的 `main` 哈希确认与本机一致。若推送失败，清楚记录“本机已合并、远端未同步”，不继续下一阶段。
7. 在合并后的代码上恢复本机 API，核对 `/health`、`/app`、登录和只读行程。把实际哈希、检查结果和数据库状态写入《当前进度》，以中性说明单独提交并普通推送，再核对远端最终哈希。

## 3. 停止条件与确认边界

远端分叉、凭证或禁止字样命中、测试失败、数据库与验收基线不符、不可快进或推送失败时停止相应步骤。不得自动强推、改写公开历史、重置数据库或把备份上传。用户确认 **G-16** 后才执行本机主线合并和 GitHub 同步；P3.1e6 的确认只覆盖正式演示库更新。
