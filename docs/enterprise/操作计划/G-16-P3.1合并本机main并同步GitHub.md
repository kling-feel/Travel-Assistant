## 2. 用户确认后执行的顺序

1. **开工核对**：重新打开《产品需求》《软件架构》《当前进度》、本计划和[发布规则](G-发布同步与公开内容规则.md)。核对功能分支无未提交改动、`main` 与功能分支提交关系，以及 `git remote -v` 的目标仓库。识别并先停止本机 8000 API，避免切换代码期间仍用旧进程提供页面；不停止或重置数据库。
2. **获取远端与审查范围**：`git fetch origin` 后确认远端 `main` 与计划基线关系。如果远端新增提交、主线分叉或工作区有额外改动，停止执行并给出新的整合方案。列出 `origin/main..feature/p31-traveler-ui` 的所有提交、路径和差异；特别检查本轮搜索默认值与公开说明一致。
3. **公开内容与凭证检查**：扫描本轮提交说明、作者／提交者、路径和拟发布最新树，确保不出现用户要求避免的旧工具品牌字样；确认 `.env`、数据库备份、模型／搜索账本、日志与测试令牌未被跟踪。用本机已配置凭证值做只报告命中位置的定向比对，并检查明显私钥和长期令牌格式。既有历史不改写，旧远端历史不能通过本次普通推送抹除。
4. **合并前回归**：功能分支运行完整单元／集成测试、两日期完整航线校验、Python 编译、前端脚本语法、`pip check`、文档相对链接和差异检查；核对旅客 API 与页面路由，确认旧图交易路由不注册。检查当前正式演示库 `as_of` 与本机当天日期是否一致；若日期已跨天，只记录现状并单独按备份方案处理，不在合并过程中静默重置会话。失败即停止发布。
5. **本机快进合并**：记录合并前的 `main` 哈希，切换到 `main`，只使用 `git merge --ff-only feature/p31-traveler-ui`。不能快进时停止，不自动解决冲突、不重写提交历史。合并后核对 `main` 与功能分支树和哈希一致。
6. **合并后验证与 GitHub 同步**：在 `main` 重跑发布关键检查；通过后再次核对远端没有移动，执行普通 `git push origin main`。不用强制推送，不推送所有分支或标签。读取远端 `main` 哈希并检查公开最新文件树与本机相同。推送失败时记录“本机已合并、远端未同步”，保留可恢复状态并先解决原因，不继续其他主线阶段。
7. **恢复页面与记录结果**：在已合并代码上启动本机 8000 API，核对 `/health`、`/app`、登录及只读行程；不再次生成交易卡或付费搜索来重复证明已完成的 P3.1c 联调。将实际合并／推送哈希、检查结果及数据库状态写入《当前进度》，以中性说明单独提交并普通推送，使 GitHub 进度与本机一致，再核对远端哈希。

## 3. 验收与停止条件

- 验收：本机与 GitHub `main` 指向相同最终提交；公开最新树无密钥、备份及禁止字样；测试通过；本机页面可打开；演示订单仍保持原状态。
