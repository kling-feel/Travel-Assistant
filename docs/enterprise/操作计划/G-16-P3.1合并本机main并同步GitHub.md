## 2. 用户确认后按顺序执行

### A. 发布前核对

1. 重读《产品需求》《软件架构》《当前进度》、本计划和[公开发布规则](G-发布同步与公开内容规则.md)。核对当前分支、提交、工作区及用户是否正在占用 8000 页面；不关闭用户进程。只读核对正式 5433 数据库可用性、演示基准日、旅客和订单数量，不导入、不重置、不清理。
2. 刷新目标仓库的远端 `main`，核对仓库地址、最新远端哈希、本机 `main` 与功能分支的祖先关系。若远端已变化、不能快进或功能分支出现未验收的新改动，暂停，给出差异和新的整合方案。
3. 审核 `origin/main..feature/p31-traveler-ui` 全部新增提交的说明和作者信息，以及最终文件树、路径与公开文本。不得在新增公开内容出现用户要求排除的开发工具品牌字样；既有公开历史不改写。确认凭证、账号、原始聊天、数据库卷／备份、费用流水与日志没有进入跟踪文件。对已配置密钥只做本机比对，不打印密钥。发现公开内容或敏感文件问题时，先在功能分支修复并重新验收。
4. 在功能分支重跑完整自动化、Python 编译、前端语法、依赖、两日期全航线样本、文档链接与差异检查。复核旧图交易路由未注册，九类动作仍经本人待确认卡和服务端事务。正式数据库只读核对演示基准与可售窗口；不因代码发布自动平移日期。任何关键检查失败，停止发布并修复。

### B. 本机合并与远端同步

5. 记录本机 `main` 原哈希，切换到 `main`，仅执行快进合并。核对合并后 `main` 与已验收功能分支完全一致；不进行强制重置、变基或自动冲突解决。不能快进时停下并让旅客审阅新方案。
6. 在合并后的 `main` 再跑发布关键回归和公开内容检查。再次读取远端 `main`，确认它没有从 A 步核对的哈希移动；若移动，停止推送。
7. 普通推送 `main` 到目标 GitHub `main`，不强推、不推送功能分支或标签。独立读取远端哈希，确认与本机 `main` 一致。若推送失败，明确记录“本机已合并，远端未同步”，停止后续发布动作并查明原因。

### C. 发布后核对与记录

8. 在不干扰用户现有 8000 进程的条件下，确认合并代码的健康检查、登录、本人行程与页面静态资源可读；如 8000 被占用，用独立端口做只读冒烟检查或约定用户空闲窗口。演示数据过期则先报告重建方案，不在 G-16 里静默覆盖订单。
9. 把实际合并、推送哈希、测试结果、正式库只读状态、页面冒烟结果与遗留限制写入《当前进度》。进度文档使用中性公开文字，单独提交并普通推送后再核对远端最终哈希。若发布后发现重大缺陷，先保留证据，再拟定可审阅的修复提交或回退方案，不自行改写公开历史。
