# P3.1e4：完整旅程与重启验收操作计划

> 编写日期：2026-10-21｜状态：事前计划，等待用户确认。承接 P3.1e3c 和《真实对话缺陷清单与修复路线》第 4 步；本计划不授权合并本机 `main`、推送 GitHub 或重置正在使用的演示数据库。

## 1. 目标和当前依据

开工前重读《产品需求》《软件架构》《当前进度》和 P3.1e 缺陷路线。功能分支 `feature/p31-traveler-ui` 上已分别修复交易路由、最早班次、住宿夜数与价格选择、租车时刻、地点指代和中文地点展示；P3.1e3c 的 164 项自动化测试通过。这些分段结果还不能证明旅客从查询、选班次、查落地酒店、预订机酒车、确认或拒绝，到重新登录和服务重启的整段旅程可用。

本步使用用户此前提供的真实对话作为验收主线，核对助手是否理解自然表达、能推进下一步、生成**正确对象和金额**的待确认卡，并确保每笔写入只在本人明确确认后发生。验收结果决定是否进入 G-16 发布准备；若出现新的系统性缺陷，应记录并另立修复计划，不以某几轮成功掩盖问题。

## 2. 环境、数据和费用边界

1. 先核对分支、工作区、运行中的 API 端口、Docker 引擎及现有演示库的 `as_of`、订单和待确认动作；只读检查，不根据日期过期就自动重置。正式演示库及其 Docker 卷保留原状。
2. 为本次验收建立**独立的 PostgreSQL Compose 项目和命名卷**，使用独立宿主端口（建议数据库 5434、页面/API 8002，若占用则选空闲端口）。只在该隔离库运行迁移和全航线数据导入，演示基准日取实际开工日期；导入前按现有安全流程备份并核验隔离库。若 Docker 在受限终端不可用，先核对本机普通 PowerShell 与 Docker Desktop 的状态，不把 PATH／权限差异判作数据库损坏，也不删除既有卷。未能建立真实 PostgreSQL 隔离环境时，不以 SQLite 结果冒充重启验收。
3. 页面默认使用已配置的 DeepSeek 和阿里云 `GlobalBasic`。执行前只验证密钥**是否存在**，不打印值；搜索结果只用于有来源的只读资料，机酒车库存、金额、政策仍以数据库和确定性服务为准。原始令牌、个人输入、完整提供方响应和数据库备份只保存在 Git 忽略目录；公开文档仅写脱敏汇总。
4. 本步建议硬上限为 **40 次 DeepSeek 调用尝试、25 次阿里云搜索尝试**，包含失败、重试和修复后回放；每次请求计数，达到任一上限立即停该类调用并报告未测项。模型费用按实记 token 和账单，建议以 ¥8 为本步模型费用停止线；阿里云 `GlobalBasic` 专属单价未显示，因此不声称人民币总额上限。出现异常扣费或密钥／响应泄露风险立即停止付费联调。先用固定模型完成大部分回归，真实模型只验证关键自然对话，避免重复计费。

## 3. 执行顺序

### A. 基线与可复现脚本

1. 将用户的典型旅程整理为逐轮验收矩阵，记录每轮输入、继承的任务状态、预期查询、候选、卡片、订单和来源。固定当前日期及机场当地时区，避免把旧对话里的 2026-10-25 当成永远有效的日期。
2. 用固定模型在隔离库先回放：查未来有效行程；从上海到伦敦找最早可订直达航班；“就订这班／预定前面的机票，顺便找落地酒店”；补充到达日和两晚、选择最高价房型；切换到上海租车并补齐取还车当地时刻、选择最高价车；再询问当前位置经典地点、政策与可核查天气。明确验证“最近”“前面的”“落地附近”“最贵”“明后天住两晚”等指代和任务切换。
3. 每轮同时比对数据库事实、服务端候选 ID、对话文字和结构化引用。明确订票却没有卡、卡绑定旧日期／旧候选、把伦敦酒店当上海酒店、展示金额与卡不一致，均视为失败；不得只凭 HTTP 200 判通过。

### B. 交易与安全边界

1. 对机票、酒店、租车分别走“查询→选定→待确认卡→本人确认”的完整路径；在固定模型和服务端回归中覆盖九类既有动作：机票预订／改签／取消、酒店预订／改期／取消、租车预订／改期／取消。真实模型重点走旅客主线里的机票、落地酒店与租车预订，并抽查用户原话里的机票／酒店批量取消须拆成独立卡。补一笔拒绝和一笔过期／冲突。每张卡核对产品、机场／地点、当地日期时间、人数或夜数、金额、规则、有效期和归属。确认前查询订单与审计，证明无写入；确认后逐笔核对状态、版本、模拟金额和审计。
2. 两个账号和多个会话交叉测试：账号乙不可查看或确认账号甲的卡或订单；同一个请求键重复发送应返回同一轮结果，卡复用不得跨账号、跨会话或越过有效期。重复确认不得二次写入。用户口头说“确认”不能代替页面上对指定卡的确认动作。
3. 混合任务中，机票卡可先给出，酒店缺晚数时只追问酒店；酒店卡不能替机票卡确认。天气、地点推荐或外部搜索结果不能触发交易写入。模型错误或伪造的“已预订”文本不得改变服务端订单事实。

### C. 真实助手页面与故障恢复

1. 在独立 API 地址用真实 DeepSeek 走一遍上述核心连续对话，并让阿里云搜索按默认开启状态参与有来源的推荐／天气查询。记录实际模型和搜索请求数、可核查引用、无结果或超时的降级表现；不能把旧目录审查日说成实时开放信息。
2. 用浏览器核对桌面与窄屏页面：中文城市、机场与地点名、人民币格式、统一示例说明、候选选择、卡片详情与逐笔确认／放弃、状态刷新、加载和失败提示。截屏仅存忽略目录并脱敏，不把测试账号和响应原文提交 Git。
3. 在隔离库保留一张有效卡和一笔已确认订单后，依次重启 API 与隔离 PostgreSQL；重新登录并恢复同一会话，核对卡、轮次、检查点、订单和审计均未丢失。随后完成该卡一次确认，再重复请求验证幂等。重启失败要区分端口占用、数据库未就绪、检查点错误和令牌过期，不自动清空数据库。
4. 断开模型、让搜索超时／无结果、提供越权动作 ID 或已变化报价，验证明确降级、无凭空推荐／金额、无未确认写入；恢复服务后可从安全状态继续。

### D. 回归与结论

1. 修复本步**直接暴露且范围明确**的缺陷，补有区分力的回归；若需重做对话架构、数据供给或公开 API 契约，先形成单独计划与取舍，不在验收中暗扩范围。修复后重放失败场景并重跑全套测试、Python 编译、页面脚本语法、依赖、全航线数据核对与差异检查。
2. 形成逐场景通过／失败／未测表，附关键脱敏证据、卡与订单前后状态、重启结果、模型及搜索请求数、实际可查费用、残留缺陷和用户可复现步骤。更新《产品需求》《软件架构》《当前进度》及 README 中确有变化的部分，只在功能分支提交。
3. 若全部阻断项通过，再**重新编写**已过期的 G-16 合并与 GitHub 同步计划，列出最新测试和数据库状态，单独交用户确认。P3.1e4 自身不合并本机 `main`、不推送远端。

## 4. 验收判定与停止条件

- 明确的机酒车预订请求能推进到正确的卡；缺少条件时只问缺少项。三类订单在确认前不改变，确认后只改变本人选定的那一笔；拒绝、过期、越权、重复确认和模型／搜索故障均不产生额外写入。
- 最早航班、最贵产品、两晚、当地取还时刻、落地酒店、当前位置和多轮换话题的答复与数据库一致；有效行程不把已取消订单当成即将出发。地点引用中文为主且可追溯；天气无法核实时明确说明。
- 页面桌面与窄屏可完成至少一笔卡片确认和一笔放弃；真实 DeepSeek 连续旅程无阻断性误解；隔离 PostgreSQL 和 API 重启后会话、卡、订单与审计一致。任何未完成环节标为未验收，不把单元测试通过等同整段旅程通过。
- 出现错人／错订单卡、未经确认写入、密钥外泄、真实库被误写或无法解释的数据差异，立即停止相应联调，保存脱敏证据并说明恢复方案。不得通过重置正式库、删除 Docker 卷或强制 Git 操作消除失败证据。

## 5. 给用户的操作交付

实施后提供可照抄的 Windows 启动、登录和验收步骤，明确隔离页面地址、如何查看／确认卡片及如何停止**本次隔离**服务。交代正式 8000 页面与隔离 8002 页面各连接哪个库，防止用户把测试订单误当正式演示订单。验收结论和后续建议先写进《当前进度》，再提出独立发布方案。
