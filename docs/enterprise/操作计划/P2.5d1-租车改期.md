# P2.5d1：租车改期操作计划

> 编写日期：2026-10-18｜状态：待用户确认；本文件只记事前方案，实际结果写《当前进度.md》

## 目标与边界

在现有 `rental_book`、`rental_cancel` 之上增加 `rental_change`，让旅客修改**本人已确认租车订单**的取车和还车时间，车辆产品不变。改期仅在原订单取车时刻前确认；新时间在未来、先取后还，且符合现有约 30 天演示窗口和产品可用期。按原有机场当地时区和实际经过时间每开始 24 小时计一日，模拟差额为新总价减旧订单总价；正数模拟应补、负数模拟应退，不收改期费。所有写入仍要旅客确认具体动作卡。

本步骤只补租车改期、版本化规则、API 读取兼容及回归，不增加游览产品/订单，不接入模型或页面，不调用真实供应商和支付，不推送远端。**不需要新的外部 API 密钥。** 本机 `main` 当前为 `35d093f`、`origin/main` 上次核对为 `fbb02bb`；实施前重新核对。

## 拟修改范围与顺序

1. 重读《产品需求》《软件架构》《当前进度》和本计划，检查工作区、分支、数据库容器、现有租车订单及待确认动作。只读盘点后在 Git 忽略目录保存 `pg_dump`，用 `pg_restore -l` 核验；若数据库有非演示旅客或未处理动作，先停下分析，不进行重置。
2. 从干净本机 `main` 建短期 `feature/` 分支。新增 v011 迁移，扩展待确认动作约束以接受 `rental_change`，追加租车政策 v3；保留 v2 供历史迁移与审计，**不改写 v001～v010**。此前按 v2 创建、尚未确认的租车卡在 v3 生效后按现有版本机制失效，需重新生成。
3. 复用 `services/rentals.py` 的产品、IANA 当地时间、夏令时、计费日与可用窗校验。提案参数使用 `order_id`、`expected_version`、新取车和还车时间；服务端从本人订单固定 `product_id`，不接受客户端更换产品、价格或旅客。卡片显示原/新当地时刻、计费日、总价、差额、规则版本和有效期。
4. 确认事务重新锁定并核验本人订单、原取车时刻、订单版本、政策版本、新时段、产品可用性和新报价；确认后仅更新该租车订单时间、计费日、总价与版本，保存结果及审计。重复确认返回已有结果；并发改期/取消两张卡只能有一个成功。若请求仍是同一时段，或与本人已有的**同车辆产品、完全相同时段**的有效订单重复，给出清楚错误，不生成无意义或重复订单。
5. 更新虚构政策文本、README、迁移/重置兼容、单元测试和实库验收脚本。测试覆盖原取车截止、新取车未来、跨时区与 DST 不存在/歧义时刻、价格补退、跨账号、拒绝/过期/重放、双卡竞争、应用及数据库重启持久化，并顺序回归现有八类动作。
6. 验收前后核对正式数据计数和演示订单关联；清理临时验收记录，停止容器但保留卷与备份。`git diff --check`、编译、`pip check`、两日期离线样本和全部自动化测试通过后，在功能分支提交代码与《当前进度》结果。另拟本机合并计划并取得确认；本步骤不自动合并或推送。

## 通过条件与失败处理

- 未确认时订单不变；本人确认一次只改目标订单，金额与当地时间可解释，版本递增，历史动作和政策可追溯。
- 原取车时刻或产品可用性变化、价格或政策变化、订单版本冲突、越权、过期及并发竞争均不产生不完整写入；旧八类动作继续通过。
- 迁移首次运行成功、重复运行跳过，现有账号/订单/航班/酒店/租车产品不被清空。实库失败时保留现场与备份，已应用迁移只通过新版本修复；不执行强推、硬重置或清卷。

用户确认本计划后才实施 P2.5d1。P2.5d2～d4 各自另写详细计划并单独确认。
