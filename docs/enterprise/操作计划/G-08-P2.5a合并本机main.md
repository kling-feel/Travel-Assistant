## 执行顺序

1. 重读《产品需求》《软件架构》《当前进度》与本计划；核对分支、工作区、提交图和 `main...HEAD` 的文件清单。检查本轮 G-08、P2.5b、索引及进度文档的差异，`git diff --check` 通过后只暂存这些文档，在 P2.5a 分支作一笔独立计划提交。若出现不明修改，先查明，不顺带提交或覆盖。
2. `git fetch origin` 后再次核对 `origin/main`。如果它已偏离上次核对的 `fbb02bb`，先说明新增提交及影响，暂停本次合并；不自动拉取、变基或强推。确认本机 `main` 仍为分支祖先、工作区干净且能快进。
3. 审阅 v008 的动作类型约束和有效机票唯一索引、`flight_book` 提案/确认、改签防重复、API/行程变化及回归脚本。确认没有改写已应用的 v001～v007，没有把 `.env`、私有配置、数据库文件或备份纳入提交；旧 `/api/graph/` 交易路由仍未注册。合并前运行 34 项自动化测试、2026-10-17/2026-11-01 两日期离线航线校验、Python 编译和 `pip check`。实库结果沿用 P2.5a 已记录的验收，不把本次离线检查称为重新实测数据库。
4. 全部检查通过后，切换本机 `main`，执行 `git merge --ff-only <历史功能分支>`。若不能快进，停止并分析分叉；不制造合并提交、不重写历史。
5. 合并后确认 `main` 与已审阅的分支末端一致；复跑自动化测试、两日期离线校验、编译/依赖检查与旧路由检查。将实际提交、检查结果、数据库未触碰及下一步状态写入《当前进度.md》，在本机 `main` 单独提交这条结果，再复核提交图和工作区。

## 通过条件与异常处理

- 本机 `main` 线性包含 P2.5a 代码与两份新计划；合并前后自动化及离线校验通过，旧图交易路由保持关闭。
- PostgreSQL 容器、数据卷、备份及远端 `main` 均不因 G-08 改变。P2.5b 要在此后按独立计划另行确认和实施。
- 合并前有检查失败则停在原分支并记录原因；合并后失败则保留现场，定位问题并另拟修复。不用 `reset --hard`、强推或 `docker compose down -v`。
