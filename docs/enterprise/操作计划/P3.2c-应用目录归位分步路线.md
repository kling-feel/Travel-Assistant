# P3.2c：应用目录归位分步路线

> 2026-10-24 制定｜状态：P3.2c1、P3.2c2 已在本地功能分支实施；后续各子步须分别确认。承接 [P3.2 总路线](P3.2-代码清理与目录重组分步路线.md)及已完成的 P3.2b3；执行结果统一记入[当前进度](../当前进度.md)。

## 1. 目标与已核对的依赖

将现行应用收拢到 `travel_assistant/`，让根目录只保留清楚的启动、部署、数据、迁移、脚本、测试和文档入口。保持 `python main.py`、`/app`、`/static/*`、现有 `/api/v1/*`、数据库表和迁移版本不变。页面、交易规则、确认协议和虚构数据内容不因目录调整改变。

当前启动链是 `main.py → api/routers.py → api/travel.py → graph_chat/controlled.py`；现行 Python 代码分散在 `api/`、`config/`、`db/`、`graph_chat/`、`services/`、`utils/`。静态页面位于根目录 `static/`。跨目录的绝对导入有数百处，`config`、地点服务和多个脚本还通过 `__file__` 推导 `.env` 或数据路径。迁移模块导入当前数据库模型及政策；迁移版本已应用，不能改版本号、顺序或表结构。全部脚本仍在根目录 `scripts/`，README 提供具体调用方式，搬走文件可能使用户照着文档无法执行。

因此按路径、底层模块、业务模块、入口整理四步推进；每一步先核对三份核心文档与实际引用、单独给出操作计划，等旅客确认后才改代码。下一步仅申请 [P3.2c1](P3.2c1-项目路径与页面资源归位.md) 的确认。

## 2. 目标结构与逐步落地

```text
main.py                         保留简短启动入口
travel_assistant/
  paths.py                      项目根、交付样本和页面资源的明确路径
  core/                         配置、日志、身份和通用 HTTP 处理
  db/                           正式数据库连接及当前模型
  services/                     确定性业务、政策、推荐和对话辅助
  agents/                       当前受控主助手与业务助手
  api/                          现行旅客路由和请求响应模型
  web/static/                   同源页面四项资源
migrations/                     现有 13 个版本，保持版本身份与次序
scripts/                        当前命令及按职责说明的入口索引
tests/                          当前自动化与隔离页面辅助代码
data/fixtures/                  可交付虚构样本，内容不变
data/source/                    本机原始 SQLite，继续 Git 忽略
docs/                           当前文档入口与完整历史资料
```

`travel_assistant/` 中具体文件名以各子步的引用核对为准。目标不要求把 `migrations/`、`scripts/`、`tests/`、`data/` 或 `docs/` 搬进应用包。不能把数据库文件、密钥、备份或付费流水带入 Git。

| 子步 | 拟定范围 | 独立验收门槛 |
| --- | --- | --- |
| [P3.2c1](P3.2c1-项目路径与页面资源归位.md)（本地实施） | 建应用包及统一项目路径；移动四项页面资源到 `web/static/`；更新 `main.py` 的文件位置和相应说明 | 页面和资源仍由原 URL 返回、资源字节不变、静态路径不泄露本机目录；230 项自动化与离线检查通过 |
| [P3.2c2](P3.2c2-配置数据库与通用模块归位.md)（本地实施） | 归位 `config/`、`db/`、`utils/` 到 `core/` 和 `db/`；逐项修正运行、迁移、脚本、测试的导入；确保 `.env` 仍从项目根读取 | 完整回归、迁移入口只读导入检查、配置路径与数据库目标不变；不实际执行迁移或连接正式库写入 |

子步编号为建议顺序。如果 c2 或 c3 的依赖实测显示必须合并移动，先修订计划并重新确认，不能留下长期兼容包装或同名双实现。单步完成后记录实际文件树和验证结果，再制定下一步详细计划。

## 3. 每一步共同的安全边界

1. 先读取《产品需求》《软件架构》《当前进度》，核对工作区、已确认计划和实际依赖；保留已经完成的历史计划、验收和进度正文。
2. 移动前记录文件清单、当前启动和测试基线；先修改使用方，再清理空目录，检查根 README、脚本索引、文档链接和代码导入。公开命令以当前 README 为准，不修改历史记录中的当时执行事实。
3. 每步至少跑相关定向测试、完整自动化、两日期全航线样本检查、Python 编译、页面脚本语法、依赖及差异检查；核对注册路由和页面资源 URL。若测试因环境不可用而不能执行，应保留风险，不宣称已验收。
4. 目录整理不操作 8000 页面、不写正式或隔离数据库、不重置演示日期、不运行迁移／数据导入、不调用付费模型或联网搜索。若某步必须做真实数据库验收，另拟隔离与备份方案供确认。
5. 结果及测试证据写入《当前进度》；每步只在本地功能分支提交。G-17 的本机 `main` 合并与 GitHub 同步另行制定、审核和确认。公开内容避免内部工具品牌字样。

## 4. 停止与回退

- 如果移动后出现导入循环、`.env` 路径改变、静态文件 404、样本路径失效、迁移版本变化或 README 命令失效，先停在该子步修复；不得带着半迁移状态进入下一步。
- 对单纯移动保留 Git 可追踪的差异与原文件内容校验；失败时只回退该子步的未发布文件改动，不恢复或覆盖数据库。
- 历史文档位置整理属于 P3.2d。P3.2c 只更新当前导航与准确引用，不能借目录整理删除历史内容。
