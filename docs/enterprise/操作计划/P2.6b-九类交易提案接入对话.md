# P2.6b：九类交易提案接入多轮对话操作计划

> 编写日期：2026-10-18｜状态：已执行并按 G-13 合并本机 main；本文件只记事前方案，实施结果写《当前进度.md》

## 目标、起点与边界

让登录旅客在现有 `/api/v1/sessions/{id}/turns` 对话中，针对本人航班、酒店、租车订单或正式模拟产品，提出以下九类交易：`flight_book/change/cancel`、`hotel_book/change/cancel`、`rental_book/change/cancel`。助手负责查询、澄清和生成**待确认卡**；旅客仍通过现有指定动作 `/confirm` 或 `/reject` API 逐笔决定，订单只有确认事务通过后才变化。示范句“把明天下午的航班改签，并订一晚附近酒店”应在条件明确时形成两张相互独立的卡。

起点是本机 `main=b20aa26`：P2.6a 只读对话、v012 轮次表和 PostgreSQL 检查点已合并，九类提案及确认服务已存在；`create_proposal()` 当前每次生成随机幂等键，对话轮次尚不保存卡片快照。正式库有 12 版迁移、2 个演示旅客、2 张机票/2 张酒店订单，测试记录为 0，数据库容器已停止。执行前重新核对这些状态。现有 52 项测试是回归基线。

本阶段不改九类价格、取消、改期政策；不接真实支付/供应商、游览预订、联网推荐、页面或真实 DeepSeek 调用。有效模型密钥不是开工条件；固定模型完成确定性验收，真实模型留 P2.6c。

## 建议的交互规则

1. **选对象**：取消/改期先读本人已确认订单，使用服务端取得的订单 ID 和版本；不存在或有多个可能对象时追问。新预订从正式候选查询中取得产品 ID。多候选时先给最多三个选项并询问选择；旅客明确指定班次/产品，或明确说“最便宜”“离目的地机场最近”且条件足以唯一排序时，才生成对应卡。不能凭模型猜一个 ID。
2. **补条件**：航班需要日期、路线及具体班次；酒店需要城市或目的地、入住/退房日和房型产品；租车需要车辆产品、取车和还车的**机场当地时刻**。缺项、时间含糊或夏令时偏移不明确时追问，不能自动补出会改变交易结果的值。对“附近酒店”，以本人已确认行程或本轮明确选择的航班到达机场作为位置依据；先显示按近似直线距离排序的酒店候选，不把机场距离说成道路时间。
3. **一轮最多两笔提案**：覆盖“改签＋酒店”主场景。超过两笔时先处理明确的前两笔并说明其余需下一轮；本轮若两笔中的任何一笔对象/条件不明确，建议先追问，**不创建部分卡片**。两笔都明确后，同一数据库事务生成两张独立卡，各有动作 ID、有效期、模拟金额及规则版本；确认一张不会替另一张确认。此“全有或全无”规则作为本计划推荐选择，用户确认计划即接受。
4. **答复状态**：助手文字严格区分“候选建议”“待确认”“已执行”。生成卡片只说“待确认”，返回结构化卡片快照及动作 ID；已确认/拒绝/过期的当前状态仍以现有动作详情 API 为准。模型文字、聊天中的“确认”或通用 `y` 都不能直接执行订单写入。

## 实施顺序

1. **开工核验和隔离**：重读三份核心文档、本计划及交易政策；核对 Git 工作区、`main`、远端差异、正式库迁移/订单/会话/动作计数和备份。若需新增列或运行实库验收，先做并验证 Git 忽略的 `pg_dump`。从干净的本机 `main` 建 `<历史功能分支>`，先将确认后的计划文档独立提交；不改写 v001～v012。
2. **结构化交易规划**：在新版图的交易分支输出有界、严格校验的动作计划，最多两项，类型仅九类；模型只提出业务意图和候选/订单引用，不提供旅客 ID、会话 ID、金额、政策内容或确认决定。服务端从 JWT/已验证会话绑定身份，查本人订单、当前产品、规则与报价；对未明确目标、越权/失效目标或不在候选集合的引用降级为追问。保留 P2.6a 一般聊天、政策和只读查询路径。
3. **轮次与卡片原子性**：扩展现有轮次响应，加入 `actions` 卡片数组（通常 0～2）。新增仅追加的 v013 迁移保存本轮卡片快照或稳定引用，用于相同 `request_key` 的精确重放和应用重启恢复；不改 v012。为 `create_proposal()` 增加可选的稳定幂等键，旧内部调用保持兼容。图计算只产出计划，不在图节点写动作；模型调用结束后锁定服务端会话/轮次，复核仍可处理，在**同一数据库事务**中创建全部卡片、提案审计、助手消息和完成轮次。任一失败则整批回滚，不留下单张卡或“已准备好”的回复。响应丢失时相同请求键读取已保存结果，不重新生成卡。过期轮次与并发请求沿用 P2.6a 的单会话约束。
4. **API 和文档**：`/turns` 响应保留 `answer`、`references`、`status`，新增 `actions`；不改变现有动作详情、确认、拒绝 API 的逐笔语义。README 详细展示登录、两轮澄清、两张卡、分别确认/拒绝、查最新行程及重复请求；标注所有金额为模拟、卡片可能过期，绝不把密钥写入示例。
5. **确定性验收**：固定模型覆盖九类动作、两张卡主场景、选择候选与缺条件追问；模型伪造旅客/订单/产品/价格/政策、旧图工具、跨账号、过期产品和版本变化都不能写入。验证未确认订单不变，确认/拒绝只影响指定卡；同请求重放、响应丢失、模型异常、数据库异常、并发/进程中断后无孤儿卡或重复审计。运行全部既有测试与必要新增测试、两日期离线样本、编译、依赖和路由检查；再用真实 PostgreSQL/固定模型顺序验证九类动作与“改签＋酒店”，包括数据库重启恢复，最后清理临时记录并核对演示数据基线。
6. **收尾**：停止数据库并保留卷/备份；检查 `git diff --check`、迁移文件、提交清单和凭证边界。更新《当前进度》记录实际结果并在功能分支提交。本机合并另拟 G-13 计划确认，远端推送独立规划。

## 完成门槛与失败处理

- 九类交易都能从对话走到**本人待确认卡**；没有旅客指定动作确认，就没有订单变更。双任务给两张独立卡，缺条件先追问，重放不重复建卡。
- 政策、价格、可用性、订单归属和版本由正式服务确定；模型不能直接调用确认/订单写服务，旧 `/api/graph/` 路由继续不注册。新卡确认时仍由现有事务服务重新核对最新状态。
- v013 首次和重复迁移通过，已有 P2.6a 会话兼容；应用和数据库重启后卡片、轮次、历史和审计对应。失败时保留已验证备份与现场，不清卷、不强推、不自动合并。
- 如实施中发现现有提案服务无法在同一事务内实现上述原子性，或必须改变用户可见的确认协议，先修订本计划并向用户说明，再继续相关实现。

用户确认本计划后才实施 P2.6b。
