## 起点和目标

本机 `main` 当前为 `e43d189`，工作区在规划前干净；P2.4c 的 v007 已在本机 PostgreSQL 应用，数据库容器停止、数据卷和已核验备份保留。现有 `pending_actions` 只允许 `flight_change`、`flight_cancel`、`hotel_book`、`hotel_change`、`hotel_cancel` 五类；确认服务已处理归属、15 分钟有效期、重算报价、单笔事务、结果重放和审计。航班有 15,374 个窗口内模拟报价；租车有 208 个可查询产品，但没有订单表。普通旅客会话还不能自行生成卡片，模型接入留在 P2.6。

## 业务判定与确认结果

1. **机票新预订**：只接受正式库中未来、`Scheduled`、有当前模拟报价的航班。卡片按报价显示一次模拟应付额；确认时重查班次、报价版本、规则与身份。建议同一旅客同一班次只保留一张有效机票，取消后可以重新预订，以免两个并发确认生成重复机票。当前虚构机票规则 v3 已写明新预订逐笔确认，无需为此改写 v3。
2. **租车时间与计价**：建议要求明确取车、还车的日期和时刻；以产品机场的 IANA 时区展示，内部用 UTC 比较。按真实经过时间每开始 24 小时计一个模拟计费日，至少一天，卡片列出日价、计费日数、总额和取还车当地时刻；未说明时间时由后续助手澄清，不擅自补时间。取车时刻前取消免费，模拟应退全额；到达取车时刻后不能取消。租车仍无真实库存、扣款或退款。
3. **酒店取消**：用户已确认在产品机场**当地入住日期之前**取消时模拟全额应退，从入住日期开始不可取消；同日预订和改期仍可进行，需提示后续不能取消。新条款用酒店政策 v4，历史 v3 保留，既有待确认卡按版本失效；P2.5c 分支已实施并验收。

租车与酒店规则均已确认并在各自分支实施；后续规则变更须另行版本化并回归待确认动作。

## 共同实现与验证边界

- 新动作沿用 `services/actions.py` 和 `services/confirmations.py` 的结构化提案、确认与审计；旅客 HTTP 只能读本人卡片及确认/拒绝指定动作。P2.6 才让受控智能体调用提案服务，不开放客户端直接填写价格、旅客 ID 或调用订单写服务。
- 新增迁移只追加 v008/v009，不修改已应用 v001～v007。数据库迁移前检查数据和待确认动作，创建并核验本机 Git 忽略的备份；演示重置必须显式触发，普通启动与迁移不清空订单。若存在待确认动作，重置继续拒绝。
- 在分支内先做确定性单元测试，再顺序运行 PostgreSQL 迁移、真实 API、两账号隔离与旧流程回归；验证后清理测试旅客/会话/动作，复核演示账号订单、报价及产品计数，停止容器但保留卷。任何会写测试数据的验收脚本不并行运行。
- 机票、酒店、租车金额均标记为模拟计价单位；旧 `/api/graph/` 写路由继续关闭。P2.5 不接 DeepSeek、真实供应商、支付、联网推荐或页面；这些能力按后续 P2.6/P2.7/P3 独立实施。
