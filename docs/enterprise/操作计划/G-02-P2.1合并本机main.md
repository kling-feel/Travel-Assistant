# G-02：P2.1 合并本机 main 操作计划

> 编写日期：2026-10-17｜性质：待确认的事前计划；实际执行结果只写《当前进度.md》

## 目标与当前基线

把已在 PostgreSQL 验收的 P2.1 会话归属与持久化实现，从 `<历史功能分支>` 快进合并到**本机** `main`，作为 P2.2 的稳定起点。计划编写时，P2.1 实现提交为 `d08f9f7`，本机 `main` 为 `6d798fa`，已知 `origin/main` 为 `fbb02bb`；计划文档的本地提交会使分支末端提交号变化，执行时须重新核对。当前工作区干净。

本次 Git 操作只涉及本机分支；不推送 GitHub、不改 P2.1 业务代码、不运行种子或重置演示库、不启动数据库。远端还缺少 P1 与 P2 的本机提交，后续推送须另列目标与范围并取得确认。

## 执行顺序

1. **复核现场**：重读《产品需求》《软件架构》《当前进度》和本计划；运行 `git status`、分支图和提交差异检查，确认无意外未提交文件、P2.1 分支包含预计的实现与计划文档。
2. **刷新远端信息**：执行 `git fetch origin`，核对 `origin/main` 的实际提交。如远端发生变化，先展示差异和新的合并方案，暂停本计划；不自动把远端改动合入或覆盖。
3. **核对可快进条件**：确认本机 `main` 是 P2.1 分支的祖先；列出 `main..<历史功能分支>` 的提交和文件，检查没有凭证、原始大型 SQLite、生成的 SQL 或其他不该纳入主线的内容。
4. **合并前验证**：运行当前自动化测试和 `pip check`。数据库已通过 P2.1 实库验收且停止，本次不为纯 Git 合并重复初始化数据库。
5. **本机快进合并**：切换 `main`，执行 `git merge --ff-only <历史功能分支>`。若无法快进，立即停止并说明分歧；不执行重置、强推、自动变基或产生未经审阅的合并提交。
6. **合并后核验与记录**：确认 `main` 指向预期分支末端、工作区干净、远端未变；复跑自动化测试。随后只更新《当前进度.md》的真实提交号、测试结果、远端状态和 P2.2 起点，创建本机文档提交。若 P2.2 随后获准，须从这个文档提交后的干净 `main` 建新分支。

## 通过标准

- 本机 `main` 包含 P2.1 代码、迁移、测试和计划文档，保持可追溯的线性历史。
- 会话隔离与恢复相关自动化测试仍通过；P1 回归测试仍通过；工作区干净。
- `origin/main` 未被推送或改写；PostgreSQL 容器与数据卷状态不因本次合并变化。
- 《当前进度.md》准确记录合并结果；不能将 P2.1 的会话历史误写为已完成 LangGraph 检查点持久化。

## 失败处理

任何前置检查或测试失败时保留当前分支与证据，不合并。若合并后出现测试失败，保留主线现场并先分析修复方案，不用 `reset --hard` 掩盖问题。只有本计划获得用户确认后才执行以上 Git 操作。
