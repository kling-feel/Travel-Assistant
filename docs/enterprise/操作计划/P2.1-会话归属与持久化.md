# P2.1：会话归属与持久化操作计划

> 编写日期：2026-10-17｜性质：事前计划；执行结果只写《当前进度.md》

## 本步目标

先给 P2 后续动作和 LangGraph 检查点建立可靠的会话边界。登录旅客能由服务端创建会话，列出和读取自己的历史；会话 ID 由服务端生成，客户端不能指定所有者。旅客经 API 只能追加 `user` 消息，助手消息留给后续内部图流程写入。本步不调用模型、不提出或执行订单变更、不开放旧图路由。

## 计划修改的模块

- `db/travel_models.py` 和新的版本迁移：新增 `chat_sessions`、`chat_messages`，包含所有者、时间、消息顺序与必要约束；不保存令牌或模型隐含推理。
- `scripts/migrate_p1.py` 或通用迁移入口：按版本顺序运行 v001、v002，重复运行跳过已应用版本，旧 README 启动流程保持可用。
- `services/`：创建、列出、读取和追加消息的确定性服务；每次传入由服务端验证的旅客 ID，并核对会话归属。限制消息长度和角色，避免无边界数据写入。
- `api/travel.py`：新增鉴权后的会话 JSON 端点。请求体不接受 `traveler_id`；读取历史按会话 ID 和当前旅客双条件查询，越权返回拒绝。
- `tests/`、README：覆盖两账号隔离、伪造会话 ID、消息顺序、重复迁移和重建应用实例后的恢复，并说明本机调用方式。

## 执行顺序

1. 事前计划文档先在本机 `main` 保存为文档提交；待用户确认本步后，从干净的 `main` 建立短期 `<历史功能分支>` 分支，核对未提交修改。
2. 设计 v002 表与索引，保留 P1 正式订单和 `demo_source` 数据；更新迁移入口，验证重复运行。
3. 实现会话服务和新 API。使用已有 `current_traveler` 依赖；服务端生成不可预测会话 ID，禁止请求传入所有者字段。
4. 添加必要的服务和 API 测试；检查重建应用实例后，同一旅客可读历史，另一旅客不能读取或追加。
5. 在本机 PostgreSQL 应用迁移并执行验收脚本；只读核对表、会话归属和旧路由未开放。验收后停止数据库容器，保留数据卷。
6. 检查差异、依赖和敏感文件；只在短期分支创建本地提交。把实际结果、测试、限制和下一步写入《当前进度.md》。是否合并 `main` 另按 Git 操作计划执行，不在本步推送远端。

## 验收标准

- 两名演示旅客各自创建并读取会话；猜测／伪造另一人的会话 ID 无法读取或追加。
- 服务进程或应用实例重建后，已有会话与消息仍从 PostgreSQL 读出，顺序不变。
- v002 迁移可重复执行，不改写 P1 订单和 `demo_source`；原有 5 项测试仍通过。
- 新会话 API 不接受客户端旅客 ID；旧 `/api/graph/` 和旧写工具没有重新暴露。
- 工作区不包含 `.env`、原始大型 SQLite 或生成的 SQL；本步不推送 GitHub。

## 失败处理与边界

若迁移或实库测试失败，保留当前本地分支与错误信息，不合并 `main`，先修复并重跑；不删除数据库卷、不重置 P1 订单。若发现当前 LangGraph 版本的持久化格式对会话表提出额外要求，记录后留到 P2.4 的检查点设计，不在 P2.1 擅自扩大为完整图重构。
