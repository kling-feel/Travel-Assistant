# G-21 云端隔离验收成果合并与 GitHub 同步操作计划

> 2026-10-27 制定，**等待旅客确认后执行**。本计划只把已经验收的云端配置、恢复记录和对话修复合入本机 `main`，再同步到 `kling-feel/Travel-Assistant` 的 GitHub `main`。云服务器上的正式镜像、公网入口、数据库和订单均不在本轮改动范围内。

- P3.4c3b 的机票／酒店／租车九类交易、确认边界、跨账号、竞争卡、重启与原库隔离均已验收；最终本机 275 项测试通过。修复版在隔离应用重放 11 轮确定性失败场景；修复后真实 DeepSeek 抽样、精确桌面／375／338 像素视口及正式云端镜像发布仍属后续独立验收，不借本次 Git 同步宣称完成。

## 执行顺序

1. 再读《产品需求》《软件架构》《当前进度》和本计划，确认旅客已授权 G-21。检查功能分支工作区干净、提交历史、完整差异和当前本机 `main`。核对远端地址确为授权仓库，执行 `git fetch origin` 后确认实时 `origin/main` 没有超出规划基线的新提交；如有变化，停止并重新审查。
2. 对将进入公开 `main` 的**完整最新文件树、全部新增文本和新增提交说明**检查用户要求避免的工具品牌字样、疑似密钥、密码、个人私钥路径、真实数据库／备份、临时账号与服务器私有 IP。复核 Git 忽略规则、公开文件名、文档链接、Caddy 路由、云端配置预检不泄露值；差异空白检查必须通过。有疑点先在功能分支修复并重新检查。
3. 复核 `main` 是功能分支祖先、没有新增迁移，也没有意外更改 8000／5432 公网暴露或 2 GiB 资源约束。执行语法／配置定向检查及完整业务回归，以本次 275 项通过记录为基础；若结果与基线不一致，暂停合并并定位。
4. 在本机切换 `main`，只用快进方式合并功能分支。确认合并后的 HEAD 与功能分支相同，工作区干净，再做差异和关键回归检查。若不能快进，停止，不自动解决冲突、不重写历史。
5. 只对授权仓库执行普通 `git push origin main`，不强制推送，不推送功能分支或标签。随后独立读取远端 `main` 完整哈希，确保与本机 `main` 一致；若推送失败，保留本机状态并报告“本机已合并、远端未同步”，先排查远端变化。
6. 把实际合并哈希、远端核对结果、测试与公开审查结论写入《当前进度》并普通推送该文档结果提交。整个过程不启动云端正式应用／代理，不导入数据，不调用模型或搜索，不改变本机 8000。

## 完成判定和后续边界

只有功能分支、本机 `main`、GitHub `main` 的预期提交一致，工作区干净且公开内容与回归检查通过，才标记 G-21 完成。云端正式发布与展示日验收另拟 P3.4c3c 计划：先备份原库，构建修复版镜像，短时开启并抽样真实模型与搜索，核对准确视口和外部网络，再决定是否配置 OSS 自动留存。G-21 的确认不授权这些云端操作。
