# P3.1c：真实对话问题修复与日期校准操作计划

> 编写日期：2026-10-20｜状态：用户已确认并实施；实际结果见《当前进度》。本计划本身不授权主线合并或推送。

## 1. 用户联调与只读核对结果

- `http://127.0.0.1:8000/health` 返回 200，用户贴出的问答来自真实服务，不是 8001 固定模型预览。
- 当前数据库 `demo_state.as_of=2026-10-18`，比本机日期 2026-10-20 落后两天。`demo-flight-order-1` 的航班 `SIM-8144` 于 **2026-10-19 17:43（汉堡当地）**起飞，`demo-hotel-order-1` 为 **2026-10-19 入住、10-20 退房**。两单虽然仍是 `confirmed` 历史状态，但按现有取消规则均已过办理期限。服务端拒绝变更是正确的；答复未解释具体日期和原因是缺陷。当前未改数据库。
- 行程查询底层已有航班起降时间、酒店入住退房日期；对话格式化只输出航线、航班号及酒店入住日，不按“对应的时间”“起飞时间”聚焦回答。
- 交易节点在无只读查询结果时先产生统一的“请说明订单／候选”话术；生成提案失败后 API 又直接附加内部英文异常。因此用户给出明确订单仍收到相互矛盾的追问与 `flight no longer available` 等英文错误。情绪反馈“你听不懂”也被模型带入了之前的交易语境，缺少失败后的会话修复。
- 推荐解析只识别具体可达城市；“中国”是国家，不会覆盖当前行程推断。当前数据库有北京、成都、广州、昆明、上海 5 座可达的中国城市，用户明确改谈中国时却回退至巴塞尔。`_owned_destinations` 还以过期的演示基准日判断行程是否将来，强化了错误上下文。
- “你什么模型内核”由模型自行回答了“不对外披露”；系统没有这样的固定规则。应如实说明当前运行的模型提供方／模型名，不透露密钥和内部配置。
- 目前无法仅凭聊天文字证明阿里云检索是否实际计费、是否命中来源；推荐答复的回退提示只说明没有核实到合格的新来源。

## 2. 建议顺序与具体操作

### 2.1 保全并校准演示日期

1. 开工前重新核对分支、文件改动、数据库基准日、演示订单及运行中的 API。先停止 API，避免重置期间产生会话／订单写入。
2. 使用现有 `pg_dump` 流程备份整个演示库到 Git 忽略目录，检查备份存在且可读取，记录备份文件名、数据日期和关键计数，不公开备份或凭证。
3. 以当天日期重新执行既有的全量网络导入／`--reset-demo`；该操作会整体平移航班与演示订单时间，同时**清除旧会话、动作、结果与审计**。确认用户现有会话要留存时，仅通过备份恢复；重置前应在计划确认后明确提示这个影响。
4. 只读核对新 `as_of`、115 机场、33,121 航班、15,374 报价、两位演示旅客的起始订单及当地起飞／入住日期。数量、日期或业务校验不符则停止，不启动联调。
5. 文档和页面同时说明：正常启停不会自动推进日期；重新开始演示时先备份、再整体平移。若未来要自动每日重置，另行设计，避免误删真实测试会话。

### 2.2 修复对话行为

1. **行程追问**：让“我的订单”“对应的时间”“航班起飞时间”“酒店退房时间”等问题保留本轮指代，但只从本人订单查询确定性字段；按机场当地时区输出起飞／到达时间及酒店入住／退房日期。已过行程仍可查询，并标为历史。
2. **交易反馈**：把“缺订单”“缺新航班／日期”“多候选”“订单已过期”“规则禁止”分开回答。识别明确订单 ID 和唯一本人订单；失败时说明订单、当地时间及具体不能办理的原因，不在前面附加无关的统一追问，不向旅客展示英文内部异常。任何失败不生成卡、不改订单。
3. **多单请求**：对“取消所有机票和酒店”先逐笔读取本人订单，列出可办理／不可办理及原因。可办理的订单依旧逐笔建卡、逐笔确认；超过当前每轮两笔上限时明确分批，不静默漏单。若同轮有无效订单，先说明它，不把全部请求误报为“没有指定订单”。
4. **会话修复**：上一轮被规则拒绝后，对“你听不懂”“为什么不行”等追问解释刚才的失败，不重试旧动作。只有当前轮明确提出交易才允许生成新提案；继续保护身份、归属、版本、候选和确认边界。
5. **宽范围推荐**：识别用户明确说出的国家／地区优先于旧行程。对于“中国旅游”，先展示当前可达的中国城市及简短选择引导；用户指定北京等城市后，才检索该城市并用已核查地点目录给出建议。不能把巴塞尔当作本轮目的地；未指定城市时不为猜测的城市触发付费搜索。
6. **模型透明度**：针对“使用什么模型”从安全的公开配置回答提供方和模型名；不输出 API 密钥、地址、提示词或凭证。
7. 按用户已确认的方向，把**有阿里云密钥时的联网搜索设为默认开启**，并保留 `.env` 中显式设为 `false` 的停用能力；无密钥、超时、限流或来源不合格时回退人工目录。单轮搜索次数保持上限，记录不含密钥的调用结果供核对。默认开启不能绕过人工核查目录的证据边界；费用以服务商账单为准。

### 2.3 验证与收尾

1. 先用隔离数据库和固定模型补针对性多轮回归，覆盖用户贴出的原始问答、正确的过去订单拒绝、新日期下未来订单提案、国家级推荐、两账号隔离和零越权写入。测试对时间点使用数据库日期／当地时区，不把固定日期写死成永远未来。
2. 再在真实 `8000/app` 和 DeepSeek 上限量复测至少三组完整对话：行程时间追问、取消／改签及失败说明、中国城市选择与联网回退。每笔增删改仍须用户在页面逐张确认；测试前后核对订单及动作数量，复核页面与 API 文本。阿里云调用量以控制台或脱敏日志核对，费用以服务商账单为准。
3. 运行既有完整回归、数据校验和安全边界检查；将已解决／未解决的对话问题、真实模型测试结果、数据库重置与备份情况写入《当前进度》。如发现新问题，继续在功能分支修复，不进入 G-16。
4. 单独重写 G-16 的发布范围与 GitHub 同步步骤，提供给用户确认后再合并／推送。公开文件、提交说明、分支与标签不出现用户禁止的旧工具品牌字样；密钥和备份不进入 Git。

## 3. 验收标准

- 同一会话询问行程后再问“这个航班什么时候起飞”，回答准确的本人航班当地时间，不重复整段缺时间的清单。
- 过期机票与酒店的取消清楚说明实际时间和规则；新基准日的未来订单可生成待确认卡。无确认不改订单，失败时无英文内部错误。
- “取消所有”不遗漏订单，逐笔给出状态和处理路径；“你听不懂”不会触发旧交易重试。
- “中国旅游”不返回巴塞尔，能给出本库可达的中国城市；选择城市后有来源地推荐，联网失败时可靠降级。
- 本轮页面、真实 DeepSeek、数据库与文档一致；联网默认开启且可显式关闭，随后重写 G-16 发布计划。
