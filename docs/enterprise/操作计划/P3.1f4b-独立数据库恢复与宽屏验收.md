# P3.1f4b：独立数据库恢复与宽屏验收操作计划

> 制定日期：2026-10-22｜状态：用户已确认并实施；验收结果见《当前进度》。本计划不授权本机 `main` 合并或 GitHub 推送。

## 1. 为什么需要这一步

P3.1f4 的候选选择、逐笔卡片、长对话和 338 像素页面已在专用数据库通过。该数据库与正式演示库共享同一 PostgreSQL 服务进程，重启进程会打断正式服务，因此未做数据库重启试验；本工作台也只提供窄幅内置浏览器，不能把它当作桌面宽屏视觉验收。完整结果和真实调用上界已写入《当前进度》。

## 2. 开工前只读核对

1. 重新读取《产品需求》《软件架构》《当前进度》和本计划；检查功能分支工作区、P3.1f4 本机提交、测试端口 5434／8013 空闲，以及正式数据库所在项目、端口和卷。若已有其他服务使用目标端口，先重新选一个空端口并更新计划记录。
2. 在用户正常的 PowerShell 核对 `docker --version` 与 `docker info`。当前受限工作台找不到 Docker 命令，不以此认定用户的 Docker Desktop 故障。若需要用户操作，只请用户发送版本／健康状态，不发送 `.env`、密码或 API Key。
3. 再核对 DeepSeek、阿里云密钥仅“已配置／未配置”，不要重复实际付费长对话；本步主要测持久化和页面，固定模型即可。

## 3. 独立数据库与重启

1. 使用另一 Compose 项目名，例如 `travel-ui-acceptance`，将映射端口设为 `5434`，让 Compose 自动创建**独立命名卷**。先确认容器名、端口和卷均不属于正式项目，再迁移并导入同一份虚构数据；只对新容器和新卷写入。
2. 在该库用一次性旅客与固定模型建立一段会话，生成至少一张待确认卡，并记录脱敏的会话 ID、卡片状态、订单和审计计数。停止独立测试 API 后，仅重启 `travel-ui-acceptance` 的数据库容器，核对正式项目和 8000 服务没有被重启。
3. 重新启动独立 API，使用同一会话 ID 读回工作记忆、消息、最新候选、待确认卡、订单和审计；再完成一笔确认和一笔拒绝，核对重复请求幂等及无跨账号读取。失败时保留独立卷供分析，不以正式库重置来修复。

## 4. 桌面和窄屏页面

1. 独立 API 使用 `8013`，在可调整宽度的浏览器分别以约 1280 像素和 338 像素打开 `/app`。如本工作台仍不能控制该浏览器，请用户在本机打开并提供两张**不含密钥或密码**的截图；页面登录使用一次性测试账号。
2. 逐项查看航班、酒店、租车候选的中文信息与按钮；租车缺时刻的提示；卡片详情、键盘聚焦、确认／拒绝；有效行程、已取消历史和待确认／已拒绝动作卡的颜色及文字区别。检查无水平溢出、遮挡或误触；发现问题先在功能分支修复并重复针对性验证。
3. 核对普通对话不提取消历史，明确问历史时才列；页面刷新后候选选择仍可用，旧报价或过期卡需要重新查询。用固定模型覆盖，不再调用昂贵长程付费流程。

## 5. 结束条件和 Git 边界

把通过、失败、未测、数据库与端口隔离证据、页面截图结论和剩余风险写入《当前进度》。测试结束只停止独立容器和 API，暂不删除卷；正式库、8000 服务和演示账号不改动。若所有阻断项通过，另写 G-16 的本机 `main` 合并与 GitHub 同步计划，逐项说明提交范围、公开文本检查、冲突处理、回退与推送目标，再请用户单独确认。若无法获得独立容器或宽屏证据，保持 G-16 暂缓并明确指出缺口。
