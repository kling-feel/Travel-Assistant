# Git 主线发布同步与公开内容规则

> 编写日期：2026-10-19｜状态：发布原则已确认；具体合并与推送仍需单独计划和确认。

## 1. 用户目标与当前事实

用户要求以后每次功能成果合并到本机 `main` 时，同步推送到自己的 GitHub 仓库 `kling-feel/Travel-Assistant` 的 `main`。公开的分支名、标签、提交说明和最新项目文件均不使用开发工具品牌字样；历史提交不改写。每次合并/推送前仍须读三份核心文档、单独给出具体操作计划并等待确认。

当前本机 `main=9a505ec`、`origin/main=fbb02bb`，本机主线领先远端约 57 个提交；P2.7a 在本地功能分支，P2.7b 未实施。审查发现远端已有两份历史文档包含不希望公开的工具字样，当前计划中的代码树约 37 个文件、98 行含该字样，另有一份相关文件名。**不改写历史就无法让 GitHub 的旧提交页也消失这些记录**；本计划的可达成目标是下次发布的最新文件树无该字样，且今后新增的公开分支、标签、提交说明、文件内容不再出现。若将来要求清除旧提交历史，须另拟历史重写方案，说明克隆者、链接、强制推送和回滚影响后再决定。

以上提交数与文件命中数是本规则编写时的快照；2026-10-20 的实际审计结果以《当前进度》和 G-15b 计划为准。旧计划中的 `<历史功能分支>` 仅是阶段占位符，旧命令不能直接作为当前操作命令。

## 2. 下次发布前的整理

1. 在待合并功能分支内，把历史计划、进度和架构文档中的本地工具分支名称改成中性的“功能分支”或保留可核对的提交哈希；把含品牌字样的文件名改为通用项目名称，同步修复所有站内链接与命令示例。保留真实业务结果、时间、测试和风险，不改原有 Git 提交历史。
2. 使用不区分大小写的全文、跟踪文件路径及新增提交说明检查最新树；零匹配才视为公开内容整理通过。检查 `.env`、数据库、账本、报告和密钥未进入 staged 文件。维护者姓名/邮箱与历史提交原样保留。
3. 本地工作分支可按功能命名，远端只推送 `main`，除非用户另行要求公开功能分支或发布标签。README 和进度文档对外只写稳定版本/阶段，不写工作台或工具名称。

## 3. 每次合并与 GitHub 同步的具体门槛

1. 功能分支验收后，单独编写例如 G-15 的计划，列出准确的分支、起终提交、文件范围、迁移/数据库影响、测试证据和远端仓库地址。用户确认后才执行。对已有远端积压提交，G-15 必须一次审查 `origin/main..目标分支` 全部差异，不只看最近一个阶段。
2. 执行前 `git fetch origin`，核对目标仓库、当前 `origin/main`、本机 `main`、工作区干净及快进关系；对公开最新树、提交说明、文件名、密钥和忽略文件做检查。远端若有新提交、分支不再可快进、GitHub 无权限或公开内容检查不通过，停止合并/推送，先报告并修订计划。
3. 先跑合并前回归，再用 `--ff-only` 将已验收分支合入本机 `main`，跑合并后回归；同一获确认的 G 计划随后执行普通 `git push origin main`。不用强制推送，不推送本地功能分支或临时标签。推送失败时明确记录“本机已合并、远端未同步”，查明原因并优先恢复同步，在此之前不继续下个主线合并。
4. 用远端引用核对 GitHub `main` 的提交哈希与本机 `main` 一致，核查公开最新树和仓库页面，最后把合并哈希、推送结果、测试与任何差异同步《当前进度》。每次阶段计划明确本轮是否需要数据库启动、备份和清理。

## 4. 本轮边界和下一步

本轮只纠正 Docker 诊断、调整联网搜索方案并建立上述发布约定；不改业务代码，不合并、不推送、不改写历史。P2.7b 完成后，以实际提交和远端状态另写 G-15 具体计划，请用户确认后再进行首次“本机合并＋GitHub 同步”。后续 G 计划沿用同一同步门槛。
