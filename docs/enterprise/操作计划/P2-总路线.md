# P2 分步实施路线

> 编写日期：2026-10-17｜状态：P2.1～P2.3 的历史路线；后续阶段已由 R-01 重排，本文后半部分不再作为实施依据

## 总目标

在保留 FastAPI、LangGraph 主助手／专门助手和简洁 Python 分层的前提下，把 P1 的旅客身份与订单服务接成可恢复、逐笔确认的模拟交易闭环。目标覆盖航班改签／取消、酒店预订／改期／取消五种写入，以及“明天下午改签并订一晚酒店”的两张独立确认卡。任何模型输出都只能提出动作；实际订单写入由登录旅客对指定动作确认后在数据库事务中执行。

当前旧图仍依赖客户端 `passenger_id`、旧 SQLite 写工具、文本 `y` 和 `MemorySaver`，且其 HTTP 路由未注册。P2 不会把这条旧写路径重新开放；迁移时会在新服务与新接口上逐层替换。租车、景点保留原代码结构，但本阶段不开放其写入。

## 五步路线与验收门槛

| 步骤 | 主题 | 主要交付 | 通过后才能进入下一步的证据 |
| --- | --- | --- | --- |
| P2.1 | 服务端会话归属与持久化 | `chat_sessions`、`chat_messages` 迁移；登录旅客创建、列出、读取会话的 API；服务端生成会话 ID | 两账号互不可读写会话；页面刷新／服务进程重建后仍能读取历史；旧图接口仍关闭 |
| P2.2 | 结构化动作提案 | `pending_actions` 与提案服务；五种操作的参数校验、订单前后快照、模拟费用、规则版本、有效期；只返回待确认卡，不改订单 | 非本人的订单无法提案；无确认写入为零；待确认动作跨重启可读且只归属本人 |
| P2.3 | 逐笔确认与事务执行 | 指定动作 ID 的确认／拒绝 API；单笔事务中复核身份、会话、订单版本、资源与规则，再调用 P1 订单服务并写审计 | 五种操作的成功、拒绝、过期、重复确认、版本冲突和跨账号测试通过；数据库最终状态可核对 |
| P2.4 | 智能体接入和检查点 | 主助手／航班／酒店助手改用 P1 查询服务；模型只能调用提案工具；会话检查点持久化，图上下文从服务端绑定旅客 | 固定模型输出的图测试证明两张独立确认卡；重启后可恢复；旧 SQLite 写工具不能从新图调用 |
| P2.5 | 场景与模型验收 | 固定演示脚本、故障注入、模型适配与能力检查；DeepSeek／GPT 主路径及本地模型可选实测 | 贯穿场景完成；模型超时、无工具能力或错误提案不产生订单写入；日志与审计不含令牌／密钥 |

每一步完成后只更新《当前进度.md》记录实际改动、测试、风险和下一步；下一步开工前重读三份基线文档，建立该步独立计划并详细告知用户，按用户确认推进。若测试或关键设计改变，更新计划并重新确认。每步合并本机 `main` 前另建 Git 操作计划；远端推送也另列计划与提交范围。

## 贯穿规则

1. 旅客身份来自已验证的登录令牌；客户端的旅客 ID 不作为授权依据。会话、动作和订单每次访问都核对归属。
2. 每个动作只对应一笔订单变更。拒绝、过期、版本冲突或模型失联都不改变订单；成功执行一次后重复请求返回既有结果。
3. 提案展示系统计算的结构化旧值、新值、模拟价格／费用、规则来源和有效期。模型的文字不能取代这些字段。
4. 新 API 未达到验收门槛前，不恢复旧图交易路由。数据库重置只针对虚构演示环境，原大型 SQLite 保持只读。
5. 每步从本机稳定 `main` 建短期 `feature/` 分支，先测试再合并；Git 合并和远端推送分别列计划。凭证文件、原始大库和生成数据不得进入提交。

## 阶段外事项

简单页面、完整部署和可观察性展示属于 P3；P2 只提供足以验证协议的 JSON API 和自动化脚本。真实支付、真实供应商及租车／景点写入不纳入 P2。
