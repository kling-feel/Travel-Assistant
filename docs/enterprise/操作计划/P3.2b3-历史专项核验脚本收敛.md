# P3.2b3：历史专项核验脚本收敛操作计划

> 2026-10-24 制定｜状态：旅客已确认，本地功能分支已实施；结果见[当前进度](../当前进度.md)。承接 [P3.2 总路线](P3.2-代码清理与目录重组分步路线.md)与已完成的 [P3.2b2](P3.2b2-历史评估脚本与验收入口清理.md)。

## 1. 本步目标与判断

目前 `scripts/` 有 28 个 Python 文件。当前 README 所列的初始化、迁移、数据导入和交易核验命令仍可找到；目录末尾还保留 6 个历史专项文件：`audit_p31e4_flight_time.py`、`p26d_eval_guard.py`、`verify_p27d1_restart.py`、`verify_p31e4_faults.py`、`verify_p31e4_journey.py`、`verify_p31e6_formal.py`。它们不是普通旅客页面的运行依赖。

其中旧航班时长审计只允许旧 5434 隔离库，现行 `audit_p31e5_schedule.py` 已核对全量航班、报价、跨洲时长和落地酒店覆盖。旧地点重启脚本要求已结束的 `travel-eval` 容器标签；旧正式库旅程脚本会创建临时账号、订单和动作，且要求演示日期等于当前日期，不宜作为开发者日常命令。故障脚本会写测试会话，当前代码中未见对该会话的清理。直接保留这些入口会让读者误用，但直接删除又可能丢失有价值的重启和失败边界测试。

建议本步**先补等价自动化，再移除确证冗余或不适合日常保留的历史入口**。保留历史计划、验收记录和 Git 历史全文；不改当前业务、交易确认规则、API、迁移和页面。

## 2. 逐项处理建议

| 文件 | 建议 | 依据与门槛 |
| --- | --- | --- |
| `audit_p31e4_flight_time.py` | 移除 | 现行 `audit_p31e5_schedule.py` 检查范围更广；先逐项对照“长航段不得少于五小时”等断言，确认无独有检查 |
| `verify_p27d1_restart.py` 与 `p26d_eval_guard.py` | 成对移除 | 前者唯一引用后者，且硬依赖已结束的隔离容器；先在现行自动化里证明地点推荐、引用和历史在同会话重建应用后仍一致，并保留现有 PostgreSQL 通用检查点重启脚本 `verify_p26a_restart.py` |
| `verify_p31e4_faults.py` | 条件移除 | 现有测试已覆盖模型不可用、推荐搜索超时；先核对天气搜索失败、卡片与订单不变、会话无残留等断言，缺项补到当前接口测试，再移除会留下临时会话的旧入口 |
| `verify_p31e6_formal.py` | 条件移除 | 已完成的正式库旅程验收由历史记录保留；脚本会写正式库，且只适配某一天的空白基线。先对照现行交易／隔离旅程测试是否覆盖本人归属、逐笔确认、重放、清理；缺项补测试，再从当前执行目录移除 |
| `verify_p31e4_journey.py` | 本步保留，并明确标为仅历史隔离验收 | 它仍包含跨 PostgreSQL 重启的多业务交易旅程检查，`verify_p31e6_formal.py` 还从中导入 `FixedModel`。移除后复核其自身可独立导入；其旧 5434 前置条件、日期与清理流程在后续验收入口升级计划中处理，不在本步直接指向正式库 |
| `audit_p31e5_schedule.py`、`run_p31h3_metered.py` 和根 README 所列 `verify_*` | 保留 | 分别是当前只读全量排程审计、有次数／费用上限的隔离验收、现行操作指南使用的专项核验；本步不调用付费服务 |

自动化替代应针对**行为**而非脚本文件名：重建应用后的同一会话地点推荐要仍有受审来源、消息不重复且不建订单；模型或搜索失败不得创建确认卡或改变订单；已有待确认卡在未确认前不能变为已执行。测试可以使用固定模型和隔离内存数据库，不要求启动旧容器。真实 PostgreSQL 重启的覆盖仍由保留的专项脚本承担；若发现无法建立等价检查，保留相应历史文件并写明原因。

## 3. 确认后的执行步骤

1. 重读《产品需求》《软件架构》《当前进度》和本计划，核对本地功能分支干净、`main` 与远端未变；记录 228 项测试、28 个脚本、交付 SQLite 与两份本机原始库哈希。静态检查六个候选文件的 Python 导入、README 命令和历史文档链接。旧文档只保留其当时的操作证据，不把旧命令改写成“当前可运行”。
2. 将旧审计、地点重启、故障和正式旅程中的独有断言逐项映射到现行测试、`audit_p31e5_schedule.py` 与 `verify_p26a_restart.py`。缺失且仍符合当前产品需求的断言，先补在现行自动化；对“真实容器重启”与“重建测试应用”的证据边界分别记录，不混称等价。
3. 先运行新增的定向测试，再按上表移除通过替代门槛的旧文件。`verify_p31e6_formal.py` 移除前确认其他保留脚本没有导入它；移除后让 `verify_p31e4_journey.py` 独立可导入。不得把旧 5434 脚本简单改为正式 5433 运行。
4. 更新[脚本入口索引](../../../scripts/README.md)、根 README 和软件架构，清楚区分当前必需入口与仍保留的历史隔离旅程脚本；保持所有历史计划、验收和进度文档正文。需要引用已移除脚本的历史段落继续保持原文，当前导航不推荐执行它们。
5. 运行完整自动化、两日期全航线核验、Python 编译、页面脚本语法、依赖检查、README 脚本入口及全部 Markdown 本地链接检查；复核脚本导入不存在悬空引用。正式 5433 库上轮只读连接未返回，本步不以连接成功作为删除前提，也不为此启动／重置正式库；如可只读连接，只记录状态，不写入。
6. 把最终保留／替代／删除清单、测试数变化和验证限制写入《当前进度》。只在现有本地功能分支提交；不合并 `main`、不推送 GitHub。之后再单独提出 P3.2c 应用模块归位计划，等待旅客确认。

## 4. 停止条件与范围

- 如果某旧脚本仍是当前 README 命令或其他保留 Python 文件的依赖，先迁移引用或保留它；不留下半失效的导入。
- 如果业务失败保护、本人归属、检查点恢复或订单不变的有效断言尚无对应测试，停止删除该文件，先补覆盖。测试数变化需说明实际断言对应关系。
- 本步不运行旧专项脚本、不创建验收账号、不重启 Docker、不操作 8000 页面、不写正式或隔离数据库、不调用模型／联网搜索；演示日期、样本和原始 SQLite 不改变。
- 旧验收入口从当前文件树移除后，历史文档及已发布 Git 提交仍可检索其当时实现；历史文档内容不删减。
