## 目标与边界

把已离线验收的全航线样本及校验脚本，从 `<历史功能分支>` 快进合并到本机 `main`，作为 P2.4b 的干净起点。编写计划时，分支末端为 `ec8552b`，含 `daffa22` 与 `ec8552b` 两个 P2.4a 提交；本机 `main` 为 `f4f862b`，上次核对的 `origin/main` 为 `fbb02bb`。执行时以重新核对的提交为准。

本步只做本机 Git 核查、文档提交、合并与回归；不推送远端，不启动或重置 PostgreSQL，不运行新导入器，不改业务代码或原 SQLite。远端推送及 P2.4b 的数据库操作分别另行确认。

## 操作顺序

1. 重读《产品需求》《软件架构》《当前进度》和本计划，核对分支、`git status`、提交图与相对 `main` 的文件清单。审阅本轮新增的 G-05、P2.4b 事前计划和路线边界调整，作为独立文档提交留在 P2.4a 分支；提交前检查 `git diff --check`、文件清单和被 Git 忽略的本机配置。若出现不属于本轮的改动，先查明，不覆盖。
2. `git fetch origin` 并核对 `origin/main`。如果它不再是已知的 `fbb02bb`，先报告远端变化与影响，暂停合并；不自动拉取、变基或覆盖。核对 `main` 仍是当前分支的祖先，保证可快进。
3. 复查样本仅含机场和航班非个人字段，文件大小与 SHA-256 分别为 5,210,112 字节和 `c7a69be6ffc5fcfd0502041e1c5c2844b24e904d0b138dad148bbc8d12bf790f`；检查原大库、`.env`、生成 SQL、凭证等没有进入提交清单。运行离线校验（演示日 2026-10-17、2026-11-01）、现有 19 项自动化测试、Python 编译、依赖检查，并确认旧 `/api/graph/` 交易路由仍未注册。
4. 前述检查通过后切换本机 `main`，运行 `git merge --ff-only <历史功能分支>`。若不能快进，停止并分析分叉，不自行制造合并提交或改写历史。
5. 合并后核对 `main` 与分支末端一致、工作区干净，复跑离线校验和 19 项测试。仅将实际合并提交、核查与未完成项写入《当前进度.md》，作本地进度文档提交，并再次核对最终 `main` 状态。

## 验收与失败处理

- 本机 `main` 线性包含 P2.4a 样本、离线校验、README 说明及已确认的计划文档；样本仍覆盖 115 个机场、33,121 班航班与 618 条有 Scheduled 班次的航线，原大库没有进入 Git。
- 测试及校验通过，远端 `origin/main`、PostgreSQL 容器和数据卷均未改变。
- 合并前检查失败则不合并；合并后检查失败则保留现场、记录证据并给出修复计划。不使用 `reset --hard`、强推或清除 Docker 数据卷。

用户确认本计划后才执行。P2.4b 从合并后的干净 `main` 建新的 `feature/` 短期分支，并单独按其计划实施。
