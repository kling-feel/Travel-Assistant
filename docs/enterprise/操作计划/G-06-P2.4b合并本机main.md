## 执行顺序

1. 重读《产品需求》《软件架构》《当前进度》和本计划，核对当前分支、工作区、提交图及 `main...HEAD` 文件清单；检查本轮新增 G-06、P2.4c 计划、索引和进度记录的改动。先用 `git diff --check` 和暂存清单核查内容，仅把这些计划文档作为单独提交保留在 P2.4b 分支；不纳入 `.env`、本机备份、数据库文件或其他无关文件。出现意外改动先调查，不覆盖。
2. `git fetch origin` 后检查 `origin/main`。如果远端不再是上次核对的 `fbb02bb`，先报告差异和影响，暂停本次合并；不自动拉取、变基或覆盖。确认本机 `main` 仍是当前分支祖先、工作区干净，且可以快进。
3. 复核两项 P2.4b 提交与计划文档提交的文件列表、v005/v006 迁移不可改写的边界、重置命令的显式保护和 Git 忽略规则。运行现有 23 项自动化测试、两日期离线航线校验、Python 编译、依赖检查，并确认旧 `/api/graph/` 交易路由仍未注册。这里不启动已停止的 PostgreSQL；沿用已记录的 P2.4b 实库验收，不把离线检查误称为重新做了实库验证。
4. 全部检查通过后切换本机 `main`，执行 `git merge --ff-only <历史功能分支>`。若不能快进则停止并分析分叉，不自行产生合并提交或改写历史。
5. 合并后检查 `main` 与分支末端一致、工作区干净，复跑自动化测试、离线校验及必要的编译/依赖检查。将实际提交、测试、数据库未触碰及下一步写入《当前进度.md》，在本机 `main` 单独提交进度记录，再核对最终状态。
