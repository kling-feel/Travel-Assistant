## 目标与已核对基线

把本地 `feature/p33c1-isolated-acceptance` 的 P3.3a～c2 成果快进到 `main`，再同步到旅客已授权的 `https://github.com/kling-feel/Travel-Assistant.git` 的 `main`。制定计划时，功能分支 `abdaa51`、本机 `main` 为 `8fc9d12`，功能分支比本机主线多 5 个提交，差异为 39 个路径；工作区干净。本机 8000 已接新批次 5436，旧批次数据卷和新旧备份保留。完整测试基线为 **250 项通过**，详情见[P3.3c2 验收记录](../P3.3c2-正式入口切换验收记录.md)。

当前受限工作台访问 GitHub 443 失败，因此**没有把本机保存的远端引用当作实时远端状态**。真正执行时必须先从能访问 GitHub 的环境读取远端 `main`，确认仓库身份和快进关系；如果网络仍不可用，停止在本地，不尝试推送。

## 旅客确认后的执行顺序

1. 重读[产品需求](../产品需求.md)、[软件架构](../软件架构.md)、[当前进度](../当前进度.md)、[公开发布规则](G-发布同步与公开内容规则.md)和 P3.3a～c2 验收。把本计划、索引及事前进度记录单独提交到功能分支，提交说明使用中性项目表述；核对工作区干净、目标分支是本机 `main` 的后代。如计划范围变化，先告知旅客并重新确认。
2. 用 `git remote -v` 核对唯一目标仍为上述仓库，在可访问 GitHub 的环境运行 `git fetch origin`；分别记录远端 `main`、本机 `main` 和功能分支完整哈希。只接受远端 `main` 与本机 `main` 一致、功能分支可快进的情形。远端已前进、仓库身份不符或出现分叉时停止；不做强制推送、变基、重写历史或猜测冲突解决方式。
3. 审查 `main..功能分支` 的全部文件、提交说明与新增公开内容；核对不包含 `.env`、API 密钥、账号密码、原始 SQLite、数据库备份、忽略目录、测试费用流水，以及旅客要求避免的工具品牌字样。复跑凭证形态扫描、`git diff --check`、现行文档链接和脚本路径核对。旧历史不改写；若发现新增公开内容问题，先在功能分支修复并重新验收。
4. 在功能分支运行完整自动化测试（当前 250 项）、Python 编译、页面脚本语法、依赖检查和离线样本／迁移守卫回归。本步只读代码与交付样本，不调用付费模型或搜索，不操作 8000、5433、5436 或任何数据卷。若测试数量或结论变化，解释并修复后再推进。
5. 检查全部门槛通过后，执行 `git switch main` 和 `git merge --ff-only feature/p33c1-isolated-acceptance`。本机 `main` 前进后再次核对测试、文档、公开差异与工作区。把实际哈希、门槛和发布状态补入《当前进度》，在本机 `main` 做一笔中性说明提交。若合并后核对失败，停止推送并如实记录本机主线已前进。
6. 推送前再次读取远端 `main` 哈希，确认它仍等于本机合并前的共同基线；只执行普通 `git push origin main`，不推送功能分支或标签，不使用 `--force`。推送后读取远端哈希，必须与本机 `main` 一致，再核对公开最新树和进度。若网络或权限使推送失败，保留“本机已合并、远端未同步”状态，定位原因后单独报告；不重复改写历史。

## 停止点与边界

- 本计划的确认只授权上述**本机快进合并及目标 GitHub 仓库的普通 `main` 推送**。不授权删除数据卷、重置演示数据、部署云服务器或公开数据库端口。
- 旧批次仍在独立卷，5436 为当前本机演示库；Git 发布不改变运行数据库。8000 若临时离线，先按 README 核对容器与专用启动入口，不以 Git 合并修复运行故障。
- 若远端不可达、哈希不符、测试／安全扫描失败或 Git 工作区出现来源不明的改动，停在该步骤，向旅客给出具体差异和下一方案；不会自动合并、推送或改写历史。
