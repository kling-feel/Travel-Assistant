# P3.1f4：旅客页面与长程验收操作计划

> 制定日期：2026-10-22｜状态：提前规划，前序步骤完成后按实绩复核、细化费用并单独确认；不授权主线合并或远端推送。

## 1. 目标

把 P3.1f1～f3 的任务状态、条件取消、推荐和行程展示组合为旅客真正能操作的页面流程。用户无需复制助手长句或手写候选编号，就能从查询候选进入待确认卡；仍须逐笔核对并点击确认。以用户提供的整段真实对话而非几轮短脚本作为验收依据。

## 2. 页面实施步骤

1. 候选航班、房型和车辆显示可理解的主要信息：中文出发／到达或地点、当地日期时刻、示例总价、必要条件和次级代码。每个候选提供明确的选择入口；点击“预订这班／选择此房型”等只发起或填入对应**提案请求**，不能直接确认订单。服务端始终重新核实候选 ID、任务条件、报价版本、归属和可售状态，前端传参不能成为事实来源。
2. 在对话答复中简要说明本轮已记住的条件和下一步，例如“上海出发、伦敦目的地、明日无班，已查到 10 月 27 日最早班次；你可选择这班生成待确认卡”。若已建卡，答复摘要其对象、当地时间、示例金额及仍需页面确认，不重复宣称已预订。
3. 对澄清问题给具体选项：缺出发地只问出发地；“上海附近还是伦敦落地后”列两个地点；多笔汉堡出发机票列不同日期和航班。一般对话和“前面说了什么”使用 P3.1f1 的可信会话状态自然回应；不能让模型改写数据库事实。
4. 复核行程区域的有效、已结束、已取消卡片和待确认动作卡的层级、状态文字、颜色对比、键盘操作、窄屏布局及刷新行为。用户确认取消后，旧订单从有效区移到历史区；拒绝卡则原订单保持有效。页面仍清楚说明所有交易为示例，不产生真实支付或出票。

## 3. 连续回放与质量门槛

1. 在独立 PostgreSQL 测试环境回放用户本次完整对话：伦敦订票条件补全、明日无班后的最早选择、确认卡与订单、当前有效行程、保留伦敦并取消其他、按汉堡出发机场选单、上海当天酒店／天气、明日目的地与航班、会话回顾及一般离题问题。逐轮记录输入、任务状态、查询、候选、卡片、订单和审计。把历史取消订单与未来有效订单同时放入样本。
2. 覆盖机票、酒店、租车九类既有写操作，卡片确认／拒绝、过期、重复请求、并列候选、价格变化、跨账号、模型坏结构、搜索无结果／超时及提示注入。重启 API 和隔离数据库后继续同一会话；不把页面仅显示历史记录当作模型实际记住任务。
3. 使用已配置的真实 DeepSeek 和默认开启的阿里云搜索做连续页面联调。实施前列出密钥存在性检查、预估请求数和费用停止线；建议本阶段不超过 **40 次模型请求、25 次搜索请求**，全部尝试和重试计数。阿里云专属价格仍需以实际账单核对，不把未知单价包装为确定总价。正式演示库仅做只读对照，不覆盖用户正在调试的会话或订单。
4. 桌面与约 338 像素宽窄屏实际操作查询、选择、查看卡片、确认／拒绝、行程刷新和历史展开。验收材料仅保存脱敏结果，不提交密钥、账号口令、完整个人对话或数据库备份。

## 4. 发布判定

核心连续任务在固定模型和真实模型回放中均不能要求用户重复已提供条件；每笔动作的目标、价格、政策和订单前后状态须可核对。普通对话中不出现已取消订单，明确问历史才出现；页面四种状态可明显分辨。任何错人、错订单、未经确认写入或无法解释的审计差异均为阻断，不通过“测试总数增加”掩盖。把通过、失败、未测、费用和剩余风险写入《当前进度》，更新实际需要的需求、架构与 README。只有全部阻断项通过，才重新制定 G-16 的本机主线合并与 GitHub 同步计划并另求用户确认。
