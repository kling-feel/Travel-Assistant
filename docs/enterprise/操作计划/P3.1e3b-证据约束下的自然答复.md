# P3.1e3b：证据约束下的自然答复操作计划

> 编写日期：2026-10-21｜状态：用户已确认，功能分支已实施并验收；结果见《当前进度》。本计划承接 P3.1e3a，处理缺陷 D13；地点中文展示与主题审查 D14 另列 P3.1e3c。此文档不授权重置正式数据库、合并本机 `main` 或推送 GitHub。

## 1. 当前问题与本步目标

开工前已重读《产品需求》《软件架构》《当前进度》和 P3.1e 缺陷路线，核对功能分支 `feature/p31-traveler-ui` 的提交 `3d25f4c` 与干净工作区。当前 DeepSeek 主要完成一次 JSON 意图路由；行程、政策、航班／酒店／租车候选、推荐及缺条件追问随后由固定模板输出。交易提案又由 API 独立生成卡片提示，因此一轮里即使识别正确，也可能重复罗列候选、说得像表单，或没有顺着旅客当下目标给出明确下一步。

本步让助手对已核实的事实给出更自然、简短、能推进任务的中文答复：直接回答问题，按需点出一两个关键事实，并只追问真正缺少的一项条件。**模型负责表达和选择重点，事实仍只取自数据库、版本化规则或已核查来源；模型不能改变交易参数、确认卡或订单状态。**

## 2. 答复边界

| 场景 | 预期答复 | 服务端约束 |
| --- | --- | --- |
| “最近还有行程吗／那班几点起飞” | 先回答有无有效行程或准确时间，再给相关订单／航班提示 | 状态、日期、时区和订单归属来自本人只读结果；已取消订单不说成待出发 |
| “明天没有票，那最早哪天／能订吗” | 解释本次查询结论，衔接仍有效的最早班次，并说明预订需确认 | 班次、时间和金额只来自当前有效候选；不猜航班或自动下单 |
| “订这班，顺便找落地酒店” | 机票卡状态与酒店缺项分别说明，不把整轮变成泛泛缺条件提示 | 卡片数量、状态和确认方式由服务端生成；酒店日期按既有落地规则核对 |
| “这个为什么不能取消／退多少” | 引用本人订单和适用的虚构政策条件解释；无法核对时说明具体缺口 | 规则 ID、版本、费用和退款金额由业务服务计算，不靠模型推断 |
| “附近有什么推荐” | 用已选定城市的有来源地点作简短介绍；距离未知就不提距离 | 地点事实、城市和审查时间来自可信目录；搜索文字不能指挥模型或交易 |
| 问候或一般交流 | 保留简短自然对话，并能回到当前旅行任务 | 不附加未经核实的日期、票价、政策或执行承诺 |

## 3. 实施顺序

### A. 建立可用证据与回答结构

1. 在隔离库回放用户已经提供的真实对话及 P3.1e1～e3a 的代表性多轮，记录重复提问、误用旧候选、追问过多和答复冗长的位置；先明确可比较的基线。
2. 让只读工具提供受控的回答证据单元：事实来源、所属旅客和当前任务、有效时刻、可直接显示的中文事实片段，以及“下一步可问什么”。现有 API 引用契约保持兼容；必要的内部元数据不得向其他账号暴露。
3. 给回答明确状态：已回答、需澄清、无结果、已生成待确认卡、提案失败、执行结果。交易状态以服务端实际结果覆盖模型草稿，不能让“已生成卡”被写成“已预订”。

### B. 受限的语言组织

1. 对有事实依据的只读答复，在取得证据后让 DeepSeek 选择回答重点、证据编号与一个具体后续动作，并组织简短自然过渡；模型输出采用限定结构，不接受任意新增产品、金额、日期、政策或订单状态。
2. 服务端根据被选中的证据片段渲染关键事实，检查证据编号、任务关联和输出长度；对缺失、越权、矛盾、包含新数字或未经证实事实、模型超时／错误的结果，退回已有确定性答复。避免靠单个关键词过滤器保证事实正确。
3. 不为每个“你好”或已经定向澄清的轮次额外调用模型；复杂只读回答可增加一次受限组织调用，并记录延迟、token 与降级比例。保留 DeepSeek 主模型与现有 GPT／本地兼容适配器；不要求新增密钥。
4. 交易提案生成、确认卡展示、金额和政策摘要继续由服务端生成。混合任务可自然说明两项任务分别推进，但不得让模型改动动作参数、报价、规则或确认状态。

### C. 页面与结果一致性

1. 对话正文采用短段落和明确的下一步，避免重复列出页面已有的全部候选；候选和卡片仍通过结构化数据展示，保留中文主信息及核对用代码。
2. 历史回放与请求键重试返回同一完成答复和卡片，不重新生成不同措辞或新卡。新会话、另一账号不继承证据或上下文。

### D. 验证与记录

1. 增加有意义的场景回归：连续追问起飞时间、无票后最近班次、选班并问酒店、最近行程与取消历史、政策费用、缺一个条件、地点推荐、多任务一张卡、请求重试和跨账号隔离。
2. 注入无依据的日期／金额／城市、提示词指令、模型返回坏结构、超时或宣称“已预订”；核对均被拒绝或安全降级，订单和卡片状态不变。再核对拒绝、过期、并发确认仍由原事务边界处理。
3. 全套自动化测试、Python 编译、页面语法和文档链接检查通过后，在隔离数据上做少量真实 DeepSeek 多轮对比，计划上限 20 次模型调用；只有推荐场景才可能使用已配置的阿里云检索，最多 4 次公开城市查询。记录实际调用、耗时、成功与回退情况，费用以供应商账单为准，不记录密钥或完整私人对话。

## 4. 验收与停止条件

- 真实多轮中，旅客问到的主问题先得到对应事实或明确缺口；“最早班次／那班／落地酒店”等已有任务能顺畅衔接，且没有无关的整段候选重复。
- 所有显示的订单状态、城市、日期／时区、金额和政策均可回溯至当前有效证据；模型失败时仍有可用答复。确认前无订单写入，卡片只按真实业务提案生成。
- 若出现跨账号事实、错金额／错日期、未确认却声称成功、搜索注入影响交易，立即停止真实联调，修复并重新验证对应场景。

本步不改航线、价格、政策或原 SQLite，不重置／写入正式演示数据库，不合并主线或推送。若实施发现必须迁移检查点结构或改变 API 契约，先补充本计划的兼容方案并告知用户。验收结果写入《当前进度》，必要时同步《产品需求》《软件架构》，仅在功能分支提交。之后单独规划 P3.1e3c：190 条地点的中文展示名、别名与主题人工核查；再规划完整旅程和正式 PostgreSQL 重启验收。G-16 继续暂缓，待独立确认。

## 5. 实施说明

本步采用保守的受限组织方案：生产模型在只读查询得到服务端答复后，额外返回 `plain/list` 版式与预设下一步提示编号；服务端保留原有事实片段，只允许候选列表换行和选用预写的提示。模型无法自由改写金额、日期、政策正文或订单状态。无候选／无证据的澄清、一般对话和交易轮次不增加这次模型调用；坏结构、超时与网络错误回退原答复。该方案改善候选可读性和任务推进，**尚不等于任意事实问答都可自由自然生成**。真实回放、完整测试及剩余限制见《当前进度》。
