## 2. 请先选择发布路径

### A. 保留全部本地提交，普通快进

经再次审计与回归后，在本机 `main` 对功能分支执行 `git merge --ff-only feature/live-source-recommendations`，再用普通 `git push origin main` 同步。优点是 71 个阶段提交和本机主线保持完整；代价是这 71 个旧快照及旧文件名会一并公开。最新文件树可保持零品牌命中，但历史页面达不到用户要求。仅当用户明确接受该结果时执行。

### B. 只发布整理后的成果快照（建议）

保留远端已有历史，不做强制推送；在 `origin/main` 之上建立一个本地发布分支，把已验收功能分支的**最终完整文件树**导入为一个中性说明的发布提交。这样新增的公开历史只有干净的最终快照，不公开 71 个本地阶段快照。代价是本机 `main` 不能继续沿原来 71 个提交快进，需要先给旧 `main` 与功能分支各建立仅本机的可恢复引用，再把本机 `main` 指向新的发布提交。原有提交仍在本机备份引用中，不删除、不推送这些备份引用。远端已有的旧历史仍可见。

### C. 追求整个仓库历史零旧字样

需要另拟远端历史重写或迁入新仓库的独立方案。可能影响既有克隆、链接、协作者和 GitHub 缓存；本计划不执行该路线。
