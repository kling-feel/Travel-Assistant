# P3.3：演示日期维护与部署准备分步路线

> 2026-10-24 制定｜状态：旅客已选择新演示批次并保留旧记录；P3.3a 预检与 P3.3b 隔离构建已在本地功能分支完成，P3.3c1 验收计划待确认，正式切换另拟 P3.3c2。承接已发布的 P3.2；每个执行子步另有独立计划和确认，结果写入[当前进度](../当前进度.md)。

## 1. 为什么先处理日期

现有虚构航班以 `demo_state.as_of` 为演示基准，只覆盖随后约 30 天；酒店与租车也按该基准生成日期窗。现行 `scripts/import_network_data.py` 可以整体平移虚构供给，但 `--apply --reset-demo --backup` 会删除并重建旅客、订单、会话、确认卡、结果、审计与图检查点；有额外账号或待确认卡时会拒绝重置。它适合显式重建，不适合作为服务启动时静默更新。已经由旅客确认的订单若随每次启动改变日期，会与原确认卡及历史记录不一致。

**已确认方向**：每次需要新演示日期时，在独立数据库项目和数据卷创建新演示批次，整体平移航班、酒店、租车及初始订单；旧批次数据库和其中的订单、会话、确认卡、审计保持可恢复，当前 8000 页面和正式演示库不在准备阶段受影响。通过明确的切换步骤选择新批次，不在页面请求或 API 启动时自动改写数据。旧批次记录不自动混入新批次。

## 3. 决策与风险

1. **旧数据保留方式（已确认）**：旧演示批次继续留在原数据卷，新批次用独立项目／数据卷；旧记录不自动并入新批次。即使旧卷仍在，也须通过有效备份及恢复演练证明可恢复；何时把本机演示入口切到新批次，仍由旅客在 P3.3c 单独确认。
2. **运行日期与历史含义**：航班供给可整体平移；已确认订单、已取消历史和确认卡必须与其批次一起保持原始语义。不能只改 `demo_state.as_of` 而不更新相关产品，也不能只移动订单时间而留下旧确认金额与审计。
3. **部署顺序**：先证明可恢复的本机批次更新，再设计云端运行。公网访问、HTTPS、密钥管理及备份成本须在 P3.4 单独核对，不让部署反过来改变交易规则。

本路线只提出下一阶段顺序，**不授权数据库写入、日期平移、正式切换、合并或推送**。
