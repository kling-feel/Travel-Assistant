# P3.1f：长对话记忆与行程体验修复总计划

> 制定日期：2026-10-22｜状态：事前规划，等待用户确认首步；不授权业务代码修改、数据库重建、主线合并或远端推送。

## 1. 背景与目标

用户在正式旅客页面连续测试时发现：上海至伦敦的目的地、日期下界和预订意图在追问中丢失；需要复制系统回答才能订票；“保留伦敦、取消其他行程”和“取消汉堡出发的机票”不能按本人订单属性办理；“明天适合去哪并订机票”没有结合可售航班、地点和可核实天气；“你记得我们说过什么”不能回顾会话。普通“我的行程”还列出已取消订单，行程页的已确认／已取消卡片仅靠一行状态文字区分。

本计划以用户真实对话为回归主线，目标是让助手稳定承接目标、只问真正缺少的信息、能根据本人有效订单和当前候选生成正确待确认卡，同时保留现有逐笔确认、确定性价格／政策和来源边界。新发现的真实使用缺陷作为发布阻断项；G-16 的本机主线合并与远端同步暂缓，验收通过后另写新计划。

## 2. 已确认的产品规则

1. **普通对话不提已取消订单。** “我有什么行程／近期安排”、航班落地酒店、地点推荐、候选选择和任务记忆只使用本人仍有效且与问题相关的订单，不附加“另有几笔已取消”的提示。只在旅客明确问“取消记录／历史订单”等历史问题时，才单独列出已取消记录。取消动作完成时可以说明本次操作结果。已取消订单仍在数据库、审计、页面历史中，绝不物理删除。
2. **行程页保留可追溯历史，但视觉上区分状态。** 默认先显示有效行程；已取消卡片进入明确的历史区域，标题、状态徽标、边框／底色、可用操作和排序均与已确认行程不同。状态不只靠颜色表达，窄屏与桌面都可辨；动作确认卡也不得与已确认订单卡混淆。
3. 旅客自述“我在上海”仅是当前会话的自述所在地；订单和到达机场来自数据库。新会话可查询本人订单，但不继承旧会话的自述地点或未经确认的旅行偏好。
4. “没有明天的航班就订最早的”表示以上海、伦敦、明日为明确条件和日期下界，查询窗口内唯一最早班次可形成待确认卡；有并列或缺少路线时澄清。不得因为旧候选存在就选择旧票。
5. “取消伦敦以外的行程”先列拟保留／拟取消的本人有效订单。唯一可识别的每笔可生成独立取消卡；不能确定“伦敦相关”范围时先列明具体订单并澄清。每笔仍需旅客在页面单独确认。
6. “明天找风景适宜且有航班的地方”先按本人自述出发地、指定日期的模拟可售航班筛城市，再按经核查地点主题和明确偏好推荐；天气只在城市、日期、发布时间及来源均核实后作为理由。现有天气核验只覆盖中国可达城市；境外地点未取得可靠预报时不宣称天气适宜。旅客选定目的地及班次后才提出订票卡。

## 3. 当前代码证据与设计取舍

- `chat_messages` 保存完整会话，但每轮 API 只送最近 12 条消息，路由模型再看最近 10 条；PostgreSQL 图检查点另存 `context`、`task_contexts`、`candidates` 和 `location_context`。保存记录不等于能承接当前目标；需要结构化、可审计的工作记忆，不把无限历史直接塞进模型。
- `dialogue_context.read_request` 与交易路由分开补条件。只读解析复核表明，首轮“去伦敦并购买机票”没有把伦敦作为下一轮订票任务目的地；后续“我在上海明天出发”和“我要去伦敦”无法自然合并。先修状态更新，再调整路由和提案入口；模型可解释意图，服务端继续核实订单、候选、价格和政策。
- `agent_proposals._owned_order` 对多笔订单主要要求精确订单 ID，缺少按航班出发机场／目的地等事实筛选。新增筛选必须只读本人有效订单；多笔命中则列清差异，不由模型猜。
- `agent_reads` 的普通“我的行程”逐条包含取消记录；`static/app.js` 的行程卡片统一使用 `record()`，没有按订单状态分组或样式。对话过滤与页面分组分别实现，保留现有 API 的完整订单数据供历史查询及审计使用。
- `answer_composer` 只允许模型改版式和固定下一步提示。后续可以增强基于证据的自然回复，但模型不得改写航班、订单状态、金额、政策和外部来源事实；一般离题问题按产品需求作简短回应。

## 4. 分步实施与每步验收

### P3.1f1：工作记忆、连续补条件与可追溯诊断

先建真实对话的脱敏逐轮验收矩阵；统一当前任务的目标、已确定条件、条件来源、待补问题和候选作用域。修复订票意图从“伦敦→上海明天→若无班最早→就订这班”的继承，支持明确更正、切换话题后恢复及询问“前面说了什么”。模型路由输出只作受控任务更新；缺省、坏 JSON 或模型失联不能建错卡。详细事前步骤见 [P3.1f1](P3.1f1-工作记忆与连续订票.md)。固定模型和少量真实模型回放均须达成目标；本阶段不改正式演示订单。

### P3.1f2：本人订单筛选、取消语义与行程页面

补“汉堡机场出发”“除伦敦以外”等订单选择语义，按旅客、订单状态、航线／酒店城市和时限做服务端筛选。普通行程答复彻底排除已取消记录及数量提示；明确问历史时单独读取历史。行程页按有效／历史分组，已取消卡片清楚标记、弱化操作、不能被误认作待出行；动作卡状态也独立呈现。通过机票、酒店、租车三类订单，以及取消后刷新、重新登录、桌面和窄屏的验收。任何卡片仍逐笔确认。

### P3.1f3：有证据的“目的地＋天气＋航班”规划

组合模拟航班的指定日可售城市、人工核查地点目录、偏好和可验证天气。给出少量可解释候选及未满足条件；无直达班次、天气来源缺失、搜索超时分别降级。境外天气需要先确定可核实来源和核验规则，再决定是否纳入；不能把搜索摘要当气象事实。选择城市／航班之后重查报价和可用性，再生成待确认卡。联网搜索只读，不能执行交易。

### P3.1f4：页面承接、长程联调与发布门槛

为候选添加明确的“选择此班／此产品”交互，并在对话摘要卡片目标、当地日期、示例金额；页面不代旅客点击确认。真实 DeepSeek、默认开启的阿里云搜索、两账号、重启、改口、跨话题、过期候选、并列候选、取消与历史查询，按用户整段对话连续回放。覆盖九类原交易动作不退化。记录每轮预期／实际任务状态、候选、卡、订单和审计，以及调用次数、费用与残留问题。所有阻断场景通过后，再另拟本机主线合并和 GitHub 同步计划。

每一步开工前均重读《产品需求》《软件架构》《当前进度》，核对工作区、运行服务和数据基线，另写独立操作计划并经用户确认；完成后更新《当前进度》。后一阶段不能借前一阶段的确认直接开工。

## 5. 总验收门槛

| 场景 | 必须满足的结果 |
| --- | --- |
| 连续订票 | 不重复索要已给出的伦敦、上海和日期下界；唯一最早班次生成正确卡，确认前订单不变。 |
| 条件取消 | 按出发机场或保留目的地筛本人有效订单；不确定时准确列出可选项；每张取消卡只影响目标订单。 |
| 普通行程与推荐 | 已取消订单、取消数量和取消目的地均不进入正常行程回答及推荐依据；明确问历史时可以单列。 |
| 行程页 | 有效与已取消订单在桌面、窄屏有文字、位置和视觉差异；历史仍可查，不能从已取消卡发起误操作。 |
| 旅行规划 | 推荐城市在当前模拟可售航班范围内；天气／地点均有可核查依据；无依据就说明，不能编造。 |
| 安全与恢复 | 未确认、拒绝、过期、重复、越权、模型／搜索故障不产生额外订单写入；进程重启后会话、卡与订单一致。 |

## 6. 数据、费用、Git 与停止条件

先在独立测试库和固定模型重放；正式演示库只读检查，绝不为测试重置用户正在调试的数据库或代为确认卡。各步真实模型与搜索联调的调用上限写在对应独立计划中，执行前复核费用估算并向用户说明；密钥不打印、不进入日志、文档或 Git。若发现错对象卡、未确认写入、跨账号泄露或订单与审计不一致，立即停止对应联调并保留脱敏证据。

实现提交留在当前功能分支。用户曾要求 GitHub 所有公开内容避免开发工具品牌字样，后续提交说明、文档及发布内容均按既定公开规则检查。G-16 原计划的前提已被这次真实长对话推翻；本计划及任何一步的确认都不授权合并本机 `main` 或推送远端。
