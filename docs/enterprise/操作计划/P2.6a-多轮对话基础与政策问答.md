# P2.6a：多轮对话基础与虚构政策问答操作计划

> 编写日期：2026-10-18｜状态：已执行并按 G-12 合并本机 main；本文件只记录事前方案，实施结果写《当前进度.md》

## 目标、起点和本步边界

让已登录旅客在现有服务端会话中与新版 LangGraph 助手进行基本多轮对话，查询本人行程、模拟航班/酒店/租车候选和版本化虚构政策。主助手保留委派专门助手的原项目结构，但只接正式 PostgreSQL 只读服务。图状态在数据库持久化，页面历史仍由现有会话消息提供。此步建立 DeepSeek 主模型的可配置适配器，以固定模型响应完成确定性验收；有效密钥就绪后才做真实模型联调。

本机 `main` 当前为 `8fe7dea`，已含九类航班/酒店/租车受控交易及 v001～v011 迁移；普通聊天尚不能调用模型。旧图路由未注册，旧游览 SQLite 写工具不可接入。PostgreSQL 容器已停止，演示卷和忽略的备份保留。实施前重新核对 Git、数据库和依赖，不把上述状态视为永远不变。

本步**不从对话创建待确认动作**，不调用订单确认服务；九类交易接入在 P2.6b 单独计划。也不建游览产品/订单、不接联网推荐或页面；P2.7 才处理可达城市经典地点和来源。这样 P2.6a 的验收重点是对话、身份、政策依据、只读查询、状态恢复和故障行为。

## 拟修改的接口与行为

- 增加已登录的 `POST /api/v1/sessions/{session_id}/turns`。请求只含有界旅客文本和客户端生成的请求去重标识；旅客 ID 来自现有 JWT，会话归属由服务端核对，图 `thread_id` 从已验证的会话 ID 派生。响应包含助手文字、明确的轮次状态和政策/候选的结构化引用；本步不返回新动作卡。
- 保留现有会话列表/历史 API。对话轮次保存用户和助手消息，并与图检查点关联；同一请求标识重放不能重复追加消息。同一会话只允许一个进行中的轮次，避免并发覆盖状态。已有 `/messages` 手工追加入口与新图须保持可见历史一致；若无法安全同步，活跃图会话中该入口返回明确冲突，不能形成两套互不相见的对话。
- 主助手处理问候、常规旅行对话及必要澄清；航班、酒店、租车助手只调用正式的本人行程、候选查询和当前政策服务。政策答复先取得结构化规则证据，再由服务端核对规则 ID、版本和适用范围；金额、订单状态及规则关键结论须能对应工具结果，无法核对时不输出肯定断言。未找到或条件不足时追问或说明无法确定。没有联网核验时不回答真实航司的具体政策，也不冒充虚构平台规则。
- 模型可看受限、脱敏的工具结果，不看令牌、密码、数据库连接串或完整内部推理。模型不能自行生成订单、报价、政策条文或“已预订”状态；无交易提案工具、确认工具或旧 SQLite 工具权限。旅客要求景点预订时，说明项目不提供此功能；推荐联网能力尚未上线时，不编造景点事实。
- 主模型使用环境配置的 DeepSeek 兼容接口；GPT、本地兼容模型先保留适配入口，实际工具调用能力在后续单独评估。无有效模型配置时，对话返回清楚的不可用状态，现有健康、订单、政策及查询 API 仍可运行。密钥仅进入 Git 忽略的本机 `.env`，用户不需在聊天中发送。

## 具体操作顺序

1. **开工核验**：重新读取《产品需求》《软件架构》《当前进度》和本计划；检查本机 `main`、未提交文档、远端差异和旧图路由。核对现有 `langgraph==1.2.11` 等锁定依赖及官方 PostgreSQL 检查点组件的兼容用法，再决定附加依赖和初始化方式。只读盘点数据库迁移、演示账号/订单、会话/动作和现有备份；需要改表或初始化检查点前，先保存并验证 Git 忽略的 `pg_dump` 备份。
2. **隔离实现**：核对本轮未提交的规划文档确属本任务且无其他改动后，从本机 `main` 建立 `<历史功能分支>` 分支，先将规划文档单独提交，再实施代码；不丢弃或覆盖现有修改。新增与旧图分离的受控图、模型适配和只读薄工具；主助手及航班/酒店/租车专门助手保持简洁的 Python 模块。白名单只含本步允许的查询与政策工具，显式排除旧 `book_excursion`、`update_excursion`、`cancel_excursion` 及所有直接写订单工具。
3. **会话与持久状态**：用已核对版本兼容的 PostgreSQL 图检查点，定义受控初始化、版本记录、会话清理和演示重置顺序；若需要项目自有表，只追加 v012 迁移，不改写 v001～v011。增加轮次去重/状态记录，约束同会话并发。外部模型调用期间不持有订单事务锁；成功、失败、超时和进程重启后的消息与检查点须有明确一致性规则。
4. **API 与配置**：接入 `/turns` 的身份、请求校验、限长、超时、工具步数及输出大小限制。固定模型可在无真实密钥时运行测试，生产配置缺失则返回明确错误。更新 `.env.example`、README 的登录、建会话、发送多轮消息、查历史与政策操作说明；示例只使用占位符，绝不提交真实凭证。
5. **确定性验证**：使用固定模型输出验证问候、上下文续聊、本人行程、航班/酒店/租车候选、政策 ID/版本、缺字段追问和无依据回答；特意注入模型编造的票价、订单状态及政策版本，验证服务端拒绝或降级为有证据的答复。验证两账号会话隔离、伪造 `thread_id`／旅客 ID、旧写工具不可达、重复请求、同会话并发、空回复/超时/异常、应用重启恢复，以及普通聊天不能创建动作或修改九类订单。选择必要的 API/数据库实测，并复跑现有 44 项测试及旧路由检查；不为了覆盖率而堆叠镜像实现的测试。
6. **收尾**：清理本次临时会话、检查点和轮次记录，核对演示订单、政策、动作与审计仍符合基线；停止数据库并保留卷/备份。运行 `git diff --check`、编译与依赖检查，审查变更文件和凭证风险。在功能分支提交实现与《当前进度》的实际结果；本机合并另拟 G-12 计划并确认，远端推送另行规划。

## 验收、依赖和失败处理

- 固定模型场景在同一服务端会话中多轮可用；进程重建后历史和图状态对应；重复请求只产生一个轮次。两个旅客的会话、订单和工具结果完全隔离。
- 政策回答引用正式规则 ID/版本；不存在的航班、政策或订单不能由模型补造。对话不能创建任何新待确认动作或订单，旧 `/api/graph/` 路由仍不注册。
- 有效 DeepSeek 密钥**不是本步开始条件**。本步完成只说明固定模型与真实数据库的受控链路通过，不宣称 DeepSeek 真调用已验收；P2.6c 前需用户按 README 配置新的有效 API 密钥/地址。P2.7 真实联网前另需检索服务凭证。
- 如果检查点组件不兼容、轮次去重无法保证或现有 `/messages` 与图状态冲突，先在本分支解决并复测；如需改变用户可见接口语义、身份边界或迁移策略，修订计划向用户说明后再继续。数据库变更失败时保留现场和已核验备份，不执行清卷、强推或自动合并。

用户确认本计划后才实施 P2.6a。P2.6b 交易提案、P2.6c 真实模型联调、P2.7 联网推荐及 P3 页面均需各自的事前计划和确认。
