# P2.4：智能体接入与持久化检查点操作计划

> 编写日期：2026-10-17｜状态：历史草案，已被 R-01 阶段路线替代，**不得按此执行**；未来智能体接入按 P2.6 另写计划并确认

## 目标与起点

G-04 合并完成后，从干净本机 `main` 建 `<历史功能分支>`。在现有 FastAPI、LangGraph 主助手／航班助手／酒店助手框架内，让登录旅客通过自己的会话提问，助手读取 PostgreSQL 中的本人行程、候选航班、酒店产品和模拟规则，并通过 P2.2 服务生成待确认卡。订单写入只由 P2.3 的指定动作确认 API 执行。会话刷新或应用重启后，可恢复消息与图状态。

旧 `graph_chat/finally_graph.py`、`agent_assistant.py` 的路线仍直接绑定原 SQLite 写工具、客户端 `passenger_id`、文本 `y` 与 `MemorySaver`；旧 HTTP 路由当前未注册。本步保留其“主助手委派专门助手”的设计，但新建受控图与薄工具接入正式服务，绝不直接注册旧图。租车、景点代码保留为参考，不接入本阶段交易工具。

## 建议交给用户判断

1. **先固定行为，再实测云模型（推荐）**：P2.4 先用可控的假模型／固定工具调用验证路由、两张卡、权限、重启恢复和失败边界；只做可配置的 GPT／DeepSeek 适配。P2.5 再用用户自己的 API 密钥实测真实模型、提示词与工具调用质量。这避免把模型波动当成业务逻辑缺陷，也无需在本步分享密钥。
2. **本地模型先做能力探测（推荐）**：保持相同接口，但只有通过结构化工具调用测试的本地模型才进入提案流程；只会聊天的模型可用于只读问答试验。能力不足时返回清楚提示，不产生订单写入。
3. **图状态与展示消息分工（推荐）**：继续用 `chat_messages` 向页面展示历史，用 PostgreSQL 检查点保存 LangGraph 内部状态；二者通过服务端会话 ID 关联。演示重置时同步清理该会话的检查点，避免留下一份不可见的旧图状态。

以上是本计划采用的默认建议；若用户希望调整真实模型试测时机或本地模型范围，先修订本计划再执行相关步骤。

## 接口、身份与模型边界

- 增加登录后的 `POST /api/v1/sessions/{session_id}/turns`：只接收长度受限的旅客消息和必要的请求去重标识；旅客身份取自 JWT，会话由服务端核对归属和活动状态。返回助手文字、该轮新增的待确认动作 ID／卡片，以及明确的失败状态。已有只追加用户消息的接口与历史读取保持可用；首次运行新图时要纳入该会话已有消息，避免同一会话出现两套互不相见的历史。
- 图运行配置中的 `thread_id` 必须由已验证的会话 ID 派生；任何客户端传入的旅客 ID、线程 ID、模型工具参数中的“所有者”都不能覆盖服务端身份。模型上下文不放访问令牌、密码或 API 密钥。
- 新图的航班／酒店只读工具调用 P1 查询服务，规则只读工具调用版本化演示政策；提案工具只调用 P2.2 `create_proposal`。不给新图 P1 订单写服务、P2.3 确认服务或旧 SQLite 写工具的引用。
- 模型只可选择意图和提议参数；订单归属、日期、可用性、规则与价格由确定性服务验证并生成卡片。回答必须把“待确认”与“已执行”分开，明确模拟性质；不得因模型文字说“已订好”就标记订单成功。
- 模型适配由配置注入 GPT、DeepSeek 或本地兼容接口；缺少模型配置时健康检查和只读 API 继续可用，对话接口返回明确配置错误。运行时限制超时、空回复重试次数、单轮工具步数和消息长度，不记录密钥或完整模型内部推理。

## 实施顺序与分层检查点

1. **起点核验**：再次读取三份基线文档及本计划；确认 G-04 已完成、本机 `main` 干净、v004 已在演示库应用。检查当前锁定的 LangGraph 版本及其 PostgreSQL 检查点组件兼容方式，再锁定新增依赖；不凭旧教程猜测 API。
2. **受控图与工具**：在 `graph_chat/` 和 `tools/` 建简洁的新图／薄工具。主助手负责分发与汇总，航班助手处理查询和改签／取消提案，酒店助手处理查询及预订／改期／取消提案。加入工具白名单和结构化参数校验，排除旧敏感工具、旧 `y` 恢复路径、租车／景点写入。先用固定模型输出验证无确认时订单不变。
3. **会话与检查点**：把图检查点落到本机 PostgreSQL，与 `chat_sessions` 使用同一服务端会话 ID；明确检查点表初始化、重复初始化、会话清理和演示重置方式。模型调用期间不长期持有订单数据库锁；若调用失败，已保存的用户消息和错误状态要可见，不能写订单。对同一工具调用的重试／恢复做提案去重，避免重复卡片。
4. **旅客对话 API**：加入 `/turns` 并复用现有 JWT、会话和消息服务。同一请求去重标识重复提交时返回既有结果或续跑同一轮，不再追加第二条用户消息。成功轮次保存旅客与助手消息，返回新增动作；模型或检查点错误返回可定位的失败，不伪造成功。检查点写入、展示消息写入或提案写入任一步失败时，应能根据会话与请求标识恢复或清楚呈现已产生的动作，不把半完成状态说成成功。旧 `/api/graph/` 仍不注册。更新 README，给出 `/docs` 登录、创建会话、发送消息、查看卡片、逐笔确认及查看订单的完整操作步骤。
5. **自动化验收**：用固定模型输出覆盖本人行程与规则查询、航班／酒店委派、五类提案参数、贯穿场景的两张独立卡；确认其中一张不得自动确认另一张。测试跨账号伪造会话／线程、模型试图调用未授权写工具、空回复／超时、重复请求或恢复、价格或订单变化、重启后图状态与消息历史恢复。无用户确认时五类订单均不变。
6. **PostgreSQL 验收与收尾**：在临时旅客／会话上执行真实 API 与图检查点验证，应用进程重建后继续对话并读取两张卡；测试数据和检查点按标识清理，演示订单保持原样，最后停止数据库并保留卷。运行 P0～P2.3 回归、编译和依赖检查。只在短期分支创建本地提交，把实际结果写《当前进度.md》；合并本机 `main` 与远端推送各需后续独立计划。

## 验收门槛与失败处理

- 新对话图只能读取或提出待确认动作，数据库订单在确认前保持不变；正式确认仍必须由旅客对指定动作调用 P2.3 API。
- 两个演示账号不能互读会话、检查点、提案或订单；客户端给出他人的会话／线程 ID 不能改变模型看到的身份。
- 固定模型可在同一旅客会话提出航班改签、酒店预订两张独立卡；重启后继续对话与读取历史，不重复创建相同工具调用的卡。
- 模型未配置、超时、无有效工具能力和错误提案均有明确结果，不产生订单写入；旧图路由仍关闭。

若检查点组件与当前依赖不兼容、无法可靠清理状态，或重试可能重复创建动作，先在短期分支解决并复测；若需改变身份边界、事务职责或对外接口语义，先更新本计划并请用户重新判断。真实模型效果、页面及完整贯穿体验留到 P2.5／P3 验收。
