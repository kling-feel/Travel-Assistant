# P3.1f1：工作记忆与连续订票操作计划

> 制定日期：2026-10-22｜状态：用户已确认，功能与隔离联调已完成；仅覆盖 P3.1f 总计划的第一步。后续 P3.1f2～f4、数据库重建或 Git 发布仍须分别确认。

## 1. 目标和可复现失败

现有完整聊天记录与图检查点不能保证同一订票任务连续推进。用户先说“我要去伦敦旅行，帮我购买机票”，再说“我在上海明天就出发，没有的话就帮我预订最早的航班”，随后补“我要去伦敦”；正式页面分别追问出发地、目的地，最后进入“不会根据上一轮自动重试订单操作”。再问“就订最早的机票”也会丢路线。目标是在同一会话保留明确条件和预订目标，正确处理日期下界、当前候选和任务切换。

## 2. 执行前只读检查

1. 重读三份核心文档、P3.1f 总计划与用户对话；核对当前功能分支、未提交改动、正式数据库及 8000 端口状态。用户可能正在自行调试，**不停止或接管其进程**。
2. 在独立测试环境整理脱敏逐轮矩阵：每轮输入、预期任务类型、已确定字段、字段来源、待补项、候选、卡片和订单计数。对“已确认”状态无法从聊天文字判断是否点了页面确认，验收时须对照动作审计。
3. 固定当前日期和机场当地时区，保留已有机票、酒店、租车交易与价格规则；不改全航线数据或正式库基准日。

## 3. 实施步骤

1. 在现有会话检查点内建立有界的工作记忆：当前目标（查询／预订／取消／推荐）、业务域、出发地、目的地、日期或日期下界、选择偏好、待补条件、当前候选及其查询条件／版本／时间。每个字段区分“旅客明确说出”“数据库查询确认”“仅为建议”，后者不能自动成为交易参数。跨业务任务分开存放；本轮明确改口时覆盖旧值，冲突时澄清。新会话不继承旧会话自述位置和未确认偏好。
2. 调整 `dialogue_context` 与 `controlled` 的衔接：交易请求即使暂缺字段，也把用户已明确的伦敦、上海、明天和“没有就最早”保存进当前航班任务；下一轮补一个字段后继续原目标。明确新话题可以暂停旧任务；再说“前面那班／继续订伦敦机票”时，只恢复未过期且路线、日期相符的任务。模型负责识别目标和补充字段，服务端核对字段来源、候选范围与当前请求。
3. 调整候选绑定和提案前校验：候选与路线、当地日期、报价版本、会话及任务关联；“这班／最早那班”只选当前任务中唯一且有效的候选。明日无班但有之后班次时，先展示核实的最早日期和班次；旅客已明确“没有就订最早”且唯一时可以生成卡。建卡、确认、幂等、价格、政策和归属继续调用现有确定性服务；任何推断不绕开逐笔确认。
4. 增加受控的会话回顾答复：旅客问“你记得前面说过什么”时，概括本会话已明确的旅行目标、当前有效候选、仍缺的条件和待确认卡；引用订单状态时重新查询数据库。旧消息超出模型窗口后仍以工作记忆回顾，不凭空生成不存在的偏好或订单；模型不可用时可用服务端简短事实摘要。
5. 增加脱敏诊断信息：记录本轮路由、工作记忆字段变化、候选选择原因、提案拒绝类别和请求关联 ID，不写密钥、完整对话、令牌或提供方原始响应。页面对旅客展示准确的待补条件，不暴露内部字段。

## 4. 验证方式与通过标准

- 用固定模型连续重放完整订票链，覆盖“伦敦→上海明天→无班则最早→我要去伦敦→就订这班”，以及更正为另一目的地、插入上海景点话题后恢复订票、并列最早班次、旧候选过期、模型给出错误 ID／价格和请求重放。只要唯一目标明确，生成的卡须与数据库候选一致；确认前业务订单不变，审计只记录已发生的提案／拒绝等事件。
- 问“前面说了什么”应准确回顾已确定条件、待补项与当前卡状态，不把已取消订单当作旅行计划；本步尚不改变普通行程查询的完整过滤，P3.1f2 统一完成该规则。
- 运行对话和交易相关回归、完整自动化测试、Python 编译及差异检查。真实 DeepSeek 仅验证连续订票、改口与坏输出降级，建议本步最多 **12 次模型请求尝试、0 次搜索请求**；实施前核对已配置模型与费用估算，逐次记录次数和 token，达到上限即停。结果写入《当前进度》。模型不可用或输出坏结构时，不生成错误卡。
- 若需要真实 PostgreSQL 会话重启验证，使用隔离数据库；不重置或写入默认正式演示库。现有 8000 调试服务保持由用户控制。

## 5. 完成后的交付与边界

更新《产品需求》《软件架构》中实际落地的工作记忆约定，按验收结果更新《当前进度》，提交当前功能分支，并向用户列出通过、失败、未测项目。若出现跨会话串记、旧候选误绑定或未经确认写入，停止继续付费联调，先复核状态与审计。P3.1f2 的取消与页面改动须另出详细计划并再次取得确认；本步不执行 G-16。
