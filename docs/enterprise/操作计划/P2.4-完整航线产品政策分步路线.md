# P2.4：完整航线、模拟产品与政策的分步路线

> 编写日期：2026-10-17｜计划状态更新：2026-10-18；P2.4a/b/c 均已合并本机 main

## 起点和选择理由

本机 `main` 为 `f4f862b`，P2.3 的五类逐笔确认已验收，Docker PostgreSQL 当前停止。现有可交付样本仅 2 个机场、14 班航班、3 家酒店；导入器固定 HAM→BSL；报价只识别 4 个航班号；种子重置会清空演示账号的会话、订单和动作。原虚构 SQLite 只读盘点：115 个机场、33,121 班航班，其中 15,383 班 `Scheduled`，全部 618 条起终点航线均有预定航班；机场坐标与 IANA 时区有效。原数据的统一 `-04:00` 偏移不等于每个机场的当地时区，必须把平移、显示当地时间和状态筛选明确分开。

本阶段按三步推进。每步开始前重读三份核心文档，另写/复核该步详细计划，向用户说明并取得确认；只记录实际结果在《当前进度》。下一步计划可依据上一步真实指标调整。

| 步骤 | 交付边界 | 通过条件 |
| --- | --- | --- |
| P2.4a：全航线样本与时间轴 | 只读提取机场、航班非个人字段到新版本化 SQLite 样本；离线统一平移与校验脚本；不接 PostgreSQL | 115 机场、33,121 班、15,383 条 Scheduled、618 条预定航线，外键/坐标/时区/状态与未来时间窗检查通过；原库和旧小样本不变 |
| P2.4b：正式库导入、报价和演示订单 | 批量导入/种子正式库、生成全部可订 Scheduled 班次的确定性模拟报价与两名虚构旅客的演示机票；支持明确触发的重置、迁移/索引和兼容回归 | PostgreSQL 首次/重复导入、重启持久化、航线与报价覆盖、查询性能及旧 P2.3 流程通过；重置前提示会清理演示会话/订单/动作 |
| P2.4c：酒店/租车供给与政策 | 按可达城市生成有坐标的虚构酒店与租车产品；清理旧 FAQ 并同步版本化交易规则、搜索 API | 可达城市产品覆盖、无虚构航班或模型定价；原有五类事务回归通过；新政策答复有 ID/版本，矛盾和品牌内容不进入交易规则 |

P2.4c 仅建立租车**产品和政策**，旅客租车订单与逐笔确认在 P2.5；智能体与联网推荐分别在 P2.6/P2.7。用户当前无需提供 DeepSeek 或 Tavily 密钥。

## 各步共同约束

1. 原 `travel_new.sqlite`、`travel2.sqlite` 始终只读且不提交；新样本仅含必要非个人字段，航班号在展示层映射为明确虚构标识，不能暗示真实航司报价。
2. 每次初始化以一个有下午替代航班的 HAM→BSL Scheduled 航班为锚，用同一绝对时间差平移所有航班起降时间，保持航班间隔和状态；查询只把未来约 30 天的 Scheduled 班次视为可订。任何无班次路线/日期返回空结果。
3. 报价、产品和规则由可复现代码/版本生成；模型不能凭文本补齐。确认卡价格或规则变化须使旧动作失效，并维持 P2.3 的归属与幂等边界。
4. 新数据进入 PostgreSQL 前，先验收离线样本。数据库导入/重置前记录当前计数和状态，使用事务，失败保留旧可用数据，不删除 Docker 数据卷。已有演示操作不会被日常启动静默清除。
5. 各步只在短期 `feature/` 分支实现和提交，合并本机 `main` 与推送远端分别另出 Git 计划并由用户确认。

## 当前建议

P2.4a/b/c 已合并本机 `main`；P2.4c 覆盖 104 个可达目的地机场和 95 个城市。下一步单独规划 P2.5 航班新预订与租车交易，按确认、价格/规则及实库回归分层实施。远端推送另行规划和确认。
