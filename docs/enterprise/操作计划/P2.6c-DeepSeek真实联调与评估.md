# P2.6c：DeepSeek 真实联调与评估操作计划

> 编写日期：2026-10-19｜状态：用户已确认，实施中；本文件记录事前方案，执行结果统一写《当前进度.md》

## 目标、起点和范围

在 P2.6a/b 已通过固定模型与真实 PostgreSQL 验收的基础上，用**有效的 DeepSeek API**验证真实中文多轮对话、虚构政策问答、航班／酒店／租车查询，以及九类交易从旅客请求到待确认卡的路径。记录可复现的成功与失败样例、延迟、令牌用量和可核算的调用成本；对模型输出格式、意图选择或澄清造成的缺陷做有边界的修复，再复测。

规划起点为本机 `main=62e541c`，工作区干净，`origin/main=fbb02bb`；v013 已应用，本机数据库容器停止。现有 `services/model_config.py` 通过 `ChatOpenAI` 调用兼容接口，温度 0、单次超时 25 秒、自动重试 0 次；新对话图要求模型输出可解析的 JSON。57 项自动化测试与九类固定模型实库验收已通过，**尚无真实 DeepSeek 调用证据**。

本阶段允许调整模型适配、受控图提示词与解析、澄清文案、评估脚本、相关测试和 README。不改变九类交易政策、订单确认 API、正式数据生成规则、游览只推荐范围；不接联网推荐、页面、真实支付或供应商。GPT／本地模型保留适配接口，本阶段不以它们代替 DeepSeek 验收。本机合并和远端推送分别规划。

## 必要配置与调用上限

1. 用户在本机 Git 忽略的 `.env` 中自行配置 `AI_PROVIDER=deepseek`、有效 `AI_MODEL`、`AI_BASE_URL`、`AI_API_KEY`；**不要把密钥发到聊天、截图、日志或提交中**。执行时先核对官方 DeepSeek 文档中的模型名、兼容地址和用量字段，再给出准确的本机配置步骤；检查只报告“是否已配置”，不打印密钥或完整环境文件。旧 API 已不可用，不复用旧凭证。
2. 在用户确认本计划并完成有效配置后，才发起真实调用。先做最多 2 次连通性／JSON 格式试验，成功后逐批测业务；本阶段真实模型**最多 30 次请求**。适配器维持无自动重试和现有 25 秒单次超时，评估脚本记录每次耗时、是否返回可解析结果及服务商提供的 token usage。达到 30 次即停止，需增加调用次数时另行说明结果与预计用途，等待用户决定。
3. 不预先承诺固定货币成本；执行前从官方价格页核对现行计费方式，完成后只按服务商返回的用量和当时公开单价估算，并清楚标注估算条件。若没有可靠用量字段，只记录调用次数和延迟，不编造成本。

## 实施顺序

1. **开工核验与隔离**：重读三份核心文档和本计划，核对 Git 工作区、主线、远端引用及数据库容器。新建 `<历史功能分支>` 功能分支，将获确认的计划单独提交。启动数据库后先只读核对迁移／演示订单基线，再做 Git 忽略的 `pg_dump` 并用 `pg_restore -l` 验证；备份完成前不写入测试数据。不运行演示重置或旧种子脚本。只有演示账号／临时测试账号和虚构订单可送入模型。
2. **离线评估框架**：建立有上限的场景清单和结果记录格式。固定模型先复测：问候与上下文追问、内部虚构政策、真实航司政策边界、无班次、多个候选、酒店／租车日期缺失、模型编造价格与订单、九类动作及双卡全有或全无。记录每轮预期意图、允许的引用、是否应追问／建卡、订单前后计数；不把原始密钥、完整请求头或用户私人数据写入工件。校验本机 README 顶部的旧阶段描述并更新。
3. **少量真实调用**：先验证模型连接和严格 JSON 输出；再用真实 `/api/v1/sessions/{id}/turns` 和临时演示身份，分批测试基本对话、本人行程、虚构政策、模拟航班／酒店／租车搜索、九类交易及“改签＋订酒店”两张卡。每轮以服务端数据库和动作详情为标准判定，模型文字不能证明交易成功。真实模型仅产生待确认卡，**本阶段不调用确认接口去执行其提案**；固定模型验收已有确认事务证据。包含跨账号、无效产品、日期含糊、政策诱导和重放反例。
4. **据失败修复并复测**：若模型输出代码块、非 JSON、漏字段或选择错误，先保存脱敏失败样例，调整结构化输出／解析或提示词，并保留失败时安全澄清；不能以宽松解析放过未经证实的产品、订单、价格或日期。改动后跑针对性测试、全部回归，并在剩余调用额度内重测失败场景。若需改变交易规则、确认协议或超过调用上限，先另拟方案取得用户确认。
5. **收尾**：核对九类交易的真实模型结果、双卡原子性、未确认订单不变、失败无孤儿卡和同请求重放。运行全部自动化测试、两日期离线样本、编译、`pip check`、路由和 `git diff --check`。清理临时会话、检查点、订单和测试账号，对照备份前正式库计数；停止数据库但保留卷与备份。把通过率、失败分类、延迟分布、调用次数／用量／成本估算及未解问题写入《当前进度》，在功能分支提交；本机 `main` 合并另拟 G-14 计划。

## 验收门槛与中止条件

- 真实 DeepSeek 至少完成基本多轮、虚构政策、三类产品查询、九类交易提案和双卡场景；九类动作若因条件不足先安全追问，补齐后须能得到正确待确认卡。所有金额、规则版本、订单归属和候选都以正式服务结果为准；**未经旅客指定动作确认，订单变更数为 0**。
- 模型响应不可解析、密钥无效、超时或服务中断时有明确失败结果，不宣称已执行，也不遗留半张双卡。记录真实失败而不把固定模型成绩当成真实模型成绩。真实政策与地点事实没有来源时不编造；经典地点联网推荐仍留 P2.7。
- 如果用户尚未配置有效 API，可先完成离线评估框架和固定模型回归，但 P2.6c 保持“真实模型未验收”；不擅用其他密钥、其他付费模型或向用户索要明文密钥。若真实模型关键场景未达标且 30 次额度用尽，保留失败证据、停止调用并提出下一轮修复建议。
- 实库测试前后都须核对演示数据基线；若清理或数据库复核失败，保留备份和现场，不重置数据库、不合并、不推送。
