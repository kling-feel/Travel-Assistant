# P2.5c：酒店模拟退款与八类动作总回归操作计划

> 编写日期：2026-10-18｜状态：业务规则及实施均待用户单独确认；本文件只记事前方案，结果写《当前进度.md》

## 目标与推荐规则

为虚构平台酒店取消定义可计算的模拟退款，并对八类写动作做同一轮端到端回归。沿用 FastAPI、SQLAlchemy、逐笔动作卡、确认事务和简洁 Python 风格。仍不发生真实付款/退款，也不连接真实酒店或航司。

**建议请用户判断**：以酒店产品关联机场的 IANA 时区确定“今天”。在**当地入住日期之前**确认取消，模拟手续费 0，模拟应退为订单原总额；从入住日期 00:00 当地时间起不允许取消。现有订单只有入住日期，没有入住时刻，因此这个边界明确、可重复测试，但比当前“入住当日仍能取消”的实现严格。`hotel_book` 与 `hotel_change` 的现有同日入住能力暂保留；卡片和政策须清楚说明“入住当日新订/改期后不可取消”，确认时仍重新校验产品/日期/金额。若用户希望入住当天某时刻前可取消，需要先确定入住时刻字段及规则，再修订本计划。

“应退”只是演示金额，按**原订单总额**而非当前房价计算。取消保留订单和审计，不物理删除。旧酒店 v3 规则与历史动作保留；新规则为 v4，旧待确认酒店卡在确认时因政策版本变化而失效，需重新生成。已有已确认订单不自动取消或改价。

3. 调整 `hotel_cancel` 报价与确认边界：提案时按产品机场当地日期判定，卡片给出原金额、模拟应退全额、零手续费和 v4；确认时在事务内重查本人订单、版本、政策、当地日期及报价。跨过当地午夜、订单被改期/取消、政策或金额变化时，旧卡失效且不写订单。`hotel_book`/`hotel_change` 保持既有日期能力，政策版本随 v4 更新并复核卡片一致性。
4. 增补有必要的单元测试和一个顺序执行的实库/API 总回归脚本或扩展现有脚本。覆盖 `flight_book`、`flight_change`、`flight_cancel`、`hotel_book`、`hotel_change`、`hotel_cancel`、`rental_book`、`rental_cancel` 八类：提案阶段无订单写入，本人确认后金额、状态、版本、结果和审计一致；另一账号不可读/确认；拒绝、过期、旧卡失效、重复确认、两卡竞争、应用与数据库重启后重读。核对酒店退款当地日期两侧及同日入住说明、租车临界时刻、机票差价/30% 取消费。会写库的脚本顺序运行，互不踩测试记录。
5. 更新 API/README 演示步骤、进度文档和验收脚本的清理说明。完成前检查 `git diff --check`、迁移历史、跟踪文件和敏感信息；短期分支提交代码与验收记录。再单独规划本机合并，不把本阶段授权当成合并或远端推送授权。

## API 与密钥依赖

P2.5c 只用仓库现有 `/api/v1`、本机 PostgreSQL 和虚构数据，**不需要用户提供任何新外部 API**。普通聊天生成动作、DeepSeek 真正联调属于 P2.6；到那时才需要一组可用的 DeepSeek API Key/基础地址，由用户写入本机 Git 忽略的 `.env`，不在聊天里发送密钥。GPT/本地模型可作为后续可选适配器。联网旅行推荐属于 P2.7，届时再选搜索服务并配置相应密钥；真实供应商 API 不在当前项目范围。

P2.5c 的业务规则与实施请用户分别确认；G-09 的合并确认只授权本机合并。
